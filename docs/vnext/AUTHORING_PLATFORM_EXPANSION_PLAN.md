# EasyCode 作者效率、统一 UI 与扩展能力实施计划

- 状态：Implementation complete（阶段 0–8 已完成；正式发布宿主门仍按第 11 节单独执行）
- 日期：2026-09-07
- 面向角色：脚本作者、扩展作者、Player 操作者
- 目标版本：首个正式版本之后的连续垂直切片；不得以未验证能力阻塞当前发布闭环

## 1. 目标与非目标

本计划解决两类相互关联的问题：

1. 建立项目唯一的 UI 原语和组合组件体系，使相同功能不再由不同页面各自实现不同外观。
2. 补足作者效率能力：可靠控件选择器、结构化操作录制、统一触发器、浏览器 DOM 自动化与可导入官方扩展包。

本计划不新增第二套脚本模型。`ProgramDocument` 仍是项目函数唯一可编辑事实，中央结构化编辑器、右侧详情和 Player 继续遵循现有契约。

本期明确不做：CLI/CI、复合模板市场、云端设备舰队、流程挖掘、组织租户、商业扩展市场、AI 自动规划、企业凭据库、人工审批中心和自动遥测。

## 2. 总体顺序决定

不采用“先重写整个前端，再开始任何功能”，也不采用“先堆功能，最后统一 UI”。执行顺序是：

1. 先补齐最小但完整的共享 UI 原语层和强制接入规则。
2. 先迁移新功能一定会复用的公共界面骨架。
3. 此后所有新功能只允许使用共享组件和设计令牌。
4. 旧页面随垂直切片逐步迁移，并删除被替代的局部样式和重复组件。
5. 每个切片同时完成 Schema、后端、前端、持久化、执行、Player、恢复、测试与文档。

因此，“统一组件地基”先于新功能；“全站每个旧页面全部迁移完”不必先于新功能。这样既阻止新增技术债，也避免长期停摆在纯视觉重构中。

## 3. 开工门与规格冲突

浏览器 DOM 自动化目前在 `PRODUCT.md` 和既有差距记录中属于非目标。进入实现前必须显式更新：

- `PRODUCT.md`
- `docs/ARCHITECTURE.md`
- `docs/DECISIONS.md`
- 相关 `docs/vnext/TARGETS*.md`、`FUNCTIONS*.md`、`EXTENSIONS*.md`
- `docs/TEST_HARNESS.md`

必须先冻结以下数据归属：

- 录制会话是临时状态；确认后只通过命令写入 `ProgramDocument`。
- 主选择器与后备策略共同属于同一个控件选择器，不要求用户捕获多个控件。
- `TriggerDefinition` 属于版本化 IDE 项目配置，首期绑定已有项目函数，不嵌入另一种脚本；Player 保持独立签名运行方案和计划控制面。
- 浏览器 DOM 动作表现为普通强类型函数调用；DOM 元素引用不与桌面 UIA 控件引用混用。
- 扩展清单、签名、安装范围和项目锁定文件分别是扩展身份、信任、可见性和可重现性的事实来源。

规格仍存在会改变上述路线的开放问题时，不进入实现。

## 4. 项目唯一 UI 体系

### 4.1 三层关系

第一层是全项目共享原语：

- `AppButton`、`AppIconButton`
- `AppInput`、`AppTextarea`、`AppSelect`
- `AppCheckbox`、`AppSwitch`
- `AppSearchField`
- `AppTooltip`、`AppMenu`
- `AppDialog`、`AppToast`、`AppNotice`
- `AppDisclosure`、`AppTabs`
- `AppBadge`、`AppProgress`、`AppSpinner`

第二层是工作区组合组件：

- `NavigationPane`
- `PaneHeader`
- `ListToolbar`
- `ObjectListItem`
- `InspectorSection`
- `InlineFieldRow`
- `EmptyState`
- `BottomPanel`

第三层是领域组件：函数行、Control 编辑器、目标编辑器、扩展详情、运行记录、Player 字段等。领域组件必须复用第一层原语，可以复用第二层组合，但不强行共用整页布局。

IDE 与 Player 共用强类型参数契约、令牌和 Control 原子组件；两者可按不同任务采用不同页面组合。

### 4.2 稳定需求

- **UI-SYS-001**：同语义控件只能有一个公共实现；页面不得复制按钮、输入框、搜索框、列表选中态或弹窗基础样式。
- **UI-SYS-002**：尺寸、圆角、边框、背景、文本色、图标色、间距、焦点环、悬停、按下、禁用、危险态全部由共享令牌控制。
- **UI-SYS-003**：默认字体只保留正文、辅助文字、标题三档；同一行不得用字号表达字段类别，优先使用颜色、字重和图标。
- **UI-SYS-004**：图标和文字在所有密度下按视觉中心对齐；不得依赖单页像素偏移修复。
- **UI-SYS-005**：能一行完成的表单保持一行；能在当前表单完成的编辑不打开弹窗；弹窗只用于确实需要独立上下文或较大工作区的任务。
- **UI-SYS-006**：Control 组件通过注册表声明类型、校验、展示、编辑、变量候选和 Player 映射，不允许页面自行猜测字段外观。

### 4.3 迁移顺序

1. 令牌、按钮、图标按钮、输入、选择、搜索、菜单、Tooltip。
2. 左侧边栏标题、工具栏、列表项、选中态和空状态。
3. 右侧检查器行、分组、Control 和内联操作。
4. 弹窗、通知、底栏、运行中心和问题面板。
5. 扩展中心、目标、资源、变量、Player 和剩余页面。

每迁移一类组件，必须删除重复样式并以静态扫描阻止重新引入。视觉回归至少覆盖默认、悬停、按下、焦点、禁用、错误、窄宽度和长中文文本。

## 5. 扩展包统一模型与体验路径

### 5.1 官方、用户与项目扩展的关系

三者使用同一种包格式、清单、签名和运行契约，区别只在来源、安装范围和治理方式：

- 官方扩展：由 EasyCode 发行，进入只读官方范围，可随 IDE 分发。
- 用户扩展：由用户导入，对该用户的多个项目可用。
- 项目扩展：由项目导入并锁定，只在该项目生效，便于可重现构建与发布闭包。

“官方自带”不应是另一套硬编码实现。它仍是一个扩展包，只是分发时被安装到官方范围。

### 5.2 本计划的强制体验原则

- **EXT-PKG-001**：本计划新增的所有“扩展路线能力”必须先产出为真实、可签名、可导入、可启停、可卸载、可发布的包。
- **EXT-PKG-002**：开发阶段不静默预装；作者必须亲自走完导入、查看权限、信任、启用、调用、打包、卸载和失败恢复。
- **EXT-PKG-003**：自动测试同样从安装包开始，不允许直接引用源码绕过安装器。
- **EXT-PKG-004**：验证稳定后，可以把完全相同的产物提升为官方随附包；不得维护“导入版”和“内置版”两份代码。
- **EXT-PKG-005**：项目创建向导未来可以明确勾选推荐包，但默认选择、体积和权限必须可见，不得伪装成核心能力或静默导入。

当前“包”可以继续采用已有的签名扩展目录。是否增加单文件安装载体应另立格式规格，不能在本计划中假定已有 `.ecxpack`。

### 5.3 第一批用于验证全流程的包

1. 最小 Python 计算扩展：验证最短作者路径、参数、返回值和错误。
2. Excel/CSV 扩展：验证文件权限、表格类型和 Player 发布闭包。
3. 浏览器 DOM 扩展：验证宿主依赖、元素捕获、会话和下载。
4. 最小 Android Kotlin/JVM 扩展：验证平台限定、离线闭包和签名。

验收要求：同一个包在用户范围与项目范围均可导入；卸载不会损坏项目文档；缺包时显示可恢复的明确错误；发布时能准确计算扩展和权限闭包。

## 6. 更可靠的控件选择器

### 6.1 用户视角

用户仍然只捕获一次、只选择一个目标控件。系统在这一次捕获中保存同一控件的多种定位描述，例如自动化 ID、名称、角色、窗口、层级路径、邻近文本和相对控件。这些不是两个控件，而是寻找同一个控件的主路线与后备路线。

默认流程：

1. 用户捕获一个控件。
2. 系统立即重新查找并显示“稳定 / 可能变化 / 当前不可验证”。
3. 系统自动选定主策略和确定性的后备顺序。
4. 用户一般无需额外操作；只有测试不稳定时才展开高级详情或重新捕获。
5. 运行失败时提供“重新捕获并修复引用”，用户确认后批量更新引用。

### 6.2 边界与失败语义

- 首期将后备策略嵌入现有 `ControlSelector`，不先引入庞大的共享控件仓库。
- 只有唯一、满足阈值且规则确定的候选可以自动使用后备策略。
- 多候选、低置信或语义冲突时必须停止并报告，不得静默点击“看起来差不多”的控件。
- 每次解析记录实际采用的策略，便于日志诊断。

验收：一次捕获可生成并测试多种策略；主策略失效时确定性后备成功；歧义时不误操作；重新捕获可在用户确认后修复全部引用。

## 7. 结构化操作录制

### 7.1 定位

录制器只负责快速搭建可编辑骨架，不承诺把整套业务意图一次录制正确。录制结果直接生成现有 `ProgramDocument` 语句，用户继续在中央编辑器和右侧详情精修。

### 7.2 首期可可靠录制的基础动作

- 单击、双击、右键、按住和释放
- 文本输入、按键和快捷键
- 滚动和拖动
- 应用启动、窗口激活和切换
- 操作间等待
- 控件目标或目标空间坐标

录制器不推断条件、循环、业务意图或任意扩展函数，也不承诺识别插件私有动作。后续扩展函数仍由用户在录制骨架中手动插入或替换。这个边界是正确且必要的。

### 7.3 控件树与游戏/画面区域

存在可靠控件树时，优先生成“查找控件并操作”的语句，并保留可测试的控件选择器。

不存在控件树的游戏、画布或远程画面中，记录目标空间坐标、拖动路径、按键与时间关系，并保存必要的录制前后帧作为建议证据。录制结束后可以提出：

- 将坐标点击替换为“等待图片并点击”；
- 在动作前增加“等待文字 / 等待图片”；
- 将区域内容转为 OCR 读取。

资源创建和语句替换必须由用户确认，不能自动制造大量无名图片或猜测游戏意图。

### 7.4 编辑与恢复

- 录制期间只写临时会话，不持续污染项目。
- 停止后进入轻量审阅：删除噪声等待、合并连续输入、命名资源、确认坐标或控件策略。
- “插入到当前位置”作为一次原子命令，可整体撤销。
- 权限不足、捕获中断或目标切换失败时保留可恢复草稿并说明未记录区间。

验收：桌面控件路径与无控件树路径均可形成可运行骨架；录制不创建第二种源码；用户可以在提交前审阅；提交后一次撤销完整恢复。

## 8. 统一触发器系统

触发器只回答“什么时候启动”，首期执行对象始终是已有项目函数，不引入第二套脚本。Player 触发入口不复用开发机配置，继续由 Player 运行方案和计划控制面负责。

### 8.1 第一阶段

- Windows 全局快捷键
- 应用启动、退出或获得焦点
- 文件或目录变化
- 系统启动或用户登录

### 8.2 第二阶段

- 输入缩写自动展开
- 剪贴板变化
- HTTP Webhook
- 受权限控制的消息入口

`TriggerDefinition` 必须版本化，并声明启用状态、目标入口、防抖、冷却时间、并发策略、运行目标、权限和失败通知。入口统一放在运行中心的“启动方式”，避免散落到脚本编辑器各处。

验收：禁用触发器零副作用；相同事件风暴不会无限创建运行；冲突快捷键可解释；项目函数改名或删除时能修复绑定；Player 发布确定性排除 IDE 触发器。未来若增加“随 Player 发布”，必须另立终端权限、配置和宿主生命周期切片。

## 9. 浏览器 DOM 自动化

### 9.1 用户体验

浏览器 DOM 功能在作者侧与官方函数完全同一种使用方式：从函数库搜索、插入中央语句、在右侧编辑参数、使用 `@变量` 与 `.字段`、进入日志和返回值体系。不得新增第二个脚本编辑器或独立“新地盘”。

可以有一个轻量的浏览器连接/元素捕获入口，用于显示连接状态、选择标签页和拾取元素；它只是目标管理工具，不是另一套编辑环境。

### 9.2 内部实现与包形态

首期实现为第一方签名扩展包，贡献浏览器宿主、DOM 选择器类型、函数和必要的捕获能力。开发与验收阶段必须由用户手动导入这个包，完整体验安装生命周期；验证成熟后，才决定是否随 IDE 作为官方包分发。

即使以后成为官方随附包，项目也必须显式启用；未启用时不得启动浏览器宿主、下载运行时或产生后台连接。

### 9.3 首期能力

- 启动、连接、关闭浏览器
- 打开地址、前进、后退、刷新、等待页面状态
- 查找、等待、点击、输入、选择 DOM 元素
- 按文本、角色、标签、稳定属性和有限 CSS 定位
- 读取文本、属性、表格与表单值
- 标签页、窗口、iframe 和下载管理
- Cookie/会话操作作为高级能力

先支持本机 Edge 与 Chrome。Firefox、Safari、远程浏览器、任意 JavaScript 注入和网络拦截暂缓。

DOM 选择器和桌面 UIA 控件选择器必须是不同强类型，但可以共享“捕获、立即测试、稳定性提示、重新捕获”的交互组件。

验收：用户从扩展导入到函数插入不经过特殊脚本模式；页面变化时等待语义可靠；多标签页和 iframe 目标明确；浏览器最小化条件下按能力声明运行；离线发布不会运行期下载。

## 10. 明确暂缓项

### 10.1 CLI 与 CI

CLI 的确意味着不打开 IDE，也可通过命令行检查、测试、运行、打包和导出报告。它需要稳定项目加载器、退出码、无界面执行宿主、凭据/权限策略和机器可读报告，复杂度中等，不是简单增加几个命令。本期暂缓，待 IDE/Player 契约和打包闭包稳定后再立项。

### 10.2 模板与示例生态

模板本质上是由多个官方函数组成、可插入的复合脚本骨架。它有价值，但本期先用结构化录制解决“快速搭骨架”，暂不建设模板浏览、版本和导入体系。

### 10.3 企业重能力

云端设备舰队、流程挖掘、大型组织权限、多租户、商业市场、AI Agent 自动规划、企业凭据库、人工审批中心和自动遥测继续保持范围外。

## 12. 完成定义

只有同时满足以下条件，相关切片才算完成：

1. 用户面对相同语义时看到相同组件、状态和交互，不因页面不同而重新学习。
2. 新能力没有绕开 `ProgramDocument`、Control 契约、扩展契约或发布权限闭包。
3. 扩展路线能力能从真实包导入开始完成安装、使用、发布、卸载与恢复。
4. 核心能力与扩展能力边界清晰：录制、选择器和触发调度属于平台；浏览器、Excel 等领域集成可作为包交付。
5. 自动验证、人工验证、未验证和环境阻塞被明确区分。
6. 对应平台真实宿主和离线场景通过 `docs/TEST_HARNESS.md` 的完成门。
