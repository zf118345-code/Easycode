# 运行计划与批量调度

状态：`Approved`（首版触发类型、Windows 跨项目批量、Android 单 APK 边界、同实例串行、LAN 特权派发与幂等语义已冻结；实现证据和数值预算仍由 Harness 管理）

最近修订：2026-09-03

当前实现证据（2026-09-03）：Windows 与 Android 模拟器已使用真实配对身份和加密 LAN 通道完成 `dispatch.start → 普通 Android Runtime → dispatch.status` 闭环。同一 `dispatch_id` 以两个不同网络 `request_id` 连续提交时，两次均返回同一个确定性 `run_id`，设备只保存一条派发记录并最终收束为 `completed`；复用该编号但改变条目内容会以 `schedule.dispatch_identity_conflict` 拒绝。Android Player 内撤销“远程启动”并保存后，Windows 刷新权限即以 `lan.remote_permission_remote_start_denied` 阻止派发，恢复授权后状态同步。上述为模拟器与同机 ADB 转发下的真实应用交互证据，不替代两台物理设备、公网阻断、休眠/重启和真机长稳验收。

## 1. 产品结果

运行计划让终端用户在 Player 运行中心配置单次、每日或固定间隔触发，并在一次触发中启动一个或多个已安装项目和运行方案。Windows Player Hub 可以调度当前 Windows 用户已安装的多个签名项目，也可以向已经配对并授权的局域网实例派发启动请求；Android 本机 Player 只调度当前 APK 内的运行方案，但可以作为已配对实例接收当前 APK 的远程启动请求。

计划只负责“何时在何处创建普通任务”。项目函数、消息、条件、数据传递、页面恢复和 GUI 业务重试仍由 ProgramDocument 表达。计划不是脚本函数，不进入函数目录、ProgramDocument、ECIR 或项目内容更新包。

## 2. 宿主与控制面边界

- **Windows Player Hub** 是当前 Windows 用户的计划拥有者、已安装产品注册表和本机实例调度器。它使用随用户登录启动的 Agent 拉起签名 Player；GUI 自动化不在 Windows Session 0 服务中运行。
- **Android Player** 在当前 APK 的应用私有目录保存本 APK 的计划、运行方案引用和触发记录。一个项目 APK 不枚举、读取或启动其他项目 APK 的方案。
- **计划拥有者** 是创建并保存计划的本机 Agent。跨机计划不复制为多个可独立触发的主副本，也不自动选举新协调器；拥有者离线期间远端不会自行猜测触发。
- **LAN Dispatch Gateway** 只接收经过配对、授权和防重放验证的启动命令。它可以与普通消息共享设备身份和加密传输，但不使用 `消息.发送`、消息已读或监听器代替远程启动协议。
- **Execution Service** 在目标设备完成本地预检并创建普通 `run_id`。调度成功只说明任务被目标运行时接纳；任务最终成功、失败、停止或暂停仍使用现有运行状态机。

同机同项目的本地实例通过操作系统用户边界和项目命名空间自动信任。Windows Hub 跨本机项目启动来自用户在本机计划中的显式选择，不需要把项目间普通消息权限扩大为自动互信。跨设备配对与权限契约见 [`NETWORK.md`](NETWORK.md)。

## 3. 领域模型

### 3.1 计划与条目

`SchedulePlan` 至少包含：

- 稳定 `schedule_id`、单调 `revision`、显示名、启用状态；
- IANA `timezone_id` 和一种类型化触发器；
- 错过策略、重叠策略和批次派发模式；
- 有序 `PlanEntry` 列表；
- 创建者、创建时间、最近修改时间和下一次计算触发时间。

每个 `PlanEntry` 至少包含：

- 稳定 `entry_id` 与显示顺序；
- `host_id + instance_id`；
- `product_id + profile_id`；
- 可选的确定性 `start_offset` 和 `start_deadline`；
- 是否启用，以及保存时最后验证到的产品、方案和目标摘要。

显示名、窗口标题、ADB 临时端口和列表位置都不是运行身份。产品、方案、实例或设备重命名只更新投影，不改写上述稳定引用。

### 3.2 触发记录与派发记录

每个到期点生成一个不可变 `Occurrence`，至少包含：

- `occurrence_id`、`schedule_id`、触发时使用的 `schedule_revision`；
- 计划到期时间、实际发现时间和触发来源；
- 当次不可变条目快照；
- 批次状态和每个条目的独立结果。

每个条目的 `dispatch_id` 由 `occurrence_id + entry_id` 唯一确定。协调器重试、进程恢复和 LAN 重连必须复用相同 `dispatch_id`；目标 Agent 在一个本地事务中写入接纳记录并创建 `run_id`，重复请求只返回原结果，不能创建第二个任务。

该幂等契约只保证 EasyCode 任务不会因派发重试被启动两次。项目已经执行到外部游戏、文件或 API 的副作用仍遵守普通脚本语义，不能宣称“外部世界恰好执行一次”。

## 4. 触发器与时间

首版只提供三种触发器：

1. **单次**：一个带 `timezone_id` 的本地日期时间。条目达到终态或超过补跑窗口后，计划自动停用并保留历史。
2. **每日**：一个本地墙上时间和 `timezone_id`。夏令时导致该时间不存在时在下一个有效时刻触发；同一墙上时间重复出现时只触发一次，记录实际 UTC。
3. **固定间隔**：由 `anchor_time + n * interval` 计算计划到期点。任务耗时不会把后续到期点永久向后漂移；同一计划仍受重叠策略限制，不并发创建多个批次。

系统时间、时区或夏令时规则变化时，Trigger Engine 使用持久化的上次已处理到期点重新计算未来 occurrence。时间回拨不能重复已经落盘的 `occurrence_id`，时间前跳按错过策略处理。

首版错过策略只有：

- **跳过**：记录错过原因，不创建任务；
- **在最大迟到时间内补跑一次**：拥有者恢复、实例上线或权限恢复时，如果仍在窗口内，则为所有尚未过期的条目创建一次合并补跑。

每日或固定间隔无论错过多少个到期点，都不得无界回放历史，只能跳过或合并为一次补跑。首版重叠策略只有“跳过本次”和“排队一次”；相同计划已经运行、排队或主动暂停时，不得为每个新到期点累积队列。

## 5. 批次、串行与错峰

- 同一 `instance_id` 任意时刻只允许一个普通任务运行。运行、启动中、停止中和主动暂停都占用实例；该实例的计划条目按接受顺序 FIFO 排队。
- 不同实例可以并行接纳任务。选择“同时派发”时，计划拥有者在同一 occurrence 内并发提交各实例条目；一个条目失败不把其他条目标记为失败。
- 选择“错峰派发”时，每个条目按有序 `start_offset` 计算最早派发时间。条目实际开始还要等待自己的实例空闲和本地预检，因此错峰时间是最早边界，不是假定准点完成的承诺。
- 同一实例出现多个条目时始终按条目顺序串行；跨实例不得因为某个实例离线而形成全批次屏障。
- 批次默认继续处理相互独立的后续条目。需要“上一步成功才执行下一步”、跨任务传值或业务补偿时，开发者应把逻辑放入一个项目流程或使用 `消息.*`，不能把计划条目扩张为第二套工作流语言。

用户点击“立即运行”会生成新的手动 occurrence，不改写下一次计划时间。禁用或删除计划只阻止未来 occurrence；已经接纳的普通任务继续。停止当前批次是独立动作，目标离线时只记录“停止待确认”，收到远端终态前不得显示已停止。

## 6. 本地预检与版本快照

目标 Agent 收到本地或 LAN 派发后，按以下顺序处理：

1. 验证设备配对、远程启动授权、请求有效期、`dispatch_id` 和防重放信息；
2. 解析本机已安装且签名有效的 `product_id`，确认平台、Runtime、扩展和依赖闭包兼容；
3. 解析本机 `profile_id`，重新校验 Player Schema、目标绑定、权限和未确认字段；
4. 检查强制更新是否已经阻止该版本创建新任务；
5. 检查实例是否空闲；空闲则创建不可变启动快照和 `run_id`，忙碌则按 occurrence 策略排队或跳过；
6. 把接纳、排队或结构化拒绝结果返回计划拥有者并写入本地诊断。

未来触发使用目标设备在触发时已安装且允许启动的版本，并从当时保存的运行方案生成不可变参数覆盖快照。计划不固定永远使用旧 `release_id`，也不因内容更新静默修复失效方案。更新造成字段不兼容时，条目进入“方案需要检查”，直到用户修复后才可运行；已经接纳的任务继续固定原 `release_id`。

## 7. LAN 派发、离线与状态收束

- 未配对、已撤销、未知或没有远程启动授权的 `host_id/instance_id` 在保存或派发时立即失败，不进入离线队列。
- 已配对且仍在可信注册表中的实例暂时离线时，计划拥有者可以把同一 `dispatch_id` 保留到条目 `start_deadline`；目标恢复后只派发一次，超过期限记为错过。
- 计划拥有者在到期时离线或未运行时不能触发远端。拥有者恢复后根据 occurrence 到期点和错过策略生成零个或一个补跑批次。
- 目标 Agent 已接纳任务后，即使协调器或 LAN 随后断开，任务仍在目标设备本地运行。拥有者显示“远端状态未知”，重连后使用 `dispatch_id/run_id` 查询并收束，不能重新启动。
- Agent 在线与操作目标在线是两种状态。窗口不存在、ADB 断开、手机权限撤销或 Android 后台限制必须返回目标/权限阻塞，不能伪装成设备离线或任务成功。
- 协调器、目标 Agent、操作目标、产品、运行方案、权限和更新限制分别产生稳定错误码；一个条目的错误只影响该条目和同实例队列。

所有 LAN 调度都属于“本机或局域网”能力，不依赖 EasyCode 云、公网账号、云端在线设备面板或公网中继。

## 8. 平台差异

### 8.1 Windows

- Windows Hub 可以在当前用户会话中枚举受信任注册表里的多个已安装 EasyCode 产品和运行方案，并创建独立 Player 实例。
- Agent 可以随用户登录启动，但不能声称在用户注销、没有交互桌面或 Session 0 中继续完成窗口、截图和物理输入自动化。
- 锁屏、UAC 安全桌面、目标进程权限级别高于 Agent、物理输入不可用或桌面被切换时，目标预检返回等待或阻塞；不得向不可交互桌面盲发点击。
- 同一物理窗口或 ADB 设备不能被两个本机实例并发占用。宿主内部目标占用检查只用于保护实际驱动，不向脚本恢复已经取消的通用 `租约.*` 能力。

### 8.2 Android 本机

- Android 本机计划只能引用当前 APK 内的 `product_id` 和运行方案。Android 不提供跨已安装项目 APK 的 Hub、方案读取或批量拉起。
- Android 可以接收已授权 LAN 主机对当前 APK 的远程启动，但仍必须在本机完成签名、方案、目标和系统权限预检。
- 系统可能因休眠、后台执行限制、前台服务、通知、MediaProjection、无障碍或用户强制停止应用而延迟或阻止触发。Player 必须记录计划时间、实际触发时间和阻塞原因，不能承诺闹钟级精确启动。
- 设备重启后 Player 重新登记未来计划；应用被用户强制停止后，必须由用户重新打开才能恢复计划。已失效的截图或输入授权不能由计划静默重新取得。

## 9. 诊断与隐私

计划、occurrence、dispatch 和 run 使用稳定关联 ID。每条诊断至少记录计划时间、实际时间、拥有者、目标主机/实例、产品/方案、`schedule_revision`、`occurrence_id`、`dispatch_id`、`run_id`、状态变化和结构化原因。

诊断默认只保存在相关设备。用户主动导出时，系统生成脱敏包并列出包含项；运行方案值、消息正文、HTTP 正文、配对短期码、私钥和认证令牌默认不进入诊断。EasyCode 不自动上传计划、在线设备、崩溃或任务结果，也不建设云端在线设备面板。

## 10. 稳定需求

- `[REQ-SCH-001]` 运行计划必须使用类型化单次、每日或固定间隔触发器、IANA 时区和稳定 `schedule_id/revision`，不能保存自由 cron 文本作为首版事实。
- `[REQ-SCH-002]` Windows Hub 必须能引用当前用户已安装的多个签名产品与方案；Android 本机只能引用当前 APK 的方案。
- `[REQ-SCH-003]` 计划必须保存稳定主机、实例、产品、方案和条目 ID；重命名不得破坏引用。
- `[REQ-SCH-004]` 每个到期点必须生成不可变 occurrence 和条目快照；编辑计划只影响未来 occurrence。
- `[REQ-SCH-005]` 同一实例必须串行执行，运行和主动暂停均占用实例；不同实例可以并行或按确定性 offset 错峰。
- `[REQ-SCH-006]` 每个条目的 `dispatch_id` 必须稳定；网络重试、ACK 丢失、协调器重启和目标重连不得创建第二个 `run_id`。
- `[REQ-SCH-007]` 错过策略只能跳过或在有界窗口内合并补跑一次；重叠策略只能跳过本次或排队一次，不得累积无界历史。
- `[REQ-SCH-008]` 计划拥有者必须是唯一触发权威；首版不得复制多主计划、自动选主或在协调器离线时让远端猜测触发。
- `[REQ-SCH-009]` LAN 远程启动必须使用独立特权协议和显式授权，不能由普通消息、消息已读或项目监听器隐式获得启动权限。
- `[REQ-SCH-010]` 未知、未配对、已撤销或未授权实例必须立即失败；已知离线实例只能在条目 TTL 内保留同一派发，过期后标记错过。
- `[REQ-SCH-011]` 目标 Agent 必须在本机重新验证产品签名、版本/Runtime、方案 Schema、目标、权限、强制更新和实例占用后才能创建任务。
- `[REQ-SCH-012]` 已接纳远端任务在 LAN 断开后必须继续本地运行；协调器重连时查询原派发状态，不能重启任务。
- `[REQ-SCH-013]` 禁用或删除计划不得停止已接纳任务；远程停止未确认时不得伪报成功。
- `[REQ-SCH-014]` 计划任务必须使用普通运行状态机；崩溃后不恢复旧调用栈，后续 occurrence 创建新的运行现场。
- `[REQ-SCH-015]` 方案删除、不兼容更新、目标离线、权限撤销、实例忙和强制更新限制必须产生不同条目状态，不能把整个批次统一标记为离线或失败。
- `[REQ-SCH-016]` Windows 计划只能在可交互用户会话中启动 GUI 自动化；锁屏、注销、提权或桌面不可用时必须阻止受影响动作。
- `[REQ-SCH-017]` Android 必须按系统允许范围尽力触发并记录迟到；强制停止、后台限制或权限失效时不得伪报准时运行。
- `[REQ-SCH-018]` 本机计划不得依赖公网；LAN 计划不得回退到 EasyCode 云或公网中继。
- `[REQ-SCH-019]` 计划与派发诊断必须保留稳定关联 ID 和真实状态，同时默认排除方案秘密、正文、配对码、私钥和令牌。
- `[REQ-SCH-020]` 计划控制面不得注册脚本函数、进入 ProgramDocument/ECIR 或把批次条目扩张为条件工作流。

## 11. Harness 验收

- `[AC-SCH-TIME-001]` 虚拟时钟覆盖单次、每日、固定间隔、重启、时区变化、夏令时跳过/重复和系统时钟前后跳；同一到期点最多生成一个 occurrence。
- `[AC-SCH-MISFIRE-001]` 协调器错过连续 100 个到期点后只跳过或合并补跑一次；“排队一次”不形成第二个等待批次。
- `[AC-SCH-IDEMPOTENCY-001]` 超时、重复提交、ACK 丢失、协调器崩溃和目标重启反复发送同一 `dispatch_id` 时，目标始终返回同一 `run_id`。
- `[AC-SCH-SERIAL-001]` 同一实例在运行、启动、停止和主动暂停状态下都不会并发创建第二任务；FIFO 顺序与跳过/排队策略一致。
- `[AC-SCH-PARALLEL-001]` 不同实例可独立并行；错峰条目不早于各自 offset 派发，一个实例离线不阻塞其他实例。
- `[AC-SCH-OFFLINE-001]` 协调器离线、已知目标 Agent 离线、未知实例、LAN 分区和操作目标离线分别产生正确状态、TTL 与恢复行为。
- `[AC-SCH-REMOTE-RUN-001]` 远端接纳后断开 LAN，目标任务继续并写终态；协调器恢复后查询原 run，不产生重复任务。
- `[AC-SCH-PREFLIGHT-001]` 产品/方案删除、签名失败、Schema 需要检查、目标断开、权限撤销、实例忙和强制更新受限逐项阻止对应条目并给出修复动作。
- `[AC-SCH-PAIR-001]` 未配对、权限撤销、过期命令、重放和伪造主机请求被拒绝并审计；普通消息权限不能启动任务。
- `[AC-SCH-WIN-001]` Windows 真实宿主完成两个已安装产品、多方案、并行/错峰、登录启动、锁屏、UAC 权限差异和相同目标占用测试。
- `[AC-SCH-AND-001]` Android 真机仅列出本 APK 方案，覆盖重启、后台、休眠、网络切换、强制停止、前台服务和权限撤销，并记录计划/实际时间与真实阻塞。
- `[AC-SCH-LAN-001]` 公网阻断时 Windows→Windows、Windows→Android 的已配对 LAN 派发仍工作；抓包证明没有云端发现、在线设备面板或公网回退。
- `[AC-SCH-UPDATE-001]` 内容更新保持兼容方案可继续计划运行；不兼容方案进入需要检查；运行中的 release 不切换，强制受限版本不创建新计划任务。
- `[AC-SCH-DIAG-001]` 批次部分成功、停止待确认和远端状态未知均可通过 schedule/occurrence/dispatch/run ID 追踪，导出包不包含禁止数据。

## 12. 首版不包含

- 自由 cron 表达式、依赖图、条件分支、跨批次变量和计划内业务补偿；
- 多主计划复制、自动选主、云端调度、公网中继和云端在线设备面板；
- 通过调度下发或安装项目、ECIR、扩展、任意参数、文件或系统命令；
- Android 跨项目 APK 批量启动、被用户强制停止后的静默自启、闹钟级准点承诺；
- 任务崩溃后自动恢复旧调用栈，或对外部 GUI/API 副作用承诺恰好一次。

默认 TTL、最大条目数、最小间隔、Agent 心跳、幂等记录保留期、历史保留期和时间容差由 Harness 在 Windows 与 Android 基线设备上冻结；这些数值不得改变本文件的有界队列、同实例串行、无云和平台边界。

## 13. 当前实现证据与边界

2026-09-03 已把本机计划核心扩展为 Windows Player Hub 与 Android 当前 APK 垂直切片：

- `core/vnext/schedule_v6.py` 使用事务型 SQLite 保存类型化计划、不可变 occurrence、条目快照、dispatch、实例 FIFO 状态和脱敏结构化诊断；单次、每日、固定间隔、IANA 时区、DST、有界错过合并和“跳过/排队一次”重叠策略由虚拟时钟覆盖；
- `core/vnext/schedule_registry_v6.py` 建立当前用户的已安装产品、发布版本、独立 Player 实例和可复用批次注册表。注册时和每次启动前都会复验固定信任根、`.ecplayer` 签名、构建清单、文件哈希、路径边界与方案引用；同一产品的签名身份被固定，发布切换使用 revision 冲突检测，旧发布可以作为显式回退目标；
- `core/vnext/schedule_hub_v6.py` 把 `LocalDispatchPort` 接到普通 Player Runtime。`dispatch_id` 对应稳定 `run_id`，重复接纳、重复 ACK 或 Hub 进程重启不会创建第二个运行身份；普通任务终态回写计划历史并释放同实例 FIFO，不同实例可以并行或确定性错峰；
- Windows 使用单个当前用户 `EasyCode.PlayerHub` 任务唤醒 Agent，而不是为每条计划膨胀系统任务。任务以 `InteractiveToken + LeastPrivilege` 运行，随登录恢复并只登记最近一次系统唤醒；安装或更新失败时恢复先前任务定义；
- Windows 目标运行前检查活动用户会话、可交互桌面、锁屏/安全桌面、签名产物、方案 revision、目标与危险操作。无人值守计划发现需要逐次确认的递归删除时直接阻止，不伪造用户确认；Agent 重启后不恢复旧 GUI 调用栈，而是记录结构化中断结果；
- `/api/vnext/player-hub` 与 `/api/vnext/schedules` 提供严格字段、revision、登记、实例、发布切换、批次、计划、历史、诊断与 Agent 管理接口；独立的 loopback-only `/api/vnext/player-hub/lan` 路由承接监听、发现、配对、三项权限、撤销和诊断。`VNextScheduleWorkspace.vue` 的实例与设备区只显示真实本机实例、已配对设备与 LAN 状态，不显示云设备面板；
- `core/vnext/lan_schedule_v6.py` 把远端引用解析、加密 `dispatch.start/status` 与目标侧普通 SQLite admission 串接。远程启动必须有独立授权和产品/实例范围；同一 `dispatch_id` 在 ACK 丢失或重试时返回原 `run_id`，计划仍只保存在协调端；
- Android `AndroidScheduleStore`、`AndroidScheduleCoordinator` 与系统 `AlarmManager` 在应用私有目录保存当前 APK 的单次、每日和固定间隔计划。触发时重新打开签名内容与运行方案，检查 MediaProjection、Accessibility、交互确认和实例占用，随后进入同一普通 Runtime；系统广播使用 `goAsync` 并等待 occurrence 已持久接纳后才结束；
- Android 共享 Player 提供当前 APK 范围的计划列表、编辑、立即运行、启停、删除和 occurrence 历史，没有加入 cron、跨 APK Hub 或第二套工作流。固定间隔按锚点计算、不随运行时长漂移，系统迟到会同时保存计划时间和发现时间；
- 计划仍属于宿主控制面，没有新增 `计划.*` 函数，也没有把计划写入 ProgramDocument 或 ECIR。
