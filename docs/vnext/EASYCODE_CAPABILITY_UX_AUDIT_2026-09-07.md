# EasyCode 脚本能力与操作体验审查报告

审查日期：2026-09-07  
审查性质：只读产品、实现与交互审查；未修改项目业务数据或生产代码  
事实基线：格式 6 / ProgramDocument 1 / ECIR 1

## 1. 一句话结论

EasyCode 当前已经不是“录一段鼠标键盘动作”的宏工具，而是一套面向开发者和高级自动化作者的、强类型、本地优先、可发布的跨平台结构化自动化平台。

它现在最擅长的是：把 Windows、ADB 和 Android 上的视觉、OCR、控件、输入、文件、网络与业务判断组合成可读、可检查、可调试、可复用并可打包交付的中大型流程。加入扩展函数后，它还能承接路径规划、专用识别、行业协议和第三方系统适配等领域算法。

正式范围内已经没有已知 `Open` 的源码功能空洞，但这不等于“首个正式版本已经可以放行”。24 小时最终候选长稳、生产签名、干净客户机、Android 脱离数据线/IDE/后端的最终矩阵等仍未完成。

## 2. 本次审查怎样区分事实

报告使用四种证据等级：

- **当前实现**：从正在运行的 API、源码或当前 UI 直接核对。
- **自动验证**：当前工作树的聚焦测试实际通过。
- **既有真实证据**：仓库发布审计中记录的 Windows、ADB、模拟器或物理 Android 结果。
- **未验证/延期**：规格允许或源码已实现，但缺少对应真实环境的最终证据。

不能把“规格写了”当作“已经实现”，也不能把模拟器或共享 Python Runtime 当作 Android 本机最终证据。

## 3. EasyCode 能实现什么级别的脚本

### 3.1 能力等级判断

| 等级 | 典型产品 | EasyCode 当前结论 |
| --- | --- | --- |
| L1 简单宏 | 固定坐标、按键录制、顺序回放 | 已明显超过 |
| L2 可靠 GUI 自动化 | 图像/OCR/控件识别、等待、判断、失败处理 | 已具备 |
| L3 可维护自动化应用 | 强类型变量、项目函数、调试、Player 表单、发布 | 已具备，核心闭环成熟 |
| L4 可扩展领域平台 | 第三方函数、领域工作区、宿主变体、发布闭包 | 架构与实现地基已具备，作者体验仍需实战样例收口 |
| L5 云端通用 RPA/设备舰队 | 云编排、DOM 自动化、远程设备治理、商业市场 | 明确不是当前产品范围 |

因此，最准确的定位是：**专业级本地结构化 RPA/自动化应用平台，具备向垂直领域平台扩展的能力，但不是通用编程语言，也不是云端设备舰队产品。**

### 3.2 当前实际能力盘点

当前运行服务实际返回：

- 78 个官方函数，全部为 `available`；
- 78 个函数都带版本化中央语义摘要；
- 97 个已登记、可执行的纯值操作；
- 64 个官方函数会返回可继续使用的结果；
- 结构化控制另含条件、循环、跳出、跳过、异常区域、目标作用域、返回和主动失败等，不混入官方函数数量；
- 当前 Windows 平台目录 78/78 为 `verified`；Android 本机目录仍统一显示 `planned`，这是刻意的发布保护，不代表源码没有 Android 实现。

官方函数覆盖：窗口、等待、画面、剪贴板、控件、目标、目录、日志、时间、输入、随机、图像、网络、文件、文字、项目、消息、颜色和应用。

纯值操作覆盖：文本、数值、日期时间、持续时间、可选结果、条件选择、坐标/区域、颜色、列表、字典、JSON 和文件引用派生。它们可以递归组合，但不会把有副作用的普通函数偷偷嵌入表达式。

## 4. 它现在很适合制作哪些脚本

### 4.1 视觉驱动的桌面或移动自动化

例如：等待按钮图片出现，点击，等待消失，OCR 读取状态，再依据文字进入不同分支。相比固定坐标宏，这类脚本能够显式处理“没找到”“超时”“目标变化”和“有结果/无结果”。

适合：游戏或模拟器辅助流程、桌面软件重复操作、无人值守状态检查、图像回归、无法提供 API 的旧软件。

### 4.2 控件驱动的可靠业务流程

Windows UIA、ADB UIAutomator 和 Android Accessibility 被统一投影为“控件”。脚本可以查找、等待、点击、读文字、输入、读状态、聚焦、设置值、选择项目、切换开关和滚动到控件。

适合：企业桌面表单录入、客户端软件批处理、安装配置、测试自动化。对 SurfaceView、游戏画布等没有语义树的界面，则应回到图像/OCR，而不是伪造控件能力。

### 4.3 数据、文件和 API 混合流程

脚本可以处理文本、列表、字典、JSON、文件、目录、HTTP 请求、上传和下载，并把结果用于后续判断或写入。文件传输与普通 JSON 请求被分开建模，避免把大文件塞进变量或日志。

适合：批量文件整理、报告生成、接口取数后驱动 GUI、下载资源后自动处理、跨运行通过显式文件保存状态。

### 4.4 可复用的中大型业务流程

项目函数、局部变量、项目变量、提取函数、稳定引用、错误区域、调试断点和结构化日志，允许把几十到上万条语句拆成可理解的业务块。10,000 条语句和 1,001 个函数已有性能基线。

适合：长期维护的自动化项目，而不只是一次性脚本。

### 4.5 给非作者使用的 Player 工具

作者可以只把必要参数发布为 Player 表单，让终端用户选择图片、文件、目录、区域、目标或填写业务值，而不暴露 ProgramDocument。Windows 与 Android Player 共用 Control 契约和渲染层，平台权限由各自原生宿主承接。

适合：把内部脚本包装成“同事只需填表并点击运行”的小型自动化产品。

### 4.6 多实例、计划与局域网协作

系统具备计划、批次、实例配对、消息、监听和幂等派发能力。单个 Player 内保持串行，跨实例才并行，避免多个流程同时抢同一窗口或设备。

适合：多开实例轮询、局域网内分工、定时执行和批量运行。两台独立物理宿主的完整网络矩阵仍处于延期验证状态。

## 5. 加上扩展后，能力上限在哪里

### 5.1 扩展特别适合承接的内容

- 专用图像算法、模型推理、路径规划和复杂匹配；
- 某个行业或软件的协议封装；
- 复杂数据计算、报表算法和格式转换；
- 企业内部系统适配器；
- 官方函数不应承担的单项目、单游戏或单客户领域逻辑；
- 受信任的目标驱动或原生能力。

扩展函数仍作为普通流程语句出现，使用同一函数库、中央摘要、右侧参数 Control、结果绑定、调试和 Player 发布链路。用户不需要学习第二套“扩展脚本语法”。

### 5.2 扩展的真实入口与生命周期

当前扩展中心已经具备以下真实入口：

1. 新建外部扩展骨架，或导入已签名扩展文件夹；
2. 在 PyCharm、VS Code、Android Studio 等外部 IDE 编写实现；
3. 回到 EasyCode 校验清单、签名、契约、权限、依赖和宿主变体；
4. 明确信任本地代码；
5. 构建密封运行产物、导入 Android JAR、运行契约测试；
6. 启用并把精确版本、哈希和函数契约写入 `easycode.lock`；
7. 扩展函数进入统一函数库，像官方函数一样插入和配置；
8. 发布时只携带锁定的密封产物，不携带源码、测试或外部 IDE 配置；
9. 停用、取消信任或删除前进行引用分析，避免留下失效调用。

Worker 能隔离超时、崩溃、取消和序列化失败，但它不是针对恶意代码的安全沙箱。扩展是受信任的本地代码。

### 5.3 本次不能证明的部分

当前活动项目的扩展 API 返回 `packages: []`。也就是说，本次能确认扩展平台、入口、源码和自动测试闭环，但不能声称“用户当前的某个自定义扩展包已经在这个项目中实跑通过”。

仓库已有中立扩展与 Android Kotlin/JVM 的真实 Harness 证据；C++/NDK 变体仍未实现，不能对外宣称支持。

## 6. 明确不适合或不属于当前范围的脚本

以下不是遗漏，而是当前产品边界：

- 浏览器 DOM、网页选择器、浏览器会话接管和验证码自动化；
- 页面拓扑、Page Model、自愈导航和“页面.*”能力；
- iOS 和 macOS；
- 在项目函数中直接写任意 Python、PowerShell、Shell 或命令行；
- 单个 Player 内的任意并行流程；
- 云端设备舰队、在线设备监控、运行遥测和公共扩展市场；
- 商业授权/VIP 激活。

如果未来用户的主场景转向网页后台，浏览器 DOM 会成为一个新的产品纵向切片，而不是再加几个函数就能补齐的小功能。

## 7. 操作入口与交互审查

### 7.1 已经做得好的部分

- **函数发现**：函数库按用途分组，搜索“控件”会直接出现 12 个相关函数，名称和中央摘要使用用户语言。
- **就地快速插入**：主流程、空“那么”分支和“否则”入口都能在当前位置打开搜索；输入“控件”会展示可插入函数，Enter 插入、Esc 取消，不必回左栏拖找。
- **值语法发现**：`@` 只显示变量或结果本体，`.` 再逐级发现字段；命名空间、`Ctrl+Space`、参数候选和运算符来自同一注册表，避免“支持了但用户不知道”。
- **中央与右侧分工**：中央只展示流程语义，完整参数在右侧；当前图像等待行能明确表达“等待图片出现 → 保存结果”，没有把内部 ID 当正文。
- **表单渐进披露**：图片、相似度、区域、超时是主要字段，高级参数折叠；测试按钮会说明缺少图片，不伪造可用状态；“根据结果添加条件”靠近返回值。
- **响应式行为**：窄屏时函数库和检查器变为互斥抽屉，避免把中央编辑区压到不可用；键盘与无障碍名称完整。
- **扩展一致性**：扩展函数不创建第二套表单或中央组件，受控扩展工作区也必须使用共享 UI 契约。

### 7.2 仍会影响用户满意度的地方

#### P1：扩展首次成功路径仍偏“工程化”

扩展中心的生命周期完整，但“签名、信任、构建、测试、启用、锁定、宿主变体”对第一次写扩展的人仍然很多。现有界面提供动作，却还缺少一条足够强的、按当前状态计算的“下一步建议”。

建议不是删掉安全步骤，而是增加单一主路径：

- 当前只显示一个推荐主动作，例如“完善契约”“信任代码”“构建产物”“运行测试”“启用”；
- 其余动作保留在次级区域；
- 每一步失败都给出外部 IDE 中应修改的文件和回到 EasyCode 后应执行的下一动作；
- 提供一个正式、可复制的“最小扩展”示例，从创建到 Windows Player 发布全程走通。

#### P1：缺少真实新用户的 15 分钟验收

当前交互已经可发现，但自动测试不能证明第一次使用的人能在 15 分钟内完成“找图 → 点击 → 等待 → 日志 → Player 参数”。应安排至少 3 名未参与开发的人，只给任务目标，不给操作步骤，记录卡点、误解和完成时间。

#### P1：发布能力仍不能对外按“正式版已完成”宣传

必须补齐：

- UI 冻结后同一最终候选从零完成 24 小时长稳；
- Windows 生产 Authenticode 与正式 Android keystore；
- 无开发工具的干净 Windows 客户机安装、升级、修复、卸载；
- Android 真机断开数据线并关闭 IDE、后端后的独立运行；
- Windows Player 交互进程中的窗口激活复核；
- 当前设备可完成的最终离线和权限矩阵。

#### P2：扩展“能做什么”的示例仍不够产品化

技术文档能解释 Manifest 和 lock，但普通扩展作者更需要按目的组织的模板：纯计算函数、视觉算法、HTTP 协议适配、Android Kotlin/JVM 四种模板。每个模板都应说明可发布平台、权限、测试和失败语义。

#### P2：窄屏抽屉带来合理但真实的额外一步

检查器打开后会遮挡中央列表，用户要先关闭检查器才能选择另一条语句。这是窄屏下正确的空间取舍，不是缺陷；但可以通过“上一条/下一条语句”快捷键或检查器标题栏导航减少往返。

#### P2：完整发布状态应集中呈现

函数、扩展、Player、Android、更新与签名各有检查结果。发布前最好有一个唯一的“发布就绪”总入口，把阻塞项按“需要修改项目 / 需要当前电脑权限 / 需要外部生产环境”分类，避免作者在多个工作区寻找红点。

## 8. 发布阻塞与延期事项

### 当前发布阻塞

- 24 小时最终候选长稳尚未重新完成；
- 生产签名和干净客户机矩阵缺失；
- Android 最终断线独立运行与发布签名尚未闭环；
- 一部分 Windows/ADB/Android 真实宿主细项仍是 `Partial`，例如窗口前台、SAF Provider、部分控件类型和故障矩阵。

### 已明确延期，不应反复开发替代品

- 非小米 Android 实体设备矩阵；
- 两台独立物理宿主的完整 LAN 防火墙/休眠/分区矩阵；
- 官方托管账号、域名、对象存储/CDN、配额与运营服务。

这些项目必须保持“延期/未验证”，既不能冒充通过，也不应在当前 UI 阶段用模拟功能占位。

## 9. 优先级建议

### 第一优先：把正式候选证据封口

目标：证明当前实现可在真实终端长期、独立、离线运行。完成后才可以把“专业级实现”升级为“专业级正式交付”。

### 第二优先：做一个真正面向扩展作者的黄金路径

目标：一名熟悉 Python 的开发者可以在 30 分钟内创建最小扩展、通过契约测试、启用、插入脚本并发布到独立 Windows Player；错误时知道改哪个文件、下一步做什么。

### 第三优先：做真实新用户可用性测试

目标：验证函数搜索、中央快速插入、`@`、`.`、`Ctrl+Space`、图像/OCR 测试、结果条件和 Player 发布是否真的无需口头教学。

### 第四优先：只根据真实任务数据继续精修

当前不建议再进行无目标的全面 UI 重写。表单、导航、中央语义和插入方式已经建立统一规范；后续只处理真实旅程中反复出现的卡点。

## 12. 最终判断

功能方面，本轮没有发现需要立刻补一个“基础官方函数”才能完成常见自动化的空洞。现有 78 个官方函数、结构化控制、97 个纯值操作、项目函数和扩展函数已经组成了一个足够完整的语言与运行平台。

真正需要补足的不是继续堆函数，而是：

1. 用同一最终候选补齐真实发布证据；
2. 用一个正式扩展示例证明开发者首次成功路径；
3. 用真实新用户验证“找得到、看得懂、出错能恢复”；
4. 保持当前统一 UI 规范，避免重新出现逐页面、逐函数打补丁。

完成这四项后，EasyCode 才能从“能力很强、实现接近完整”稳妥地进入“用户敢长期依赖、作者敢交付给别人”的阶段。
