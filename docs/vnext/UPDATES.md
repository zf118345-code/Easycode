# 在线更新与发布分发

状态：`Approved`（首版更新域、托管协议、可选/强制策略、终端控制权、灰度发布与作者控制测试通道已冻结）

最近修订：2026-08-31

## 1. 产品边界

在线更新是可关闭、可失败且不属于任务运行前置的维护能力。大型脚本作者可以向已交付的 Windows 与 Android Player 发布新版本；不需要更新的项目可以完全关闭，关闭后不配置更新端点、不启动更新调度器、不产生更新 DNS/TCP/HTTP，也不显示更新入口或徽标。

发布报告必须分开显示：

```text
任务运行网络：可完全离线 / 需要本机或局域网 / 需要公网
在线维护服务：更新已关闭 / 已启用 IDE 更新 / 已启用 Player 应用更新 / 已启用项目内容更新
```

更新服务器不可达只意味着“尚未检查”或“检查失败”。当前已经安装、签名有效且兼容的版本仍可打开；运行和主动暂停的任务继续。没有已生效的最后可信强制策略时仍可新开本地任务；已经缓存且超过宽限期的可信策略不能因服务器不可达而解除最低版本限制。

## 2. 三个更新域

1. **EasyCode IDE 更新**：更新开发端本身，由 EasyCode 官方信任根验证，在全局设置与“检查更新”中管理，不属于项目配置。
2. **Player 应用更新**：更新 Windows Player 外壳、Runtime、原生驱动、权限、ABI 或原生扩展。作者把经过验证的新 Runtime 与项目作为完整 Player 应用版本发布；EasyCode 不绕过作者单独向第三方 Player 静默替换 Runtime。
3. **项目内容更新**：更新签名 ECIR、资源、Player Schema、项目数据和兼容配置，不改变宿主、权限、ABI 或原生执行代码。它是大型脚本日常快速发布的首选路径。

每个更新产品拥有稳定 `product_id` 和固定信任根；每次不可变发布拥有 `release_id`、单调递增 `release_sequence`、展示版本、通道、产物类型、目标平台/架构、Runtime/ECIR 兼容范围、文件大小、内容哈希和签名。展示版本不参与机器排序，已经发布的同一 `release_id` 和文件不能原地覆盖。

## 3. 作者发布与配置

项目内容更新和 Player 应用更新分别配置，项目初始均关闭。第一次启用时，作者选择更新服务、通道和策略；关闭全部更新后，发布闭包不携带端点、上传令牌或更新调度配置。

作者发布流程固定为：

1. 比较上一发布，判断可以使用项目内容更新，还是必须生成 Windows Bundle/Android APK 应用更新。
2. 填写展示版本和简短更新说明，选择测试或稳定通道。
3. Publisher 检查 ECIR、Player Schema、运行方案迁移、Runtime、平台、资源、扩展、权限、ABI 和网络维护声明。
4. 在作者受控环境完成签名；发布服务器不取得发布私钥。
5. 上传不可变产物与签名元数据，服务端验证身份、大小、哈希、版本和签名。
6. 先在测试通道验收，再把同一不可变发布推广到稳定通道白名单、百分比灰度和全量；作者可以暂停、按原范围继续或扩大范围，坏版本通过更高序号修复版本替换。

发布器不得把普通扩展更新误判为内容更新：新增或变更 Python/Kotlin/C++、原生库、Android Manifest/权限、ABI、Runtime 或宿主能力时必须走应用更新。Android 内容更新只包含平台允许在应用私有目录切换的数据型发布内容。

## 4. 客户端生命周期

更新状态统一为：`disabled / idle / checking / available / downloading / staged / waiting_safe_point / awaiting_platform_install / applying / verifying / complete / failed / rolled_back`。

- 检查与下载使用低优先级、随机错峰、缓存验证和指数退避，不在每个任务开始时请求服务器。
- 下载进入独立暂存区，支持取消、断点续传、大小上限和完整包复验；半包永远不可被 Loader 发现。
- 运行或暂停中的任务固定使用启动时的不可变 `release_id`。可以检查和暂存，但任务结束或停止且没有未提交表单草稿前不能替换 ECIR、资源、Schema、Runtime 或应用文件。
- Windows 与项目内容更新使用可恢复的 A/B 槽或等价原子切换，至少保留一个上一正常版本。新版本无法启动、无法通过 Bundle Loader 或启动健康检查时恢复上一槽。
- 普通游戏流程失败、识图未命中或项目函数报错不属于更新健康失败，不能触发平台自动回滚。
- 多个 Player 进程共享同一安装目录时只下载一次；所有占用相关版本的进程退出或进入允许切换的空闲状态后才应用。
- 运行方案、资源覆盖与用户数据不写入更新包。兼容 `control_id` 继续保留；新增必填字段、删除字段或类型不兼容时把方案标记为“需要检查”，不能清空数据或静默用默认值自动运行。

## 5. 安全与信任链

更新协议采用 TUF 风格的角色化签名元数据、离线信任根、在线发布密钥、元数据版本/过期、大小/哈希校验、密钥轮换/吊销与防回滚，不自创只依赖 HTTPS 或单个长期在线密钥的简化协议。具体实现优先采用经过审计的标准库；协议兼容性与密钥生命周期进入 Harness。[TUF 的安全模型](https://theupdateframework.io/docs/security/)明确覆盖任意文件、回滚、冻结、混搭、无限数据与密钥泄露等更新攻击。

- IDE 内置 EasyCode 官方更新信任根；每个 Player 固定该项目发布者的 `product_id` 与更新信任根。
- TLS 保护传输，签名、大小和哈希验证产物真实性与完整性；任一失败都保留当前版本。
- 服务器只保存不可变发布物、签名元数据、通道指针和审计，不保存作者发布私钥。
- 已见过的更高序号不能被普通旧清单降级。恢复旧业务内容通过发布更高序号的修复版完成，不能静默降低版本。
- 更新请求不上传 ProgramDocument、运行方案值、变量、日志、截图或稳定硬件身份。每个更新产品在本机生成独立高熵随机分组码，正常升级后保留；灰度资格在客户端本地计算，Feed 白名单只保存产品域哈希。用户可以显式重置分组码，但界面必须说明会退出现有白名单并改变后续灰度分组。
- 更新发布身份只证明产物来源，不等同于收费授权、设备许可或商业激活。

## 6. 官方托管与开放协议

首版同时提供两种更新源，并使用同一签名 Feed、发布对象和客户端验证语义：

1. **EasyCode 官方托管**：普通作者登录作者账号，在 IDE 中直接上传、发布和查看真实状态。EasyCode 负责上传 API、项目归属、不可变产物存储、CDN、签名元数据分发、通道指针、配额、使用量、审计、监控、备份和故障恢复。
2. **作者自建兼容源**：高级作者把同一不可变发布物和签名 Feed 上传到自己的 HTTPS 对象存储/CDN。静态 Feed 即可承接普通公开更新，不强迫作者开发一套常驻业务服务器；EasyCode 提供连接测试、上传适配与诊断。

官方托管是默认主路径，自建入口放在高级设置，但二者不是两套更新协议。Player 只信任安装时固定的 `product_id`、信任根和经过签名的源配置；不能因 URL 可编辑而绕过来源验证。更新源迁移、增加镜像或切换托管方必须由现有可信根签名，或作为经过验证的 Player 应用更新交付。

官方服务的作者登录和上传身份只用于发布管理，不等同于终端脚本激活或商业授权。Player 获取公开更新无需登录作者账号。官方服务必须具备基础配额和使用量计量以保护平台；VIP、计费、私有分发、团队席位、加速线路和更高额度属于后续商业规格，没有闭环前不显示收费入口。配额不足只能明确阻止新的上传/发布，不得让已安装版本停止运行或把现有发布悄悄改写成其他内容。

官方托管不接收终端运行心跳、任务结果、崩溃、截图、日志或设备列表，也不提供云端在线设备面板。作者发布页只能显示发布配置、签名策略、不可变产物、CDN 请求量/流量和作者显式操作产生的审计；这些数据不能伪装为安装数、在线数或业务成功率。

发布私钥始终留在作者受控环境；官方或自建服务器只验证并分发签名结果。上传凭据保存在 IDE 的本机安全凭据存储，不进入项目、`.ecplayer`、Player、导出 Feed 或版本控制。

## 7. Windows 与 Android 差异

Windows 项目内容与应用更新都可以由更新助手暂存并在安全边界原子切换；需要替换正在使用的 Runtime 或原生文件时，当前 Player 只生成受本机约束的交接记录。独立 `EasycodeUpdateHelper.exe` 先验证严格文件清单并解包到安装目录同卷的暂存槽，当前 Player 退出后整目录替换。新 Player 必须成功启动本地 API 并写入一次性健康探针，助手才生成与发布编号、序号和产物哈希绑定的最终回执；无法启动或超时则隔离失败目录并恢复上一目录。安装根、重启命令和父进程身份来自本机宿主，签名 Feed 不能指定本地任意路径或程序。

Android 项目内容更新写入应用私有 A/B 槽，签名验证后在空闲边界切换，不触发 APK 安装。Runtime、Manifest、权限、ABI 或原生扩展变化必须生成保持相同应用标识和兼容签名证书的新 APK，并交给 Android 系统安装流程；普通应用不得承诺无提示静默安装。系统可能返回需要用户操作的状态，用户取消或安装失败时旧 APK 与本地数据继续可用。[Android PackageInstaller](https://developer.android.com/reference/android/content/pm/PackageInstaller)明确区分需要用户操作、成功和各类失败；Android 系统还要求应用在生命周期内维持可用于升级的签名身份，详见[应用签名规则](https://developer.android.com/studio/publish/app-signing)。

Android APK 的恢复使用更高 `versionCode` 的修复版本，不承诺任意自动降级。当前首版不以 Google Play/AAB 为硬门，因此不能把 Play 专属应用内更新当作自建 APK 分发的唯一实现。

## 8. 可选更新与强制更新

作者可以逐次发布两种策略：

- **可选更新**：终端可以延后，当前有效版本可以无限期继续开始新任务。
- **强制更新**：使用签名策略声明最低允许发布序号、生效时间、宽限截止时间、原因和各平台目标版本。宽限期结束后，低于最低序号的 Player 仍可打开、查看状态/日志、导出诊断和修改方案，但不能开始新的任务，直到安装兼容更新。

强制更新绝不打断已经运行或主动暂停的任务。暂停属于同一运行现场，可以继续；任务完成、失败、停止、取消、Player 退出或崩溃后现场结束，下一次开始受当前最低版本策略约束。作者不能借强制更新实现远程停止正在执行的脚本。

客户端只能执行已经验证的签名强制策略。尚未取得新策略的离线客户端无法得知服务器的新要求，继续按最后可信策略运行；一旦客户端取得并缓存了签名策略，宽限期结束后即使断网也遵守。缓存策略、最后可信服务器时间和版本单调性不得因系统时钟回拨、清理普通缓存或更新源暂时不可达而静默失效。

发布强制策略前，服务端必须确认每个被覆盖的平台/架构都有签名有效、兼容且可取得的目标产物；缺少 Android APK、签名证书不兼容、Runtime/ECIR 范围错误或产物仍在处理中时阻止发布。可下载但验证/安装失败时，Player 显示具体安全或平台错误；宽限期后仍不允许运行旧任务，但应用外壳与本地数据保持可用。

启用强制更新会改变维护可用性承诺。作者发布页和发布报告必须明确显示“任务本身可离线，但已缓存的强制更新策略可能阻止旧版本开始新任务”，不能继续使用无条件“永久免费离线运行”的表述。

## 9. 终端用户控制权

更新控制分为三层，不能用一个含义模糊的总开关代替：

1. **作者打包开关**：作者没有启用 Player 应用更新和项目内容更新时，发布包不携带更新端点、调度器、入口或徽标，也不产生任何更新网络请求。
2. **终端普通更新开关**：作者启用更新后，终端用户可以对每个已启用更新域分别关闭普通可选更新的自动检查、自动下载和自动应用。手动“检查更新”始终保留；它只执行一次完整元数据检查并展示结果，不静默重开自动下载或自动应用。这些偏好按 `product_id` 持久保存，应用或内容更新后继续保留，作者不能通过普通发布重置。
3. **已验证强制策略**：Player 一旦通过自动或手动检查取得并验证签名强制策略，该策略成为最后可信状态。终端用户可以在宽限期内决定何时下载和安装，但不能用设置、断网、普通缓存清理或系统时钟回拨删除最低版本约束；宽限结束后的限制继续遵守第 8 节，且不强制终止当前任务或绕过平台安装确认。

三个普通更新开关具有独立效果：关闭普通自动检查后不再调度可选版本检查；关闭自动下载后只展示版本与说明，不取得产物；关闭自动应用后允许下载和验证到暂存区，但只在用户确认且达到安全边界时切换。Android APK 无论开关如何都遵守系统安装确认，不能承诺静默安装。

只要作者打包时启用了强制策略能力，Player 就运行独立、低频、随机错峰的 Update Policy Checker。它只取得签名最低版本策略，不下载产物、不安装版本，也不因普通更新偏好关闭；设置文案必须使用“自动检查普通更新”，并明确披露强制策略检查仍存在。服务器发布新策略并不等于离线终端已经知道它：长期离线 Player 只能遵守最后可信策略，恢复网络并取得策略后不能再回退到未知状态。

## 10. 测试与灰度发布

测试通道由项目作者控制。普通稳定 Player 不显示通道选择器，终端用户不能自行切换、搜索或加入测试通道；用户只能在本机复制匿名测试分组码并主动交给作者，作者把该产品域哈希加入测试白名单后，签名策略才会向该安装提供测试版本。测试更新仍属于可选更新并遵守终端的自动检查、下载和应用偏好。

作者从测试白名单移除安装后，客户端不再取得新的测试发布，但已经安装的测试版本不被远程降级。回到稳定线必须由兼容、序号更高且签名有效的稳定发布完成。作者将测试发布推广为稳定时复用同一不可变产物；稳定白名单、百分比和全量范围使用新的签名 `RolloutPolicy`，不要求客户端改变通道设置。

首版稳定通道使用“白名单 → 确定性百分比 → 全量”三阶段渐进发布。灰度策略是独立于不可变发布物的签名 `RolloutPolicy`，至少包含 `product_id`、`release_id`、通道、单调 `policy_revision`、`rollout_id`、比例基点 `percent_bps`、白名单哈希、暂停状态和签发时间。改变范围只发布更高策略 revision，不重新构建产物或改变 `release_id`、文件哈希与签名。

Player 首次为某个 `product_id` 启用更新时生成项目域隔离的随机安装分组码。它不来自硬件序列号、Android ID、账号、IP、路径或设备名；同一产品正常应用/内容升级和重启后保持稳定，不同产品不能用同一编号关联终端。卸载并清除数据或用户明确重置后生成新编号。多个进程共享同一产品安装时共享编号；作者打包关闭更新时不生成编号。

客户端使用固定算法在本机计算：

```text
bucket = SHA-256(product_id + rollout_id + 安装分组码) mod 10000
命中 = bucket < percent_bps
```

同一发布和安装的结果必须跨重启与平台实现稳定。比例只能扩大，原命中集合始终是新集合的子集；白名单哈希在未暂停时优先于百分比，因此 `0%` 也可以只向指定安装提供更新。原始分组码不进入 Feed 或请求，作者端只保存产品域哈希和可选的本地备注。

作者可以执行以下显式动作：暂停、按原 `rollout_id`/范围继续、扩大比例、推广到 `100%` 和维护白名单。暂停后，已经取得新暂停策略但尚未应用的客户端停止应用并清理对应暂存包；已经激活的版本不远程降级。尚未取得暂停策略的离线客户端可能继续遵守旧可信策略，因此暂停不是即时远程召回。继续必须恢复原分桶与比例；全量只把阈值提升到 `10000`，不重新打包。每次动作写入带作者、时间、旧值、新值和策略 revision 的审计历史。

白名单和百分比只适用于可选更新。强制最低版本策略必须覆盖全部兼容目标，不能绑定白名单或百分比；作者应先把同一不可变产物完成测试与可选灰度、推广到稳定 `100%`，再单独发布强制策略。首版不上传终端日志、崩溃、截图、任务结果或设备状态，也不根据这些数据自动扩大、暂停或回滚。客户端启动/加载健康失败后的本地上一槽恢复继续保留，它不是服务器遥测自动回滚。

官方托管和作者自建静态 Feed 使用相同签名 `RolloutPolicy`、分桶算法和客户端判断。发布页只能显示作者真实设定的通道、比例、白名单数量、策略状态和 CDN 请求/流量；没有遥测时不得显示安装数、安装成功率、崩溃率或业务成功率。

## 11. 稳定需求

- `[REQ-UPD-001]` IDE、Player 应用和项目内容拥有独立版本、通道、检查、下载、应用和失败状态。
- `[REQ-UPD-002]` 项目作者可以分别关闭 Player 应用更新和项目内容更新；全部关闭时发布包没有更新端点、调度器、网络请求和用户入口。
- `[REQ-UPD-003]` 更新属于在线维护能力，不改变任务运行网络等级；服务不可达不得中断当前运行/暂停现场。没有已生效的最后可信强制策略时不得阻止当前有效版本新开任务；已缓存且超过宽限期的最低版本约束不能因服务不可达而解除。
- `[REQ-UPD-004]` 项目内容更新不得引入 Runtime、原生代码、权限、ABI 或宿主变化；超出边界时 Publisher 必须生成应用更新或阻止发布。
- `[REQ-UPD-005]` 每次任务固定一个 `release_id`；运行和暂停期间只能检查/暂存，不能切换版本。
- `[REQ-UPD-006]` 发布物不可变并使用单调发布序号、平台/架构/Runtime/ECIR 兼容范围、大小、哈希和签名元数据。
- `[REQ-UPD-007]` 客户端使用固定信任根与安全更新元数据验证来源、新鲜度、完整仓库视图、目标匹配、大小、哈希和签名，不能只依赖 TLS。
- `[REQ-UPD-008]` 下载支持断点续传、取消、磁盘预算和最终全包验证；中断与半包不能污染活动版本。
- `[REQ-UPD-009]` Windows 和项目内容更新使用可恢复原子切换并保留上一正常版本；只有启动/加载健康失败触发自动恢复。
- `[REQ-UPD-010]` 运行方案与用户数据独立于版本；稳定兼容字段保留，不兼容方案在下次运行前要求检查。
- `[REQ-UPD-011]` 内容要求更高 Runtime 时不得强行加载；客户端明确提示需要先完成应用更新。
- `[REQ-UPD-012]` 多实例共享下载与更新协调，不能并发替换正在使用的目录或版本。
- `[REQ-UPD-013]` 检查使用随机错峰、缓存验证和退避；更新故障显示真实状态，不伪报“已是最新”。
- `[REQ-UPD-014]` 发布服务器不保存发布私钥，更新请求不携带项目源码、运行数据、日志、截图或稳定硬件身份。
- `[REQ-UPD-015]` Android 内容更新与 APK 应用更新使用不同生命周期；APK 安装遵守系统确认、应用标识、签名、版本和权限约束。
- `[REQ-UPD-016]` 更新签名与商业授权相互独立，不因启用更新引入收费激活或设备许可。
- `[REQ-UPD-017]` EasyCode 官方托管与作者自建使用同一开放签名 Feed、不可变发布格式和客户端验证状态机，不能形成互不兼容的两套发布模型。
- `[REQ-UPD-018]` 官方托管提供作者身份、项目归属、上传、不可变存储/CDN、通道、配额/使用量、审计、监控、备份与故障恢复；作者账号不可成为终端 Player 运行或公开更新下载前置。
- `[REQ-UPD-019]` 自建源至少支持标准 HTTPS 静态 Feed 与对象存储/CDN；IDE 提供连接、权限、上传和发布验证，不要求普通协议实现依赖专有 EasyCode 云 API。
- `[REQ-UPD-020]` 更新源、镜像和托管方迁移必须由现有信任根签名或通过可信应用更新完成；手工改 URL 不能改变 Player 信任边界。
- `[REQ-UPD-021]` 发布私钥不上传；上传凭据只进入 IDE 本机安全存储，不进入项目、发布包、Player、Feed 或版本控制。
- `[REQ-UPD-022]` 首版托管配额耗尽只阻止新上传/发布并说明恢复方式；不得终止现有 Player、改写不可变发布或伪装成商业授权失败。
- `[REQ-UPD-023]` 每个发布策略明确区分可选与强制；强制策略包含签名的最低允许序号、生效时间、宽限截止时间、原因和平台目标。
- `[REQ-UPD-024]` 强制更新只约束新任务；运行和主动暂停任务继续使用固定 `release_id` 到终态，任何远程策略不得中断或改写现场。
- `[REQ-UPD-025]` 强制策略发布前验证所有覆盖平台/架构存在签名有效、兼容且可取得的目标产物；任一缺失或处理中状态阻止发布。
- `[REQ-UPD-026]` 客户端只执行经过固定信任根验证的最后可信强制策略；未取得新策略时不猜测，取得后不能通过断网、普通缓存清理或系统时钟回拨绕过。
- `[REQ-UPD-027]` 宽限期结束且当前版本低于最低序号时，只阻止新任务；Player 仍允许更新、查看状态/日志、导出诊断和维护运行方案。
- `[REQ-UPD-028]` 发布报告明确区分任务执行离线能力与强制更新维护约束；作者启用强制策略前必须看到终端断网和服务器故障的真实影响。
- `[REQ-UPD-029]` 作者启用更新后，终端用户可以按已启用更新域分别控制普通可选更新的自动检查、自动下载和自动应用；`UpdatePreferences` 按产品跨版本保留，作者普通发布不能重置；手动检查始终存在且不改写这些偏好。
- `[REQ-UPD-030]` 终端关闭普通自动检查后不得调度可选版本检查。作者启用强制策略能力时，独立 Policy Checker 仍以公开说明的低频错峰方式取得签名最低版本策略，但不得下载产物、触发安装或改变普通更新偏好。
- `[REQ-UPD-031]` 关闭自动下载时只取得并展示签名元数据；关闭自动应用时产物只能进入已验证暂存区，必须由用户确认并在安全边界切换。Android APK 始终遵守系统安装确认。
- `[REQ-UPD-032]` 已验证强制策略不受终端自动化开关影响；宽限期内用户可以择时下载/安装，宽限结束后最低版本约束不能通过设置、断网、普通缓存清理或时钟回拨绕过。
- `[REQ-UPD-033]` 尚未取得新强制策略的离线客户端继续遵守最后可信状态；作者发布页、终端设置与发布报告必须明确“长期离线会延迟获知新策略”，不得承诺即时覆盖离线终端；恢复网络后 Policy Checker 取得并验证最新策略。
- `[REQ-UPD-034]` 灰度范围由独立于不可变发布物的签名 `RolloutPolicy` 描述；每次变更增加单调策略 revision，旧策略重放被拒绝，产物与 `release_id` 不得因推广重建或改写。
- `[REQ-UPD-035]` 每个启用更新的产品安装生成高熵随机、产品域隔离的安装分组码；它跨正常升级保留且不来源于硬件、账号、IP、路径或设备名。作者关闭更新时不生成该身份。
- `[REQ-UPD-036]` 百分比资格使用固定 `product_id + rollout_id + 安装分组码` 在客户端确定性分桶；扩大比例只能增加命中集合，不能重新洗牌。
- `[REQ-UPD-037]` 白名单在未暂停时优先于百分比；原始分组码不进入 Feed 或更新请求，发布策略只携带产品域哈希。用户重置分组码前必须看到白名单与灰度影响。
- `[REQ-UPD-038]` 作者只能暂停、按原范围继续、扩大比例或全量推广，不能降低比例伪装回滚；所有范围与白名单变化生成签名 revision 和审计记录。
- `[REQ-UPD-039]` 客户端取得暂停策略后停止取得或应用对应可选版本并清理未应用暂存包；已激活版本不自动降级，未取得新策略的离线客户端继续遵守旧可信策略。
- `[REQ-UPD-040]` 白名单与百分比只适用于可选更新；强制最低版本策略只能在目标发布对稳定通道 `100%` 可取得后启用，并覆盖全部兼容目标。
- `[REQ-UPD-041]` 服务端不依据运行日志、崩溃、截图、任务结果或设备状态自动扩大、暂停或回滚；客户端启动/加载健康失败只触发本机上一槽恢复。
- `[REQ-UPD-042]` 官方托管与自建静态 Feed 使用相同签名灰度策略、本地分桶算法和状态语义，不依赖专有动态定向 API。
- `[REQ-UPD-043]` 没有终端遥测时，作者端不得展示安装数量、安装成功率、崩溃率或业务成功率；CDN 数据只能标记为请求量与流量。
- `[REQ-UPD-044]` 测试通道必须由作者通过产品域测试分组码白名单控制；普通稳定 Player 不得显示自助通道切换或加入入口，测试更新继续遵守可选更新偏好。
- `[REQ-UPD-045]` 移除测试白名单不得远程降级已安装版本；客户端只能通过序号更高、签名有效且兼容的稳定发布回到稳定线。
- `[REQ-UPD-046]` 官方托管不得接收终端心跳、在线设备列表、运行日志、截图、崩溃或任务结果，也不得提供云端在线设备面板。

## 12. Harness 验收

- `[AC-UPD-DISABLED-001]` Windows/Android 发布关闭全部更新后没有更新 DNS/TCP/HTTP、端点、调度器或徽标，飞行模式/断网仍完成任务。
- `[AC-UPD-OFFLINE-001]` 更新源不可达、DNS/TLS/超时/5xx 时状态准确，当前版本仍能打开且运行/暂停现场继续；没有已生效最低版本约束时可以新开任务，已有且超过宽限期的可信策略继续限制新任务；只有成功验证元数据后才能显示“已是最新”。
- `[AC-UPD-SIGN-001]` 篡改产物、错误签名、旧清单重放、版本回退、错误平台和混搭发布全部被拒绝且不损坏活动版本。
- `[AC-UPD-ATOMIC-001]` 下载中断、磁盘不足、进程退出和切换中断不产生可加载半版本；当前或上一完整版本可以启动。
- `[AC-UPD-RUN-001]` 运行与暂停期间只暂存，当前任务始终执行固定 `release_id`，任务结束前不切换任何内容。
- `[AC-UPD-ROLLBACK-001]` 新版本启动/加载健康失败自动恢复上一正常版本；普通业务执行失败不会触发平台回滚。
- `[AC-UPD-PROFILE-001]` 兼容字段保留，不兼容运行方案被标记并要求检查，更新失败不清空方案、资源覆盖或用户数据。
- `[AC-UPD-MULTI-001]` 多实例只下载一次并等待所有相关进程安全释放；并发检查、下载和退出不混合版本。
- `[AC-UPD-WIN-001]` Windows 内容与应用更新分别通过真实 Bundle、安装助手、重启和 A/B 恢复验证。
- `[AC-UPD-AND-CONTENT-001]` Android 真机内容更新无需 APK 安装，在应用私有槽验证并安全切换；失败后旧内容继续运行。
- `[AC-UPD-AND-APK-001]` Android 真机 APK 更新覆盖用户确认、取消、签名不一致、版本/ABI/权限不兼容、空间不足与安装成功后的数据保留。
- `[AC-UPD-SCALE-001]` 大量客户端启动使用错峰、缓存、断点续传和退避，不形成整点惊群；请求内容审计不包含禁止数据。
- `[AC-UPD-HOSTED-001]` 作者通过官方托管完成身份验证、上传、测试通道、稳定推广、暂停分发、审计和真实客户端下载；服务故障不影响已安装版本运行。
- `[AC-UPD-SELFHOST-001]` 同一签名发布可部署到标准 HTTPS 静态对象存储/CDN，Windows 与 Android 客户端使用与官方托管相同的验证和状态语义。
- `[AC-UPD-PORTABLE-001]` 经过现有信任根签名的源迁移/镜像变更成功；篡改 URL、未签名迁移和错误信任根被拒绝。
- `[AC-UPD-CREDENTIAL-001]` 发布私钥与上传凭据扫描不会在项目、Git、构建产物、Player、Feed、日志或诊断中出现；服务端无法替作者签署发布。
- `[AC-UPD-QUOTA-001]` 托管配额耗尽准确阻止新上传/发布，现有不可变发布和已安装版本保持可用，不出现终端授权提示。
- `[AC-UPD-REQUIRED-001]` 可选版本可以延后；签名强制策略在宽限结束后只阻止低版本开始新任务，并显示原因、目标版本和恢复动作。
- `[AC-UPD-ACTIVE-001]` 强制策略在运行或暂停期间到达、生效或超过宽限均不打断现场；同一任务继续，结束后的下一次开始受策略约束。
- `[AC-UPD-POLICY-001]` 篡改、错误签名、旧策略重放、系统时钟回拨和普通缓存清理不能伪造或绕过最后可信最低版本策略。
- `[AC-UPD-PLATFORM-001]` 任一覆盖平台缺少可取得兼容产物、Android 签名/版本不合法或上传未完成时，服务端拒绝发布强制策略。
- `[AC-UPD-LOCKED-001]` 强制更新因断网、下载、验证或安装失败而未完成时，旧任务不再新开，但 Player 外壳、日志、诊断、方案数据和更新恢复入口保持可用。
- `[AC-UPD-CONTROL-001]` 三个普通更新偏好独立生效、跨应用/内容版本保留且不能被作者发布重置；手动检查成功且不会重新开启其他开关。
- `[AC-UPD-POLICY-CHECK-001]` 普通自动检查关闭后不再请求可选版本；启用强制策略能力的 Player 仍只请求签名最低版本策略，不下载或安装产物，界面与网络报告准确披露该请求。
- `[AC-UPD-GRACE-001]` 已取得强制策略后，终端可在宽限期内延后、下载或主动安装；超过宽限仍未更新时只阻止新任务，不触发静默安装或中断现场。
- `[AC-UPD-CONTROL-POLICY-001]` 已验证强制策略不能通过关闭自动化、断网、普通缓存清理或时钟回拨消失；未取得该策略的隔离客户端继续使用最后可信状态，并在下一次检查后正确收束。
- `[AC-UPD-AUTHOR-OFF-001]` 作者打包时关闭全部更新后，终端不存在更新设置、手动入口、徽标、端点或后台请求；重新启用必须通过作者重新发布的包完成。
- `[AC-UPD-ROLLOUT-ID-001]` 同一产品安装生成随机产品域分组码，重启和正常升级后保留，不同产品不同，显式重置后改变；扫描证明不含硬件、账号、IP 或 Android ID。
- `[AC-UPD-ROLLOUT-PRIVACY-001]` 官方与自建请求不发送原始分组码、日志、截图、运行数据或硬件身份，签名 Feed 白名单只含产品域哈希。
- `[AC-UPD-ROLLOUT-BUCKET-001]` 固定输入在 Windows 与 Android、跨进程和重启得到同一分桶；不同实现使用同一规范化字节和哈希算法。
- `[AC-UPD-ROLLOUT-MONOTONIC-001]` 比例从 `5% → 10% → 25% → 100%` 时，上一阶段命中集合始终是下一阶段子集，发布物哈希不变。
- `[AC-UPD-ROLLOUT-WHITELIST-001]` `0%` 下只有白名单命中；非法、空和重复分组码被拒绝，移除白名单不回退已安装版本。
- `[AC-UPD-ROLLOUT-PAUSE-001]` 暂停策略生效后新客户端不再取得版本，已暂存未应用版本停止应用，已激活版本保持不变；离线客户端恢复网络后取得新 revision 并收束。
- `[AC-UPD-ROLLOUT-RESUME-001]` 暂停后继续沿用同一 `rollout_id`、比例、白名单与原命中集合；扩大范围只提高阈值，全量后所有兼容安装可取得同一不可变发布物。
- `[AC-UPD-ROLLOUT-FORCE-001]` 百分比或白名单阶段启用最低版本强制策略被拒绝；稳定通道达到 `100%` 后才能发布覆盖全部兼容目标的强制策略。
- `[AC-UPD-ROLLOUT-NOTELEMETRY-001]` 网络审计证明没有自动上传崩溃、任务结果、日志或截图；服务端不生成伪安装成功率，也不触发自动全局暂停或回滚。
- `[AC-UPD-ROLLOUT-LOCAL-ROLLBACK-001]` 某个客户端启动/加载健康失败只恢复该客户端上一正常版本，不改变服务端灰度比例；业务函数失败不触发恢复。
- `[AC-UPD-ROLLOUT-AUDIT-001]` 开始、暂停、继续、扩大、全量与白名单变更均产生带作者、时间、旧值、新值和策略 revision 的审计记录，旧 revision 重放被拒绝。
- `[AC-UPD-ROLLOUT-STATIC-001]` 相同签名灰度策略部署到静态 HTTPS Feed 后，无动态定向 API 也能完成白名单、分桶、暂停、继续和全量。
- `[AC-UPD-ROLLOUT-UX-001]` 作者端不显示伪安装数或成功率；终端未命中时显示“当前暂无面向此安装的更新”，不伪报全局最新版。
- `[AC-UPD-TEST-CHANNEL-001]` 普通稳定 Player 没有通道选择器；只有作者把当前产品域分组码加入测试白名单后才取得测试发布，移除后不再取得新测试版本且当前安装不降级。
- `[AC-UPD-TEST-PROMOTE-001]` 同一不可变测试产物推广到稳定白名单、百分比和全量时，产物哈希与签名不变，客户端无需修改通道设置。
- `[AC-UPD-NODEVICE-CLOUD-001]` 托管服务抓包与存储审计证明没有终端心跳、设备在线列表、日志、截图、崩溃和任务结果；作者端不存在云端在线设备面板或伪在线数。

## 13. 实现参数
