## 1. 目标与边界

消息能力用于同一 EasyCode 项目的多个 IDE/Player 运行实例在同机或局域网内传递结构化数据。Windows、ADB 工作实例和 Android 本机 Player 使用同一消息契约；首版解决“一个实例向一个或多个明确实例发送同一份数据，并让发送方按需确认哪些接收脚本成功取得数据”的问题。

消息服务只负责数据传输。接收脚本通过等待函数取得内容，或监听器条件成立后由当前运行会话原子接手消息，消息即为已读取；接收方随后是否进入房间、点击成功或完成任务，由普通脚本观察、反馈和重试。消息不是项目变量、共享内存、文件引用、业务任务状态或可恢复执行现场。

真实文件交换使用`文件.*`。普通消息不向脚本暴露`租约.*`、领取时限、手动确认或手动网络重发。

## 2. 实例与路由

- 每个运行端点拥有稳定随机 `host_id + instance_id`，运行方案提供项目内唯一的实例显示名。新建方案默认使用`实例1`等顺序名称，用户可以重命名；重命名只修改显示属性，已经保存的 `instance_ref`、未读消息和监听过滤仍指向原稳定 ID。同一项目发现显示名重名时阻止提交并要求改名，不静默增加随机后缀。
- IDE 单实例调试默认使用`IDE调试-1`；多实例测试可以为每个调试实例修改名称，并执行与 Player 相同的唯一性检查。
- 实例显示名只帮助用户识别 EasyCode 运行端点，不识别或绑定游戏账号，也不作为网络认证身份。
- 实例名与操作目标相互独立。一个实例可以不绑定操作目标以运行纯逻辑脚本；允许绑定多少操作目标由`TARGETS.md`冻结，消息地址不随窗口标题、ADB 序列号或目标切换而改变。
- 消息自动包含稳定项目命名空间。默认不得向其他项目的同名实例投递。
- 脚本制作者只选择一个明确实例或明确实例列表、消息名称和内容，不填写本机数据库、协调器地址或访问令牌。多个收件人不是逗号拼接文本；ProgramDocument 参数保存包含稳定 ID 的 `list<instance_ref>` 类型化值，检查器允许逐项选择或粘贴逗号分隔显示名后在提交时解析为稳定引用。
- 多收件人发送在提交时固定收件人快照。运行时为每个实例生成独立消息 ID、队列副本和状态；一个实例读取、取消或过期不得改变其他实例的副本。
- 同一操作系统用户、同机、同一签名产品信任域的 Player 实例通过当前用户本机目录自动信任普通消息；项目命名空间相同但发布签名域不同的实例不会因此互信。跨设备实例必须使用一次性短期码或二维码完成 LAN 配对，并显式授予普通消息权限。配对、双向认证、撤销和诊断契约见 [`NETWORK.md`](NETWORK.md)。
- 已经配对且已授权的实例由局域网协调器传递。首版普通消息不依赖 EasyCode 云或公网中继，传输方式改变不得要求修改脚本。
- 目标稳定引用从未登记、未配对、已撤销、项目命名空间不符或没有消息权限时，发送立即失败且不创建队列。已登记且仍可信的实例暂时离线时，每个消息副本使用原消息 ID 保留到消息有效期；实例恢复后幂等投递，超过有效期后进入已过期。

## 3. 首版函数集合

| 函数 | 主要输入 | 返回值与结果 |
| --- | --- | --- |
| `消息.发送` | 接收实例（单个引用或引用列表）、名称、内容、有效期 | 原子保存发送批次与每个收件人的消息副本后返回发送批次；目标离线时对应副本进入等待读取或本地待发送状态 |
| `消息.等待接收` | 名称、可选来源实例、超时 | 收到并成功解码后返回接收消息记录，同时自动产生已读回执；超时返回空 |
| `消息.等待已读` | 发送批次、等待方式（全部/任一，默认全部）、超时 | 观察批次内收件消息；返回是否满足条件及已读、未读、过期和失败实例列表，等待超时不删除消息 |
| `消息.取消` | 发送批次、可选接收实例 | 取消指定范围内尚未读取的副本；返回已取消和未取消实例列表及各自状态 |

首版不提供`消息.完成`。`消息.等待接收`成功返回数据即代表传输完成。首版也不提供`消息.重发`；断线、离线发件箱和重复提交由消息服务自动使用原消息 ID 重试。业务需要再次通知时重新调用`消息.发送`，创建一条新消息。

`消息.等待接收`是消息服务的同步原子函数，用于流程运行到指定位置后等待并取得一个值；异步接收使用 ProgramDocument 的 `listen` 结构，把消息到达作为一种推送触发源。两者不得争抢同一消息副本：编译与发布检查要求同一消息名称及来源过滤条件只归属于一个消费入口，或者由开发者配置互斥的过滤条件。

### 3.1 消息监听器

监听器由固定 `kind: "listen"` 结构保存，而不是一段需要解析的文本。一次组队邀请监听至少包含：

| 字段 | 类型化值 |
| --- | --- |
| 触发源 | 消息到达 |
| 名称 | 文本 `组队邀请` |
| 来源实例 | 实例引用 `雷电-主号` |
| 接收绑定 | 局部符号 `邀请` |
| 可选条件 | 调用结果 `可以处理组队邀请` |
| 处理区块 | 调用项目函数 `处理组队邀请`，参数引用 `邀请` |

- 没有`当`条件表示在下一处安全检查点立即处理；存在`当`条件表示消息继续由消息服务保持未读，条件成立后再由当前运行会话接手。
- 条件成立后，运行时使用消息 ID 和监听器稳定 ID 原子接手队首消息，成功取得并解码内容后返回投递确认。发送方看到“已读取”只代表当前接收脚本已经取得数据，不代表监听函数已经完成业务。
- 未被任何运行会话接手的消息由消息服务保存到被读取、取消或过期。运行会话不把调用栈、页面状态或监听调度队列持久化为可续接现场。
- 同一监听器保持先进先出。调度器在安全检查点取得当前就绪队列的快照，依次执行快照中的事件；处理期间新到达的消息留到下一批，防止持续消息使主流程永久无法恢复。
- 监听器调用普通项目函数。函数正常结束后，运行时自动从被暂停主流程的下一条语句继续，不要求返回事件处理结果。页面恢复、业务重试、任务停止和错误捕获全部使用普通结构化控制语句与函数调用。
- 同一运行实例始终只有一个流程能够操作当前目标。监听器执行期间到达的其他监听消息继续排队，不发生嵌套或重入。
- Player 崩溃或被强制终止时，已经接手且尚未正常处理结束的消息不在下次启动时自动重新执行；从未接手的未读消息仍遵守原有效期。新的运行方案不会恢复旧方案的函数、页面或事件位置。若整个 Player 来不及写入终态，下次启动根据持续落盘日志中“已接手但无完成事件”的记录标记`处理中断`。

## 4. 结构化投影示例

下列文字只是 ProgramDocument 的纵向派生摘要，不是可编辑数据或固定文本格式。

向一个实例发送并等待已读：

```text
1  发送消息「房间码」给「雷电-小号2」· 内容 {房间码: "215"} · 有效期 3 分钟  → 房间码批次
2  等待「房间码批次」全部已读 · 超时 60 秒  → 已读结果
3  如果「已读结果.条件已满足」为否
4      输出警告「小号在 60 秒内没有取得房间码」
```

向多个明确实例发送时，“接收实例”参数使用类型化 `list<instance_ref>` 值，例如“雷电-小号1、雷电-小号2、雷电-小号3”。检查器使用可搜索多选 Control；用户也可以粘贴逗号分隔名称，由 Control 去除分隔空白并在提交前转换为列表。ProgramDocument 与 ECIR 都不得保存需要运行时再次拆分的逗号字符串。

```text
1  发送消息「房间码」给 3 个明确实例 · 内容 {房间码: "215"} · 有效期 3 分钟  → 房间码批次
2  等待「房间码批次」全部已读 · 超时 60 秒  → 已读结果
3  如果「已读结果.条件已满足」为否
4      读取「已读结果.未读实例」  → 未读实例
5      输出警告「仍有实例未读取房间码」
```

接收方同步等待并读取结构化内容：

```text
1  等待接收消息「房间码」· 来源「雷电-主号」· 超时 60 秒  → 房间通知
2  如果「房间通知」不为空
3      读取「房间通知.内容.房间码」  → 房间码
4      调用项目函数「进入房间」· 房间码「房间码」
```

接收方是否进入房间不改变原消息的已读状态。需要业务反馈时，接收方创建一条新的普通消息，例如向“雷电-主号”发送名称“进入房间结果”、内容 `{成功: true}` 的消息。

## 5. 消息记录与内容

`消息.发送`返回的发送批次是普通结构化结果，可以保存到局部变量。它至少包含稳定批次编号、名称、创建时间、过期时间和收件明细；每项明细包含稳定消息编号、接收 `host_id + instance_id` 的类型化引用、当时的显示名快照和独立状态。单收件人发送同样返回只有一项明细的批次，不产生第二套返回类型。

`消息.等待已读`返回已读等待结果，至少包含`条件已满足`、`已读实例`、`未读实例`、`已过期实例`和`失败实例`。默认等待方式为`全部`；选择`任一`时，只要一个收件副本已读取即可结束等待，但其他副本继续正常投递。`消息.取消`和`消息.等待已读`通过批次明细中的稳定消息编号定位副本，避免同名消息互相混淆。

发送前，运行时验证收件人列表非空、没有空名称和重复名称，并满足首版数量上限。输入校验失败时不得创建部分批次。校验通过后，发送服务在一次本地事务中保存批次与全部收件副本；后续网络投递按收件人独立进行。目标实例离线不属于整批提交失败。

消息内容按值复制。接收方得到独立数据，修改结果不会改变发送方变量。首版允许空值、布尔值、数字、文本、列表、字典和由这些值组成的结构。窗口句柄、运行驱动、控件对象、函数、未编码图片数据和其他进程内对象不得直接发送；需要传递文件或资源时发送经权限检查的稳定资源 ID、文件引用或普通结构化描述。

队伍码、房间码等业务值仍是普通局部变量或项目变量。消息函数读取调用时的变量值，不创建第三类“消息变量”。可能包含前导零的编号应使用文本类型。

## 6. 状态与投递确认

每个收件副本独立使用以下状态：

```text
等待发送 → 等待读取 → 已读取
                  ├→ 已过期
                  └→ 已取消
任意提交阶段发生不可恢复错误 → 发送失败
```

- **等待发送**：发送方已将消息持久保存到本地离线发件箱，尚未交给目标消息服务。
- **等待读取**：目标消息服务已持久保存消息，接收脚本尚未成功取得内容。
- **已读取**：`消息.等待接收`已成功取得内容，或监听器条件成立后当前运行会话已成功接手并解码消息；接收运行时已经返回投递确认。
- **已过期**：有效期内没有成功读取，消息不再投递。
- **已取消**：发送方在读取前主动取消，消息不再投递。
- **发送失败**：目标未知、未配对、权限、内容、实例配置或其他不可恢复错误阻止消息进入可靠队列。未知目标不会先进入“等待发送”。

内部使用“投递确认（ACK）”防止网络在消息返回途中断开造成丢失。消息服务在接收运行时成功取得并解码内容前保留消息；接收运行时成功取得数据后自动确认。ACK没有中文函数、表单或用户参数，不称为领取超时，也不承担后续业务完成检查。

`消息.等待已读`等待超时只结束当前等待，不删除或复制任何收件副本。未读副本继续等待读取，直到被读取、取消或过期。

监听器在当前运行会话内使用`待处理 → 处理中 → 已处理`状态管理业务调度；进程异常结束时把当前项记录为`处理中断`。这些状态不修改消息传输层的`已读取`结果，也不向脚本暴露手动确认或续接函数。运行会话结束后不恢复调度状态；诊断记录可以按项目保留策略清理。

### 6.1 本地诊断

每个消息事件使用批次 ID、消息 ID、来源/目标 `host_id + instance_id`、项目命名空间、运行 ID 和监听器 ID 建立关联。普通日志记录路由阶段、投递状态、重试、ACK、过期、取消和结构化错误，但默认不记录消息正文、配对短期码、设备私钥、会话密钥或认证材料。

Player 可以在本机按发送批次和收件实例查看等待发送、等待读取、已读取、已过期、已取消和发送失败，并显示失败发生在协调器、LAN、设备、实例、权限还是解码阶段。该页面只读取本机与当前配对连接的真实状态；EasyCode 不自动上传消息、在线实例、已读结果或业务结果，也不建设云端在线设备面板。用户主动导出的诊断包继续执行脱敏规则。

## 7. 首版范围

### 包含

- 一个或多个明确接收实例的发送；多收件人各自获得独立副本和状态。
- 按消息名称和可选来源实例等待接收。
- 项目级消息监听器、可选处理条件、会话内 FIFO 调度和函数正常结束后的串行自动恢复。
- 可选已读等待与未读消息取消。
- 结构化内容和值复制。
- 项目命名空间隔离。
- 同机与局域网统一语言接口。
- 同机同用户同一签名产品自动信任，以及跨设备短期码/二维码配对后的消息授权。
- 消息 ID 去重、有效期、自动网络重试、投递确认和发送端离线补发。
- IDE 与 Player 使用同一数据契约和日志语义。
- 公网断开时，同机与仍可达的局域网消息继续工作；消息基础设施故障不得阻止与消息无关的本地脚本执行。

### 不包含

- 订阅者各自收到副本的广播。
- 任意空闲实例竞争领取一个任务的工作队列。
- 跨项目自由通信、长期事件历史和流式回放。
- 脚本手动确认、手动网络重发、消费者组、领取时限或租约令牌。
- 云端设备发现、云端在线面板、公网消息中继和自动遥测。
- 通过普通消息启动远端项目、修改运行方案或取得远程启动权限；远程运行使用 [`SCHEDULES.md`](SCHEDULES.md) 的独立特权协议。

## 8. 后续路线

以下能力进入正式未来路线；每项仍需单独完成功能规格、权限设计和 Harness 后才能展示产品入口：

1. **主题广播**：发送者向主题发布事件，每个已订阅实例维护独立接收进度；适用于收件人会动态变化的状态通知，不与首版显式收件人列表混用。
2. **空闲实例工作队列**：发送者把任务提交到具名队列，多个符合条件的实例竞争领取，每个任务每次只交给一个实例；任务领取后的业务完成确认属于工作队列，不反向加入普通消息。

路线顺序根据真实项目需求和测试证据决定，不为尚未实现的能力保留可点击占位。

## 9. 验收基线

- `REQ-MSG-001`：发送方指定项目内一个或多个接收实例后，只有列表中的实例可以分别收到自己的消息副本。
- `REQ-MSG-002`：消息内容按值复制，接收方修改结果不得改变发送方变量。
- `REQ-MSG-003`：同一 ProgramDocument 从同机切换为局域网传输时，无需修改函数调用或参数绑定。
- `REQ-MSG-004`：协调器暂不可用时，发送方使用同一消息 ID 自动补发，不生成第二条逻辑消息。
- `REQ-MSG-005`：网络在消息返回途中中断且接收脚本没有取得内容时，消息保持等待读取；接收脚本成功取得并解码后状态变为已读取。
- `REQ-MSG-006`：`消息.等待已读`超时不得删除、复制或改变原消息的等待读取状态。
- `REQ-MSG-007`：发送方取消尚未读取的消息后，目标实例不得再正常取得该消息；已经读取的消息不得伪报取消成功。
- `REQ-MSG-008`：不同项目即使使用相同实例名和消息名，也不得互相收到消息。
- `REQ-MSG-009`：不支持的消息内容在发送前返回明确类型错误，不得静默转成不可恢复的字符串。
- `REQ-MSG-010`：接收脚本取得数据后的业务失败不得修改消息的已读取状态或触发普通消息自动重发。
- `REQ-MSG-011`：每个运行端点必须使用稳定 `host_id + instance_id` 路由；项目内显示名保持唯一但不得作为认证身份，重命名不得改变未读消息和已有引用的目标。
- `REQ-MSG-012`：多收件人发送必须在一次本地事务中创建批次和全部收件副本；收件人输入校验失败时不得形成部分批次。
- `REQ-MSG-013`：一个收件副本的读取、取消、过期、失败或自动重试不得改变同批次其他收件副本。
- `REQ-MSG-014`：`消息.等待已读`使用“全部”时只有全部收件副本已读取才满足条件；使用“任一”时首个已读副本结束等待，但不得取消其他副本。
- `REQ-MSG-015`：检查器粘贴逗号分隔实例名后必须生成与手动多选一致的 `list<instance_ref>` 类型化值；ProgramDocument 和 ECIR 不得保存需要运行时再次拆分的逗号字符串。
- `REQ-MSG-016`：监听消息只有在条件成立、当前运行会话原子接手并成功解码后才能返回已读回执；接手或解码失败时不得伪报已读取。
- `REQ-MSG-017`：没有`当`条件的监听器必须在下一处安全检查点处理消息；存在`当`条件的监听器只能在条件成立后处理，空闲且没有待处理消息时不得持续求值条件。
- `REQ-MSG-018`：监听处理必须与主流程及其他监听器串行；处理函数正常结束后必须从被暂停主流程的下一条语句继续，不要求开发者返回事件恢复结果。
- `REQ-MSG-019`：同一监听器的不同消息必须按到达顺序处理；相同消息 ID 的网络重试不得生成第二条待处理记录。
- `REQ-MSG-020`：Player 意外退出、崩溃或被强制终止后，不得恢复旧调用栈、页面状态或已经接手的监听事件；从未接手的未读消息继续遵守原有有效期、取消和路由规则。
- `REQ-MSG-021`：监听器处理期间新到达的消息必须进入下一处理批次，不得因消息持续到达而永久阻止主流程恢复。
- `REQ-MSG-022`：同步等待与监听消费范围发生重叠时，编译或发布检查必须明确拒绝，不能让运行顺序随机决定由谁取得消息。
- `REQ-MSG-023`：监听处理被崩溃或强制终止打断时，诊断记录必须包含运行方案、实例、目标、消息 ID、监听器 ID、`document_id`、`function_id`、`statement_id`、必要的 `field_path`、调用栈摘要和最后操作；已知异常必须记录，整个进程未写终态时必须在下次启动标记为异常中断。下次运行不得根据这些记录自动续接。
- `REQ-MSG-024`：同机与局域网普通消息不得依赖 EasyCode 云或公网；公网断开但本机/LAN 可达时，现有实例继续传递消息。
- `REQ-MSG-025`：协调器不可达、局域网不可达、目标实例未上线、等待读取和已过期必须使用不同结构化状态；任一消息故障不得把 Player 或与消息无关的本地流程标记为不可运行。
- `REQ-MSG-026`：同机同用户同一签名产品信任域的 Player 实例只能自动信任普通消息；跨项目、不同签名域和跨设备不得继承该信任，跨设备必须完成 [`NETWORK.md`](NETWORK.md) 的短期码/二维码配对并获得消息权限。
- `REQ-MSG-027`：未知、未配对、已撤销、跨项目或未授权实例必须立即失败且不创建离线副本；已知离线实例只能在消息有效期内保留原消息 ID，过期后不得继续投递。
- `REQ-MSG-028`：配对身份、消息权限和远程启动权限必须分离；消息正文、已读或监听器均不得启动远端任务。
- `REQ-MSG-029`：消息诊断必须使用稳定批次/消息/主机/实例/运行/监听器 ID 关联并默认排除正文、短期码、密钥和令牌。
- `REQ-MSG-030`：Player 的实例与消息状态只来自本机服务和当前配对 LAN 连接；首版不得自动上传消息状态或建设云端在线设备面板。

Harness 至少覆盖：同机单发、同机多发、同机自动信任边界、短期码/二维码配对、权限撤销、未知立即失败、已知离线 TTL、局域网多发、收件列表变量、逗号粘贴转换、空列表、重复名称、实例重命名、批次原子提交、部分已读、全部已读、任一已读、部分取消、离线补发、等待接收超时、等待已读超时、返回途中断网、解码失败、成功已读、读取后取消、重复消息 ID、项目隔离、实例重名、实例离线、消息过期、非法内容、协调器鉴权失败、监听立即处理、监听条件延迟处理、FIFO、批次快照、禁止重入、主流程自动恢复、原子接手失败、崩溃后不续接、处理中断诊断、过期不执行、同步与监听消费冲突、Player 独立运行、公网断开但 LAN 可达、LAN 不可达、本机服务重启、脱敏导出和零云端设备/消息上报。

首个正式版本的真实宿主矩阵还必须覆盖 Windows→Android、Android→Windows 和 Android→Android 的明确收件人投递，以及 Android 网络切换、进入后台、恢复前台和离线补发。Android 系统限制导致连接暂不可用时只能影响传输状态，不得让 Runtime 并发执行第二条界面操作流或伪报已读。

## 10. 由实现与 Harness 冻结的默认值

- 默认有效期：5 分钟；允许显式设置 1 毫秒至 7 天。
- 最大消息正文：按确定性 JSON 编码后 256 KiB；最大嵌套深度 64，最大结构项数量 10000。
- 首版单次发送允许的最大接收实例数量：64。
- 已读诊断记录保留时间尚未冻结；在清理策略闭环前不提供可见配置入口。
- 配对设备上限、心跳/重连间隔和传输退避上限。

首版不新增`消息.回复`；回复方使用`消息.发送(接收实例 = 收到消息.来源实例, ...)`表达，避免为参数预填充制造第二个传输函数。
