# EasyCode 架构决策记录

状态：`Accepted`。这里记录已经冻结的跨模块决定；局部实现细节留在代码和功能规格中。后续改变已接受决定时必须新增取代 ADR，不能静默改写历史语义。

## ADR-001：中文严格脚本是流程唯一数据源（已被 ADR-017 取代）

- 决定：历史方案曾计划以可解析、可格式化、可诊断的中文严格脚本和 AST 保存业务流程。该决定不再作为实现依据。
- 原因：大型流程的文字密度、搜索、复用和版本差异优于自由连线画布。
- 后果：旧流程画布不再作为可编辑主流程；页面拓扑不属于当前版本范围，是否存在派生视图由未来独立规格决定。

## ADR-002：Python 通过函数契约进入结构化程序

- 决定：普通用户调用结构化函数；官方原子函数和项目扩展函数可由 Python 实现，但必须声明类型、平台、权限、错误和返回值。
- 原因：保留 Python 上限，同时保护检查器、Player 绑定、静态检查、调试和发布。
- 后果：ProgramDocument 不直接嵌入或执行任意 Python；复杂实现以普通扩展函数进入，不再保留独立“调用能力”概念。

## ADR-003：统一强类型参数与 Control 协议

- 决定：函数形参类型生成默认 Control，特殊函数可覆盖控件和动作；IDE 与 Player 共用数据契约和原子控件。
- 原因：避免同一参数在代码、检查器和 Player 出现三套语义。
- 后果：平台不支持某个捕获动作时只禁用动作，不把复杂值降级为字符串。

## ADR-004：所有长期绑定使用稳定 ID

- 决定：语句、参数、函数、变量、持久化值节点、资源、扩展对象和 Player 控件均使用不可见稳定 ID。
- 原因：重排、折叠、重命名、提取函数、参数修改和资源整理不能破坏绑定。
- 后果：行号、显示名和文件路径只用于展示和定位，不作为长期主键。

## ADR-005：页面拓扑代码优先（已被 ADR-020、ADR-040 取代）

- 决定：历史方案曾要求页面、特征、出口和随机弹窗以严格代码表达。ADR-040 已取消首版页面导航范围，本决定不再授权任何实现。
- 原因：避免画布和文本成为两份平权数据源。
- 后果：图形操作必须生成合法结构，不能自由摆放任意动作节点。

## ADR-006：执行宿主与当前操作目标分离

- 决定：Windows Player 是可承载 Windows 桌面/窗口与 Android ADB 驱动的运行宿主。项目声明一个默认目标和零到多个附加目标；脚本通过结构化目标作用域显式串行切换，任意时刻只有一个当前目标。Android 本机 Player 只操作当前手机；无目标实例只运行不依赖视觉与输入的逻辑。
- 原因：启动模拟器后继续操作 ADB 是一条常见的连续业务流程，强制拆成两个实例会增加消息接管和配置成本；同时执行多个目标则需要隔离的驱动、日志和故障恢复，不应伪装成普通目标切换。
- 后果：ECIR 保持平台中立并携带目标引用；坐标、区域和捕获结果带来源目标，不能跨目标静默复用。单实例目标切换保持串行；真正并发使用多个 Player 实例。平台能力在编译、运行和发布前检查，不支持时明确阻止。

## ADR-007：图片资源不携带默认运行区域

- 决定：资源保存来源元数据；实际识别区域属于具体函数调用。
- 原因：同一图片可能在不同页面和区域复用，静默套用录制区域会产生隐蔽错误。
- 后果：捕获可一次填入图片和当前调用区域，但资源本身不控制其他调用。

## ADR-008：捕获使用统一 Capture Session

- 决定：取点、区域、图片、控件和路径使用同一会话协议，不同平台只替换宿主。
- 原因：统一生命周期、项目身份、字段回填、取消和错误恢复。
- 后果：每次字段捕获绑定会话 ID 和请求 ID，不能被其他 IDE、项目或旧宿主抢走。Windows 目标携带真实物理区域并原位覆盖冻结帧；没有桌面区域的逻辑目标才进入最大化等比居中模式。单选不展示序号，选区编辑使用低遮挡角标，禁用动作只降低图标权重。

## ADR-009：不迁移旧测试项目

- 决定：新格式不兼容旧画布测试项目，打开时明确提示版本不支持。
- 原因：用户确认旧内容均为可清空测试稿。
- 后果：删除旧兼容分支时仍需通过当前项目测试，不保留静默迁移。

## ADR-010：规格驱动的垂直切片与 Harness 放行

- 决定：每项功能从需求、契约到 IDE、运行时、Player、失败恢复和测试一次闭环。
- 原因：防止只做前端、只做后端或功能看似存在却无法使用。
- 后果：没有需求追踪、自动测试和环境证据的能力不能标记完成。

## ADR-011：目标架构与首个正式版本分层

- 决定：目标架构描述产品长期必须能够承接的完整方向；首个正式版本单独声明可交付、可验收的发布范围。架构预留不等于功能已实现，也不自动授权前端展示入口。
- 原因：若把所有长期方向自动等同于首版范围，会让实现优先级、验收状态和产品承诺失真；若完全不规划正式目标平台边界，又容易在后续实现时更换地基。Android 本机是否进入首版已经由 ADR-027 单独冻结，运行服务、协作扩展和其他后期能力仍按本决定逐项定范围。
- 后果：`PRODUCT.md` 同时维护长期方向与首版范围；每个未冻结能力必须通过功能规格决定进入哪个版本，并在端到端闭环完成前保持不可见或明确标记为非产品入口。

## ADR-012：前台变量模型只暴露局部变量与项目变量

- 决定：用户只学习局部变量与项目变量。每次任务从开发者默认值和当前 Player 运行方案创建独立、可读写的项目变量副本；所有项目函数共享该副本，任务结束后释放。项目变量不提供配置、本次运行或持久模式；需要长期生成或读取的数据使用显式文件函数。
- 原因：配置与本次运行的差异只是初始值来源，不足以形成两种变量；把跨运行副作用隐藏在变量模式中还会让外部目标的旧状态污染下一次运行。统一会话副本既保留跨函数共享，又让重置和写回边界可预测。
- 后果：变量工作区只管理项目变量；局部变量由 Program Service、类型系统和调试器管理；Player 按稳定 `variable_id`覆盖运行初始值但不接收运行期回写；旧 `$var/$ctx/$env`、无类型 `blueprint.variables`、持久变量模式和通用键值存储不进入 vNext；文件与消息另立函数规格。

## ADR-013：显式文件能力取代通用存储，不向脚本暴露租约

- 决定：vNext 不提供 `存储.*`或持久变量。需要跨运行保留或与本机软件交换的数据，使用首版 `文件.*`与 `目录.*`函数操作用户可见的真实文件系统对象。目录函数和递归删除的首版边界由 ADR-048 进一步冻结。普通脚本不提供本地或分布式`租约.*`函数。
- 原因：通用键值存储在用户心智上仍是“写到磁盘的持久变量”，用途与项目变量难以区分，却不能覆盖真实文件交换场景。租约对首版脚本开发的价值很低，公开其所有者、令牌和续期生命周期会显著增加理解与配置成本。
- 后果：文件覆盖、追加和替换由平台内部路径级写锁与原子提交保证，不要求脚本手动加锁；跨实例与局域网协作只通过独立`消息.*`规格讨论，消息内部投递确认不作为通用租约能力暴露。

## ADR-014：消息首版使用项目内明确收件人多播

- 决定：首版`消息.*`要求发送者指定项目内一个或多个接收实例；同机与局域网只属于运行配置和传输实现，不产生两套脚本函数。多个实例使用文本列表表达，运行时为每个收件人生成独立消息副本和状态。实例名标识 EasyCode 运行端点，不绑定游戏账号。
- 原因：显式收件人列表能够覆盖一对一与“小范围发送同一消息”的多开场景，又不要求开发者理解频道、订阅和消费者组。强类型列表还能由变量和检查器安全编辑，避免逗号字符串的转义与空项歧义。
- 后果：`消息.发送`返回一个批次记录及其收件明细；等待、取消、过期和重试按收件人独立处理。主题广播和空闲实例工作队列仍属于未来路线；前端在这些能力端到端完成前不展示占位入口。

## ADR-015：普通消息以接收脚本成功取值作为传输完成边界

- 决定：`消息.等待接收`成功取得内容，或监听条件成立后当前运行会话原子接手并成功解码消息，运行时才返回投递确认并将对应收件副本标记为已读取；普通消息不等待接收方完成后续业务，不提供`消息.完成`。`消息.发送`返回批次及收件明细，供`消息.等待已读`和`消息.取消`定位同一批次中的具体副本。
- 原因：房间码是否成功传到接收脚本与接收脚本能否进入房间是两个独立结果。把业务完成塞进消息确认会让传输层理解每个项目的页面和操作语义，并迫使普通脚本管理领取时限。稳定消息记录则能在存在多条同名消息时准确等待或取消指定消息。
- 后果：网络重试和重复消息 ID 由服务自动处理，不公开`消息.重发`；业务需要再次通知时创建新消息。未来空闲实例工作队列可以单独定义领取与任务完成，不改变普通消息的已读边界。

## ADR-016：消息监听采用协作式串行调度且不跨运行续接

- 决定：项目可以声明带可选`当`条件的消息监听器。没有满足监听条件的消息继续由消息服务保持未读；条件成立后，当前运行会话原子接手并解码消息，再返回已读回执。调度器只在安全检查点挂起主流程，串行调用普通项目函数处理监听消息；函数正常结束后自动从主流程下一条语句继续。Player 崩溃或被强制终止后不恢复旧调用栈、页面状态或已经接手的事件，ProgramDocument 和运行时契约不提供事件专用恢复或续接结果。
- 原因：同步`消息.等待接收`不能覆盖“主流程运行期间随时收到、稍后满足条件再执行”的业务；照搬 JavaScript 并发回调又会让两个流程同时操作同一窗口。脚本业务和现场状态多样，跨重启自动续接可能在用户切换运行方案或页面已经变化后执行旧操作，因此首版只保证消息在接手前可靠，不把任意 GUI 流程伪装成可恢复下载任务。
- 后果：消息传输状态与业务处理状态分离；发送方看到已读取不代表接收方已经完成业务。监听器不得重入，同一监听器按到达顺序处理，处理期间新到达的消息进入下一批。长操作必须提供安全检查点；条件在没有候选未读消息时不得轮询。运行时持续写入结构化日志，崩溃诊断记录中断位置、调用栈摘要、当前监听器和消息 ID，但这些证据不参与下次自动执行。

## ADR-017：ProgramDocument 是项目函数唯一可编辑事实

- 决定：项目函数以版本化、确定性 JSON 的强类型 `ProgramDocument` 保存。用户通过纵向结构化语句投影和右侧 Control 编辑；不提供项目函数的可编辑源码、Monaco、解析草稿或文本反向解析。
- 原因：用户实际通过插入与表单完成编辑。直接保存结构模型可以消除文本与检查器同步、临时语法错误、参数定位和稳定绑定问题，同时保留代码式顺序与高信息密度。
- 后果：Program Service 负责结构化命令、Schema、类型、引用、撤销重做和保存；缺少参数是可保存的语义不完整状态。只读伪代码可以生成，但不是第二数据源。ADR-001 不再生效。

## ADR-018：ECIR 是确定性构建产物而非第二编辑模型

- 决定：ProgramDocument、函数契约、项目配置、启用扩展和资源经同一 Compiler Service 生成版本化 ECIR。IDE 调试和 Player 都执行该语义；ECIR 与调试映射可重建，不能反向成为编辑事实。
- 原因：同一程序若在 IDE 与 Player 使用不同解释路径，会产生难以复现的行为差异；若直接编辑 ECIR，则会破坏可读模型和稳定工具链。
- 后果：相同输入和版本必须产生字节级或规范化等价输出；发布包不包含 ProgramDocument。Player 表单通过经过类型校验的参数覆盖层/执行计划生效，不直接篡改签名 ECIR。

## ADR-019：扩展实现使用外部 IDE，EasyCode 负责契约与交付

- 决定：Python、C++、Kotlin 等扩展实现在 PyCharm、VS Code 或其他外部 IDE 开发。EasyCode 只提供骨架、导入、契约审核、测试、启停、权限、依赖锁和发布闭包，不内置完整通用代码编辑器。
- 原因：复制成熟代码 IDE 的编辑、依赖和调试能力会显著扩大产品边界；普通脚本制作者只需要结构化函数契约和一致的调用体验。
- 后果：扩展源码不进入普通项目函数编辑工作区；扩展函数注册后与官方函数使用同一插入和检查器体验；Worker 故障不得拖垮 IDE 或伪报成功。

## ADR-020：页面导航是默认关闭的官方功能扩展（已被 ADR-040 取代）

- 决定：页面导航随 IDE 分发，但按项目默认关闭。扩展页面模型是页面、特征、出口和覆盖弹窗的唯一业务事实；拓扑只作为派生浏览或受约束编辑投影。
- 原因：多数普通脚本不需要页面拓扑，把它作为核心常驻服务会增加入口、后台扫描、理解成本和 Player 体积；其跨工作区、模型、编译和运行能力又明显超出普通函数扩展。
- 后果：未启用时必须为零入口、零 `页面.*` 函数、零扫描任务和零 Player 依赖。启用后由功能扩展贡献领域服务、工作区、编译步骤和运行模块。ADR-005 的“代码优先”承载形式不再生效。

## ADR-021：条件使用无副作用的强类型混合条件树

- 决定：ProgramDocument 条件同时支持布尔值叶和类型化比较叶，并只用“全部满足 / 任一满足 / 取反”组合。非布尔值不做隐式真假转换；比较由类型注册表约束；`all/any` 按投影顺序短路。输入、文件写入和目标切换等有副作用操作不能嵌入条件，正常未命中与异常保持不同结果。
- 原因：只允许布尔函数会迫使普通比较产生大量碎片项目函数；开放任意文本表达式或允许调用副作用的表达式又会重新引入一门难以检查、调试和跨平台编译的语言。有限条件树可以覆盖 GUI 自动化常见判断，同时保持确定性和检查器可编辑性。
- 后果：连续帧、等待、事件顺序和外部查询由普通函数产生结果后参与条件，不扩张条件语法。成员可选性、普通调用边界和递归纯值计算分别由 ADR-022、ADR-023 与 ADR-025 冻结；普通扩展不能注册私有条件语法。

## ADR-022：函数使用单一逻辑返回与显式可选结果

- 决定：每次函数调用只有一个逻辑返回值。多项相关信息组成带稳定 `field_id` 的不可变命名记录；只有“有值 / 无值”两种正常结果时使用 `optional<T>` 和明确空状态。用户只看到统一的“有结果”判断和契约生成的成员选择器，不看到 `optional`、空记录或字段字符串。
- 原因：多个平铺输出会拆散一次调用的结果并产生无效组合；用空 `{}`、伪造 `(0,0)` 或任意字典表示未找到，会把类型错误推迟到运行时。显式可选值允许编译器在条件成立作用域内确认成员安全，又不要求普通用户学习内部类型术语。
- 后果：未确认有结果时访问成员会产生可定位诊断，检查器提供添加存在性判断等修复。动态字典使用字典操作；正常无结果不吞掉异常。字段改名依赖稳定 ID，字段删除或类型变化必须计算 ProgramDocument、Player 与扩展引用影响。

## ADR-023：普通函数调用不嵌入参数

- 决定：官方、项目和扩展函数只作为独立 `call` 语句执行，不能嵌入参数、条件或另一调用。项目函数可以返回坐标等值，但调用语句先绑定局部结果，后续语句再使用；参数内部允许基于现有值的确定性、无副作用、类型化纯值计算。
- 原因：隐藏调用会把截图、等待、错误、日志、取消和断点埋进另一个字段，使执行次数和失败位置难以理解。完全禁止参数计算又会为坐标偏移、文本组合等简单转换制造大量临时语句。
- 后果：主流程可以通过小项目函数收纳包含普通调用或副作用的复杂逻辑，调用边界始终可见、可单步和可诊断。纯值操作按 ADR-025 完整递归组合，界面可以建议折叠或提取，但纯值复杂度本身不强制创建项目函数；表达式不能借此重新引入普通函数调用。

## ADR-024：完整集合模型包含结构化变换与 JSON 边界

- 决定：目标架构同时支持固定字段记录、顺序同类列表、动态键同类字典和外部未知 JSON。筛选、转换、排序、分组和统计作为正式无副作用集合表达式；涉及普通函数或 I/O 的逐项工作使用显式循环。循环进入时固定输入快照，集合更新采用不可变值语义。
- 原因：只提供包含、索引和循环虽然理论上能够拼出数据处理，但会让副本计划、识图结果、消息明细和 Player 配置产生大量样板语句；把任意对象都降级为字典或 JSON 又会丢失成员选择、静态检查和表单生成。
- 后果：IDE 与 Player 可以从同一 Schema 生成表格、重复卡片、键值和嵌套 Control；字典不提供隐式顺序，缺失键/序号返回可选结果。未知 JSON 使用专用操作或显式转换；流式大数据另立能力，不伪装成无上限列表。具体目标契约由 `docs/vnext/COLLECTIONS.md` 定义，实施批次后续决定。

## ADR-025：纯值表达式完整递归组合，界面提取不构成能力限制

- 决定：ProgramDocument 中经核心批准的无副作用值操作可以递归组合所有类型兼容的已有值，并为每个持久化可配置节点分配稳定 `value_id`。普通函数、I/O、等待、目标访问和扩展私有语法仍只能通过独立语句进入。界面使用摘要、折叠、聚焦和可撤销提取管理复杂度；不得以固定浅层嵌套或强制提取限制底层表达能力。
- 原因：只允许少量两层组合会迫使坐标、文本、时间和集合计算产生大量临时语句，并在后期再次改动 Schema、Compiler、Player 绑定与 Control。开放任意源码又会破坏类型检查、跨平台执行和稳定编辑。递归强类型纯值树可以保留完整能力，同时让普通用户只操作结构化表单。
- 后果：Player 可以按稳定值节点暴露表达式内部的精确值；移动、改名和无关编辑不得破坏绑定。复杂子树可以提取为赋值或返回值项目函数，语义和绑定必须保留或显式迁移。技术上的深度、节点、编译和内存预算只作为 Harness 安全门，不能成为产品能力分级；扩展复杂算法继续以普通强类型函数提供。

## ADR-026：最小运行核心与易用官方函数库分层

- 决定：EasyCode 运行核心只保留不可由现有原语和 ProgramDocument 结构表达的通用能力；官方函数目录可以收录由这些原语组成、经过多个真实项目验证的高频标准函数。原子/标准只作为内部治理分类，用户按图像、输入、等待等用途查找，插入后都生成同一种 `call` 语句。
- 原因：把“精简核心”误解为“只给用户低级函数”，会迫使普通用户为点击直到消失等常见操作反复搭建循环、等待和失败处理；反过来把每个项目便利组合都做成平台函数，又会造成同义功能和运行机制膨胀。结构化标准组合可以提高易用性而不扩大底层语义。
- 后果：标准函数必须具有规范 ProgramDocument 组合定义，并满足跨项目复用、单一清晰语义、显著减少易错样板和等价性 Harness；性能融合只是可替换实现。单项目、单游戏或领域算法继续使用项目函数或扩展，不进入通用核心。

## ADR-027：Android 本机 Player 是首个正式版本完成门

- 决定：首个正式版本必须同时包含 Windows IDE、Windows/ADB Player 和可脱离电脑独立运行的 Android 本机 Player。允许内部按垂直切片先实现 Windows/ADB，但在 Android 真机调试、权限、捕获、输入、文件、Player 表单、兼容扩展闭包、诊断和签名 APK 全部通过前，不得宣称首个正式版本完成。首版硬交付物为可安装签名 APK；AAB 仅在未来明确要求应用商店分发时另行冻结。
- 原因：Android 本机不是展示型预留，而是用户选择的首版核心场景。若只保留 ECIR/Schema 接口而把真实宿主推迟，截图、权限、文件、扩展 ABI、小屏 Control 和生命周期问题会在后期反向改动地基；反之要求同一 ProgramDocument/ECIR 契约并用真机 Harness 放行，可以在不制造第二套业务语义的前提下及早验证跨平台架构。
- 后果：Windows IDE 必须能通过 USB/ADB 部署或更新测试 APK、读取结构化日志并区分 Android 本机测试与普通 ADB 目标测试。Android APK 使用 Kotlin/C++ Runtime、MediaProjection、AccessibilityService 和 Android 文件授权，包内不包含 ProgramDocument、扩展源码、Windows Python 或 IDE 组件；断开数据线并关闭 IDE/后端后仍须独立运行。未完成的 Android 入口保持不可见或明确禁用，iOS 与 macOS 仍不在范围内。

## ADR-028：Player 本地优先且网络能力显式分级

- 决定：未显式使用公网能力的发布项目必须在无公网、无 IDE、无 EasyCode 云或单独开发后端时完整运行。发布器从真实函数、功能扩展和扩展 Manifest 推导“无网络 / 本机或局域网 / 公网”能力，打入 Runtime、函数、资源、OCR 数据、Control、原生库和兼容扩展的完整本地闭包。显式网络调用失败只通过当前调用的普通错误契约传播，不建立全局离线故障。
- 原因：仅声明“独立 Player”仍可能让实现通过启动登录、在线验权、更新检查、遥测、CDN资源、OCR模型或扩展依赖下载偷偷依赖公网。完全禁止网络又会破坏多实例局域网消息和未来显式 API 场景。能力分级和依赖闭包同时保证普通项目可靠离线，并让真正需要网络的脚本保持自由。
- 后果：同机/LAN 消息不依赖 EasyCode 云；更新、遥测、商业授权和公网服务在独立规格完成前不可成为隐式入口或运行前置。未来授权不得要求每次启动/任务在线，有效本地凭据在断网时可验证，任务中途到期不被强制终止。Windows/Android 发布与 Harness 必须在阻断公网、清空预热缓存并关闭 IDE/后端的环境验证无隐式外连和无运行期下载。

## ADR-029：商业授权延后为独立产品切片

- 决定：首个正式版本不实现脚本收费激活、设备授权、授权账号或在线授权管理，也不显示相关入口。首版继续实现发布包签名、内容哈希、完整性校验和扩展许可证材料检查；这些安全与供应链能力不等同于商业授权。商业授权保留为重要后续路线，届时以独立产品、服务端、安全、交互和 Harness 规格纵向闭环。
- 原因：商业授权会引入作者与终端用户账号、设备身份、密钥生命周期、换机、续期、吊销、服务可用性、支付/售后和攻击面。现在预建局部授权入口或空服务既会扩大首版风险，也容易破坏已确认的本地优先体验；签名与完整性已经足以承接首版可信发布。
- 后果：当前 Player、IDE、发布器和后端不得出现不可用的激活/授权 UI、隐式联网验权或占位 API。架构只保留不绑定供应商的签名验证边界，不提前冻结授权协议。未来授权必须支持本地可验证凭据、断网宽限和任务不中途终止，并在启用前补齐商业规则、威胁模型、服务端、管理端、恢复流程与真实断网验收。

## ADR-030：首版提供可关闭的分层在线更新

- 决定：首个正式版本提供 EasyCode IDE 与已发布 Player 的服务器更新，但更新是项目/全局可关闭、失败不影响当前有效版本的维护能力。更新拆分为 IDE、Player 应用和项目内容三个域；日常 ECIR/资源/Schema 变更使用签名内容更新，Runtime、宿主、原生扩展、权限或 ABI 变化使用完整 Windows Bundle/Android APK 应用更新。EasyCode 不绕过项目作者单独向第三方 Player 静默替换 Runtime。
- 原因：大型脚本交付给大量终端后，逐个重新分发无法维护；把所有变化都做成安装包又会让普通脚本和图片修改成本过高。单一模糊自动更新开关还会混淆平台与业务版本，并破坏本地优先结论。分层更新既支持高效内容发布，也让平台差异、兼容性和信任边界可验证。
- 后果：任务运行网络和在线维护网络分别报告；项目关闭全部更新时必须零更新外连。每次任务固定不可变发布版本，运行和暂停时不切换。更新采用成熟签名元数据、防回滚、暂存、原子切换和上一正常版本恢复；Android 内容更新与需要系统安装确认的 APK 更新分别验收。服务托管、强制更新和终端用户控制权由后续 ADR 分别冻结。

## ADR-031：官方托管与开放自建源共用一套更新协议

- 决定：EasyCode 首版提供面向普通作者的官方托管更新服务，同时开放相同签名 Feed、不可变发布格式和客户端验证协议，允许高级作者使用自己的 HTTPS 对象存储/CDN。官方托管是默认主路径，自建是高级配置；二者不形成两套 Loader 或安全模型。
- 原因：只做脚本制作而把分发完全交给作者，会让普通用户承担服务器、域名、对象存储和运维复杂度，产品链路停在交付前；只允许官方托管又会制造平台锁定、单点和长期迁移风险。统一开放协议可以同时获得一键发布体验与作者自主权，并为未来托管 VIP/额度服务留下合理商业空间。
- 后果：首版服务端必须建设作者身份、项目归属、上传、不可变存储/CDN、通道、基础配额/使用量、审计、监控、备份和故障恢复，但不建设 VIP 计费或终端脚本授权。终端公开更新不要求作者账号；发布私钥不上传。源迁移需要原信任根签名，配额耗尽只阻止新发布，不能影响已安装版本运行。

## ADR-032：作者可以发布不打断现场的强制更新

- 决定：每次发布可以选择可选或强制。强制策略由现有更新信任根签名，并包含最低允许发布序号、生效时间、宽限截止时间、原因和各平台目标。它只在宽限结束后阻止低版本开始新任务；已经运行或主动暂停的任务继续使用原 `release_id` 到终态，Player 外壳、日志、诊断、方案和更新入口始终可用。
- 原因：大型游戏更新后，旧图片、坐标或交互逻辑可能造成真实误操作，作者需要阻止明显不安全的旧版本继续新开任务；如果每个更新都立即强制，又会让临时网络/服务故障破坏本地优先和正在执行的自动化。签名策略、宽限期与只约束新任务在安全和可用性之间形成明确边界。
- 后果：强制策略发布前必须证明每个覆盖平台有可取得、签名有效且兼容的目标产物。未收到新策略的离线客户端不猜测；收到后缓存最后可信策略并防时钟回拨/普通缓存清理绕过。启用强制更新的发布不得宣称无条件离线新开任务，Android 用户拒绝系统安装后旧应用仍可维护数据，但宽限结束后不能新开任务。

## ADR-033：终端用户控制更新自动化，但不能绕过已知强制策略

- 决定：作者启用 Player 更新后，终端用户可以分别关闭普通可选更新的自动检查、自动下载和自动应用，手动检查始终保留，偏好跨版本保存且不能被作者普通发布重置。只要作者启用了强制策略能力，Player 继续执行已披露的轻量签名策略检查；该检查不受普通更新偏好影响，也不下载或安装产物。Player 一旦取得并验证强制策略，终端用户只能在宽限期内选择下载和安装时间，不能通过设置、断网、普通缓存清理或系统时钟回拨删除最低版本约束。强制策略仍不打断运行/暂停，也不绕过 Windows 或 Android 的安装确认。作者在打包时关闭更新的 Player 不包含端点、任何更新调度器、入口或徽标。
- 原因：可选更新不应把终端设备变成作者无法关闭的后台联网客户端；但已经验证的强制安全策略如果能被普通开关删除，就无法阻止已知危险版本继续新开任务。把“是否联网检查”“是否自动取得产物”“何时安装”和“已知最低版本约束”分开，可以同时维持用户控制、本地优先与作者维护能力。
- 后果：长期离线的 Player 无法得知服务器后来发布的强制策略，并继续遵守最后可信状态；恢复网络后由策略检查器取得最新可信策略。产品与作者发布报告必须诚实说明这一物理边界，不能宣称离线终端会被即时强制。宽限期内用户可以择时更新，宽限结束后只有新任务受阻；Player 外壳、数据、日志、诊断和更新恢复始终可用。

## ADR-034：可选更新使用匿名本地分桶渐进发布

- 决定：首版在测试/稳定通道之外，为可选更新提供稳定白名单、确定性百分比灰度、暂停、按原范围继续、扩大比例和全量推广。每个更新产品安装在本机生成随机、产品域隔离且正常升级后保留的匿名分组码；客户端依据签名 `RolloutPolicy` 在本地分桶，原始分组码不上传。比例只能扩大，白名单优先于百分比。强制最低版本不能使用灰度分组，只有目标发布对稳定通道 `100%` 可取得后才能另外启用。
- 原因：测试/稳定二分仍会让大型脚本的稳定用户一次性承受新版本风险；服务端按设备追踪又会引入身份、隐私和动态定向 API。客户端确定性分桶让官方托管与静态自建源共享同一能力，比例扩大保持原人群，且无需终端遥测。
- 后果：`RolloutPolicy` 是可变但签名、revision 单调的发布策略，不改变不可变产物。暂停只阻止已取得暂停策略的客户端继续取得或应用未激活版本，不能远程降级已经安装的版本，也不能即时影响离线客户端。作者端不得展示没有遥测支撑的安装数、成功率或崩溃率；服务端不自动扩大、暂停或回滚。本地启动/加载健康失败后的上一槽恢复仍保留。

## ADR-035：测试通道由作者通过匿名分组码控制

- 决定：稳定版终端不能自行切换进入测试通道。Player 只显示项目级随机测试分组码；用户主动把它交给作者后，作者将对应哈希加入或移出测试白名单。作者自己的测试安装也使用同一授权模型。移出测试通道不自动降级，只有稳定发布序号追平后才回到稳定更新路径。
- 原因：终端随意进入测试通道会把不稳定版本和兼容风险转嫁给普通用户；使用匿名产品域代码又能避免引入账号、硬件身份和设备跟踪。
- 后果：作者端维护测试白名单和审计，终端只提供复制、重新生成和真实状态，不显示误导性的“加入测试”开关。重新生成会退出旧白名单并改变后续灰度分组，但不回退已经安装的版本。

## ADR-036：首版提供类型化 HTTP/API 原子能力

- 决定：首版普通 HTTP 原子能力覆盖方法、地址、查询、请求头、文本/JSON正文、超时、重定向、TLS、状态、响应头和文本结果；它不接受或返回文件、任意二进制值和流对象。文件上传与下载由 ADR-042 冻结为两个独立原子能力。Runtime 不在函数内部自动重试可能产生副作用的请求；作者只有通过 ADR-046 的异常区域策略显式重试并确认副作用风险，才会产生下一次请求，项目可以提供业务幂等键。最终显示名仍在官方函数目录轮统一冻结。
- 原因：抢票、数据上传、业务接口和外部系统集成属于自动化软件的常见舒适区；要求每个项目编写扩展会造成重复工作。把浏览器 DOM、Cookie 会话接管和验证码混入 HTTP 又会扩大权限和执行语义。
- 后果：网络失败只通过当前调用返回结构化错误；密钥和敏感头按契约脱敏，动态公网地址进入发布权限报告。Windows 与 Android 保持相同契约。浏览器 DOM 自动化留给未来扩展，不成为 HTTP 的隐藏模式。

## ADR-037：计划属于 Player 宿主控制面并支持批量与局域网派发

- 决定：首版提供单次、每日和固定间隔本地计划，但不增加 `计划.*` ProgramDocument 函数。Windows 每用户 Player Hub 可以按批次启动多个已安装项目/运行方案，并向已配对且明确授予远程启动权限的局域网实例派发；Android 只调度当前 APK 内的运行方案。同一实例串行，不同实例可并行或确定性错峰。
- 原因：定时启动尚未运行的项目需要宿主级代理，项目内脚本无法唤醒自己；把远程启动当普通消息会混淆业务数据与特权控制。Android 当前一项目一 APK 的交付边界也不适合伪装成跨项目宿主。
- 后果：计划使用明确时区、错过触发与重叠策略；远程命令带稳定 `dispatch_id`，ACK 丢失或重试只产生一个 `run_id`。协调端是单一所有者，离线时其他实例不选主。Windows Hub 运行在登录用户会话，Android 承认省电/强制停止导致的延迟，不承诺虚假精度。

## ADR-038：Player 捕获和文件动作逐字段开放并按需授权

- 决定：开发者逐字段、逐动作、逐平台决定是否向 Player 开放取点、框选、当前画面截取、设备选图、控件捕获、手势路径和文件/目录选择，默认全部关闭。真实动作是作者许可、字段类型、发布闭包、宿主/目标能力和当前权限的交集；IDE 与 Player 共用强类型 Control 与结果契约，但分别提交到 ProgramDocument 和 Player 运行方案/私有资源覆盖。
- 原因：只显示一个无功能按钮无法满足终端配置；把全部动作默认开放又会增加权限、误操作和发布体积。平台权限是终端用户在动作发生时授予的事实，不是作者勾选即可预授权。
- 后果：图片截取/选择确认后进入 Player 私有覆盖目录；普通文件和目录保留带访问模式的类型化外部引用。取消、拒绝、撤销、目标变化或宿主失败保留旧值并回到原字段。Android MediaProjection 每次采集按系统要求取得同意，文件使用 SAF；控件捕获仅在真实 Accessibility 能力存在时条件显示，不作为所有机型的首版硬门。
- 补充：文件/目录系统选择器的“打开/保存/选择此文件夹”就是用户确认，返回 Player 后不再重复询问“是否使用”；宿主仍必须先把结果作为未提交候选，二次验证 `PlayerControlDestination` 后原子写入。无操作目标的方案可使用主机文件/目录选择，此时 `target_id` 为空；点、区域、图片和路径等需要目标坐标空间的动作仍必须绑定真实目标。

## ADR-039：实例使用本机信任与跨电脑显式配对

- 决定：同一操作系统用户下、同一签名产品的本机 Player 实例可以自动建立信任；跨电脑实例必须通过短期一次性配对码或二维码交换稳定公钥身份。显示名称仅用于理解，不参与鉴权。已知离线实例可以在消息/派发有效期内排队，未知名称、错误身份或已撤销配对立即失败。
- 原因：多开脚本需要低摩擦的本机协作，也需要防止局域网内陌生设备仅凭实例名接收消息或启动任务。引入云账号不是本地优先场景的必要条件。
- 后果：配对、撤销、密钥轮换和状态诊断本地完成；配对本身只允许建立连接，远程启动等高权限能力另行授权。普通消息和特权派发可以共用安全传输，但不能共用业务确认语义。

## ADR-040：页面导航不进入首个正式版本

- 决定：首版不分发页面导航扩展，不提供 Page Model、`页面.*` 函数、页面工作区、拓扑组件、页面扫描、路径规划或随机弹窗调度。历史页面规格移动到非权威 deferred 区并明确不授权实施。
- 原因：大多数脚本不需要页面拓扑，当前版本仍有更基础的函数、跨平台、Player、网络、计划和交付闭环需要完成。保留默认关闭的半成品仍会增加模型、后台、包体和验收成本。
- 后果：ADR-005 与 ADR-020 不再生效。`image / ocr / page` 三个资源根目录继续保留，其中 `page` 只是一类图片目录。通用扩展地基使用中立 Harness 扩展验证；未来若重新立项页面导航，必须从新的功能规格、权限、跨平台闭环和 Harness 开始。

## ADR-041：首版不自动遥测也不建设云端设备舰队

- 决定：EasyCode 不自动上传运行结果、崩溃、日志、截图或在线状态。结构化诊断默认保存在本机，只有用户明确导出后才离开设备。官方更新托管只展示服务端真实拥有的请求量、传输量、配额和发布审计，不提供作者在线设备列表、运行监控或从流量推断的安装/业务成功率。
- 原因：自动遥测和远程舰队管理会引入身份、隐私、服务成本、误导性指标和本地优先冲突；首版更新与消息并不需要平台观察终端业务。
- 后果：客户端灰度不自动暂停、扩大或回滚；本机启动健康恢复只影响当前设备。项目显式调用 HTTP/API 或消息发送业务数据仍按其函数契约与权限执行，不被误称为平台遥测。未来若需要设备管理，必须独立完成授权、隐私、服务端和 Harness 规格。

## ADR-042：HTTP 文件上传与下载使用独立流式原子能力

- 决定：首版在普通文本/JSON HTTP 请求之外，分别提供 multipart 文件上传和文件下载原子能力。上传只从已授权的可读 `FileReference` 流式发送有序文本/文件字段；下载只向已授权的可写 `FileReference` 写入，先落入受控临时文件，完整成功并刷新后再原子提交。Windows 与 Android 使用同一上层契约和结果语义。
- 原因：截图、配置、模型和业务文件的传输是通用自动化场景，全部交给扩展会重复实现；把文本、JSON、文件、任意二进制和流回调塞入一个万能请求又会使 Control、返回类型、内存、权限和失败恢复难以理解与验证。独立函数可以复用同一 HTTP 传输层，同时保持用户意图、文件授权和原子写入边界清晰。
- 后果：文件内容不进入 ProgramDocument、项目变量、普通日志或一次性整块内存；发布器分别闭包网络、上传读取和下载写入权限。普通请求拒绝文件/二进制正文，上传和下载不自动重试可能已经产生远端副作用的操作。原始二进制值、任意流对象、分片/断点续传协议和浏览器 DOM 不因本决定进入首版。

## ADR-043：应用与 Windows 窗口控制进入官方核心但不开放通用命令执行

- 决定：首版官方函数提供 Windows 宿主直接启动受约束应用、等待该进程退出，以及立即查找/等待、激活、关闭和读取 Windows 窗口位置、尺寸、可见性与前台状态。应用启动只接收类型化应用引用；Windows 变体的参数列表只作为 `CreateProcess` 参数向明确 `.exe` 传递，不接受 Shell 命令文本，也不允许把 PowerShell、命令解释器或脚本宿主作为通用系统命令入口。Windows→ADB 变体首版只接受包名和可选 Activity，不把自由文本参数拼入 `adb shell`；未来 Intent extras 需要单独的强类型键/类型/值契约。启动模拟器后继续操作 ADB 使用“启动应用—等待目标上线—进入 `target_scope`”的普通组合。
- 原因：启动软件、等待窗口和切换模拟器是 Windows 自动化的基础舒适区，全部交给扩展会让普通项目重复建设；开放任意系统命令又会绕过函数契约、权限、平台检查、Player 发布和安全审计。
- 后果：应用/窗口函数逐项声明 Windows 平台、权限、返回、正常无结果和异常；Android APK 不显示或编译这些函数。特殊系统管理继续由显式扩展承担。平台不得新增与应用启动、目标等待和目标作用域同义的“模拟器流程”第二语义。

## ADR-044：视觉默认取新帧并区分正常无结果与异常

- 决定：普通图像/OCR调用在开始执行后从当前目标取得新帧，不隐式复用上一调用截图。需要同一时刻分析多个特征时，项目显式取得不可变 `frame_ref` 并传给多个视觉调用；帧及其结果携带来源 `target_id` 和目标空间版本。立即查询未命中和等待图片、文字、控件或窗口到期返回正常明确空结果；资源缺失、权限不足、目标断开、平台不支持和驱动/扩展崩溃返回结构化异常。
- 原因：默认新帧符合普通用户对“现在查找”的理解；显式帧同时保证多项判断来自同一画面并避免重复截图。把未命中当异常会迫使正常分支滥用异常处理，把真实故障当空结果又会掩盖不可恢复错误。
- 后果：`frame_ref` 只在当前运行内作为局部有类型值存在，不能成为图片资源、项目变量默认值或 Player 字段。多个调用使用同一帧时不得偷偷重取；空间结果不能跨目标静默使用。日志、条件、异常区域与 Harness 分别验证正常空结果和失败异常。

## ADR-045：官方函数使用稳定契约锁和显式迁移

- 决定：官方函数规范显示名采用 `命名空间.动作`，别名只用于搜索与帮助。每个函数具有稳定 `function_id`、契约版本和行为契约指纹；项目在 `easycode.lock` 中锁定精确版本/指纹。兼容改进可以保留主版本，破坏输入、返回、结果/异常边界、副作用、权限、平台或默认行为必须产生新主版本；任何更新或迁移都由开发者明确确认，打开项目不得静默升级。
- 原因：显示名、分类和实现会演进，若以名称或当前安装版本执行，同一项目会在不同机器或不同时间产生不可复现行为。精确锁与显式迁移让影响可审计，也允许官方目录持续改进。
- 后果：迁移必须展示 ProgramDocument、Player、平台和发布闭包影响，并以可撤销项目事务更新结构与锁；失败保持旧项目可构建。安全稳定的参数才拥有默认值，资源/路径/目标/选择器等必填项保持 `unset`。每个函数分别声明 Windows、ADB、Android 本机和无目标支持矩阵。弃用不删除已有项目的兼容构建路径；标准函数只有通过多个独立真实项目和等价性 Harness 后才能正式提升。

## ADR-046：重试是异常区域的可选策略

- 决定：ProgramDocument 不增加独立 `retry` 语句、`重试.*` 函数，也不给普通函数复制通用重试参数。现有异常区域可以携带可选 `retry_policy`；策略缺省关闭，开启时默认首次失败后最多再试 2 次、固定间隔 500ms，只处理函数契约标记为瞬时的结构化异常。稳定异常契约至少包含异常 ID 和 `transient / permanent` 分类，未知异常默认永久；正常无结果、HTTP `4xx/5xx` 正常响应、取消和停止不触发重试。
- 决定：每次重试从异常区域主体第一条语句开始，不恢复运行快照，也不回滚变量、输入、消息、网络或文件副作用。失败尝试期间不执行捕获或最终分支；重试耗尽后只把最后异常交给现有捕获分支，没有匹配时向上传播，最终分支在整个区域离开时只执行一次。暂停不是异常，暂停期间冻结当前尝试或剩余间隔，继续后恢复同一现场。
- 决定：区域包含直接或传递副作用时，IDE 必须列出风险并取得作者显式确认。确认绑定规范化区域主体和 `easycode.lock` 中相关函数契约指纹；主体、引用函数或契约变化后自动失效。消息、更新和远程派发的内部幂等技术重试继续由各自服务契约治理，不成为用户程序重试。
- 决定：审核指纹是 Program Service 生成的受信任事实，不是客户端可写字段。客户端通过 `review_retry_risk` 只提交异常区域 ID 和预期 revision；服务端验证策略与副作用、计算指纹、原子保存新 revision，并纳入普通撤销/重做。未审核或审核失效的文档仍可保存和编辑，但 Compiler Service 必须用 `PGM-TRY-003` 阻止编译、运行和发布。
- 原因：多条语句需要共享明确的异常恢复行为，但新增平权重试语句或在每个函数中重复参数会扩大用户概念并制造不同语义。把策略收进现有异常区域可以复用捕获、传播、调试和取消边界，同时让正常未命中继续使用条件/循环。
- 后果：ProgramDocument、函数错误契约、ECIR、检查器、日志和 Harness 必须同步支持策略、异常分类和审核失效。每次实际副作用调用使用新的操作 ID，日志记录区域、尝试序号、异常和耗尽状态；平台不能宣称重试具有事务回滚或外部幂等保证。

## ADR-047：完整帧录制与离线分析属于首个正式版本

- 决定：首个正式版本必须在 Windows、ADB 与 Android 本机完成目标帧录制、时间线浏览、历史帧比较、官方图像/OCR 离线分析、历史帧 Capture、数据管理与显式导出闭环。像素帧不承诺重建 UIA/Accessibility 控件树；第三方扩展回放在具备独立能力隔离前不进入首版。录制默认关闭，Player 只能由终端用户主动开启或确认到当前运行方案 revision；更新不能静默开启。回放不重新执行 ECIR、输入、文件、消息、网络或其他外部副作用。
- 原因：完整历史画面可以稳定复现视觉问题、调试动态列表和从已消失现场重新采集资源，属于复杂脚本开发与交付后的关键诊断能力。若只保留失败截图，时序变化和此前画面无法重建；若把“回放”理解为重跑整个脚本，又会产生不可接受的外部副作用和伪确定性。
- 后果：增加版本化录制会话、目标片段、不可变帧、标记、分析运行和按内容寻址的 `AnalysisInputBundle`，以及 Recorder/Replay 应用服务与独立工作区。分析快照保存可重现所需的实际依赖字节，清理后相关报告明确降级；默认导出排除快照，高级可重现导出逐类披露项目逻辑、资源、模型和参数。全部帧、变化帧和诊断三种策略都必须有有界缓冲、磁盘保护、丢帧证据和明确终态；录制默认本机保存，不进入项目、Git、`.ecplayer`、APK 或在线更新，也不自动上传。三平台真实宿主、性能、隐私、导出与损坏恢复未通过 Harness 前，首个正式版本不得放行。

## ADR-048：首版目录能力包含受约束的递归删除

- 决定：首版 `目录.*` 固定提供存在、创建、列出、复制、移动、删除空目录和递归删除。递归删除使用独立 `目录.递归删除` 函数及独立权限，不复用 `文件.删除`、空目录删除或布尔模式；只能接受获得对应能力的精确 `DirectoryReference`，不得接受普通路径、通配符或从父目录推导授权。
- 决定：作者必须在 IDE 审核递归删除调用和权限；IDE 调试与 Player 的每个实际执行宿主还必须把危险确认绑定到稳定语句/参数、用户明确选择的 `authorization_root_id`、执行配置 revision 与函数契约指纹。派生引用只能缩小到授权根内；任何绑定或契约变化都会使确认失效。平台始终拒绝根目录、用户主目录和宿主保护根，逐项防止符号链接、Windows 重解析点或 Android Provider 越出授权树。危险确认是每次执行前的短期事实，不写入运行方案或计划；定时任务不得在无人确认时自动执行递归删除。
- 原因：目录树的创建、搬运与清理是通用 Windows/Android 自动化能力，完全交给扩展会重复实现；递归删除又具有不可回滚和部分完成风险，若隐藏在普通删除参数中容易误用并绕过 Player 授权。
- 后果：`DirectoryReference`、函数契约、ProgramDocument/ECIR 权限闭包、作者风险确认、IDE/Player 实际授权根确认、发布报告和 Harness 必须共同承接危险能力。复制、移动和递归删除返回完整或部分完成报告，不宣称事务回滚；目录复制/移动只允许报错、跳过或自动重命名，不能合并或覆盖既有目录。宿主无法验证授权边界或删除语义时在执行前拒绝。ADR-013 中“目录以后再扩充”的旧范围由本决定替代，但不重新引入 `存储.*`或`租约.*`。

## ADR-049：扩展使用版本化清单、可信本地代码与密封发布产物

- 决定：扩展唯一清单固定为 `easycode-extension.json`，项目解析结果固定进入 `easycode.lock`。清单分别声明宿主变体与可操作目标、贡献点、依赖、权限、网络、数据 Schema、许可证和构建产物；安装范围、项目启用状态和本机信任决定不由扩展自我声明。锁文件固定清单/产物哈希、发布者密钥指纹与信任模式、精确依赖、所选宿主变体和函数契约版本/指纹。
- 决定：Python/原生可执行扩展是用户明确批准的可信本地代码。Worker 只承诺生命周期、取消、超时、序列化、日志和崩溃隔离，不承诺抵御恶意代码读取同一操作系统账号资源。权限声明用于平台 API 执行、审计与发布闭包；未经可信代码批准的第三方包只能使用不执行扩展代码的声明式安全贡献子集。
- 决定：开发态可以运行已明确信任的源码入口；发布器只接受已构建、哈希、签名和锁定的密封运行产物。`.ecplayer`、Windows Bundle 与 Android APK 不得包含扩展源码、测试、构建脚本或外部 IDE 配置。密封产物用于不可变交付和源码隔离，不宣称防逆向或 DRM。
- 原因：旧 `capability.json + Python Worker` 不能表达跨宿主变体、贡献点、发布者信任和可重现发布，也把故障隔离误当成恶意代码沙箱。仅复制扩展目录还会把源码泄漏给终端并让开发机依赖静默进入发布物。
- 后果：Extension Service、Compiler、Publisher、Bundle Loader、Windows Worker 与 Android Loader 必须消费同一清单/锁契约。Python-only 或源码-only 扩展可以在明确受信任的开发环境调试，但没有目标平台密封变体时发布被阻止。首版不建设公开市场或任意远程代码安装。

## ADR-050：官方 v1 目录使用最小原子集合与受控标准组合

- 决定：官方 v1 目录固定为 `FUNCTIONS.md` 中列出的 60 个函数，用户按日志、等待、时间、随机、项目、目标、应用、窗口、图像、文字、输入、控件、文件、目录、网络和消息领域查找；原子/标准只作为内部实现属性。`if/loop/return/try/target_scope/listen` 是 ProgramDocument 结构，不是函数。
- 决定：平台契约分别记录运行宿主要求和当前/引用目标能力。Windows 宿主可以顺序服务 Windows 与 ADB 目标；Android 本机宿主只服务当前手机。每个函数的编辑、编译、发布和运行前检查均消费这两个维度，不使用单一“支持 Android”标签。
- 决定：页面、通用存储、租约、计划、录制/回放和任意 Shell 不进入函数目录。文件长期数据使用 `文件.* / 目录.*`，计划和录制属于宿主控制面，页面能力未来重新立项。用户程序重试只使用 ADR-046 的异常区域策略。
- 原因：最小且完整的原子边界可以避免同义函数和隐藏执行机制；少量经过等价性测试的标准组合又能消除识图等待、点击等高频样板。拆分宿主与目标后，Windows→ADB 串行切换和 Android 本机交付可以共享函数契约而不伪报平台能力。
- 后果：官方注册表必须使用冻结稳定 ID、契约版本和结果类型；新增同义函数、删除目录项或改变平台/结果语义需要走函数迁移和 ADR。Harness 对目录完整性、标准函数等价性、平台矩阵与不存在禁止命名空间进行反向扫描。

## ADR-051：项目变量是每次运行的隔离会话副本

- 决定：前台只显示“局部变量”和“项目变量”。项目变量以稳定 `variable_id`、强类型、静态 ValueNode 默认值和约束保存在 `program/variables.json`；每个新运行 ID 独立复制一份可读写会话值，按“开发默认 < Player 运行方案 < 当次 IDE 临时覆盖”应用初始值，终态一律释放且不回写。
- 决定：项目变量默认值不允许保存局部/项目引用、运行结果、帧、进程、窗口、收件消息或终端文件授权。长期数据通过显式 `文件.*`，多实例数据传递通过 `消息.*`，不再增加“持久变量”、“运行上下文变量”或 `存储.*`第二语义。
- 原因：脚本必须在当前目标上重新观察外部真相，不能把上一账号或上一次运行的历史值当作当前事实。两种变量的用户模型已足以表达函数内计算、跨函数共享和 Player 初始配置，同时避免身份、生命周期和保存方式混在变量面板。
- 后果：ProgramDocument、Compiler、Runtime、IDE 检查器和 Player 表单共用同一类型/ValueNode/Control 契约。变量重命名不改稳定 ID；类型变化或删除在事务前扫描 ProgramDocument、Player 和扩展数据引用。运行方案与 IDE 临时覆盖只提供初始值，运行中修改不反向污染任何配置。

## ADR-052：目标注册表使用强类型独立 revision，ADB 只接受显式绑定

- 决定：格式 6 的目标注册表使用 `windows / android_adb / android_local` 判别式 Schema；无目标用 `null` 表示，不建立第四种伪目标。目标块继续保存在 `project.json`，但以规范化 `targets_schema_version + targets + default_target_id` 单独计算内容 revision。目标 GET、保存、解析、运行、Capture 与发布全部携带明确 `workspace_id + generation`；保存还要求 `expected_revision`，冲突不自动重试。删除目标前扫描 ProgramDocument、项目变量、资源来源和 Player 配置的稳定 `target_id` 引用并返回定位清单。
- 决定：ADB 首版持久化开发者确认的显式非空 `device_serial`。候选设备发现只帮助用户选择，不进入运行时身份推断；缺失、离线或失效时报告重连/重绑，不自动选择唯一在线设备，也不增加厂商模拟器特例。明确重绑可以更新同一目标的序列号并保留稳定 `target_id`；目标类型不能原地改变。Windows 全屏幕固定物理输入，窗口目标按显式开关决定后台失败后的物理回退；Android 本机定义不接受外部设备字段且一个项目至多登记一个当前手机目标。
- 原因：依赖全局活动工作区或运行时设备猜测会让后台标签页、多个模拟器和 Capture 回填作用到错误对象；原始字典和无 revision 保存又会静默吞字段或覆盖并发修改。按目标块独立 revision 可以避免项目其他元数据造成无关冲突，同时保持单一 `project.json` 项目事实。
- 后果：目标配置损坏会阻止项目打开或发布；Player Bundle Loader 重新验证目标 Schema 与 revision。ADB 端口或序列号变化需要一次可见重绑，不能用“当前唯一设备”掩盖身份丢失。真实 Windows、模拟器和 Android 本机仍分别按 `TARGETS.md` 与 Harness 验证，自动测试不能替代宿主证据。

## ADR-053：函数可用性以逐平台支持与实现证据矩阵为唯一事实

- 决定：每个函数对 `windows / android_adb / android_local / no_target` 分别记录产品支持状态 `supported / conditional / unsupported` 和实现证据 `verified / planned`；条件支持必须引用稳定能力 ID。单一 `implementation_state` 仅作为“至少一个平台 verified”的派生兼容摘要，不再参与编译或发布判断。
- 决定：函数目录只展示至少一个平台 verified 的契约，并同时返回完整平台详情。Compiler、Publisher、Runtime adapter 与运行前检查消费同一矩阵：指定平台必须 verified；未指定平台的 ECIR 只声明依赖闭包共同 verified 的平台。unsupported 与 planned 分别产生“不支持”和“尚未验证”诊断，不能到执行阶段伪成功。
- 原因：Windows/ADB 已有实现而 Android 本机尚未完成时，单一 available/planned 会在“隐藏可用 Windows 函数”和“虚报 Android 可用”之间二选一。把产品支持意图和当前验证证据拆开，才能让函数提前进入已验证平台目录，同时保持发布结论真实。
- 后果：当前纯函数、目标/视觉/输入切片和文件切片只按现有 Windows/ADB/无目标自动证据标记；Android 本机保持 planned，直到签名 APK 在断开 IDE、后端和数据线后通过真机 Harness。平台矩阵进入契约指纹与项目锁，改变支持状态、条件能力或验证实现会触发锁差异与显式审核。

## ADR-054：Windows Runtime 以目标栈串行执行 `target_scope`

- 决定：Compiler 把 ProgramDocument 引用到的强类型目标定义与稳定 `target_id` 锁入 ECIR 闭包。Windows Runtime 为每个运行维护一个逻辑目标栈：进入作用域时在取得独占使用权并验证首帧后才提交切换，退出、异常或取消都弹栈恢复上一逻辑目标并释放作用域驱动。嵌套进入栈中已存在的目标可复用其驱动，但仍需验证当前帧后才执行子语句。
- 决定：单运行实例任意时刻只有一个当前目标，不为 Windows 与 ADB 建立并发操作流。恢复是逻辑驱动恢复，不激活或恢复旧前台窗口。Android 本机宿主不能通过该机制进入 Windows/ADB，Windows Runtime 也不能进入 `android_local`。
- 原因：顺序启动模拟器后转入 ADB 是常见脚本场景，但并发驱动会让坐标来源、物理输入、缓存和故障恢复失去唯一当前目标。目标栈在不增加第二套模拟器语义的前提下承接嵌套恢复。
- 后果：缺失/重复目标闭包、跨宿主目标、忙目标和首帧失败使用稳定诊断且不执行作用域主体。自动化假驱动证据不替代真实 Windows/模拟器冒烟；Capture Session 切换协调、跨目标空间值阻断、Recorder 分段和真实 ADB 中途断连仍按 `TARGETS.md` 完成门验证。

## ADR-055：格式 5 源码链退役且不保留影子编辑路径

- 决定：格式 6 只通过 ProgramDocument Repository、Program Service、结构命令和 Compiler Service 编辑与构建项目函数。旧 `.easy` Source、文本解析/语义编辑、源码编译、旧函数文件服务、页面导航与拓扑实现从当前服务注册、导入图和运行目标驱动中删除；旧 HTTP 路径只保留无状态、无副作用的结构化 `410 source_api_retired` 边界，不读取工作区、不解析请求体，也不提供迁移或兼容写回。
- 决定：IDE 断点、搜索与录制帧离线分析改用稳定 `function_id + statement_id`。回放只扫描当前入口可达 ProgramDocument 编译闭包，并对白名单内具有专用无副作用适配器的官方分析函数执行；它不恢复旧拓扑、页面节点或 `.easy` 解析。扩展目录中的 Python/原生源码仍是受信任扩展开发输入，不属于被退役的项目源码，也不能成为项目函数的第二编辑事实。
- 原因：把旧端点标成退役但继续注册旧服务，会让格式 5 状态、项目函数发现、调试和运行在后台继续成为平权事实；继续复用页面拓扑做回放则会违反首版取消页面导航的范围。最小 `410` 边界可以给遗留客户端稳定失败语义，同时证明请求不会误改格式 6 项目。
- 后果：新项目生命周期不创建 `src/*.easy`、页面模型或旧 identity/symbol 文件；活动工作区只返回 ProgramDocument、项目变量、资源和强类型目标。Harness 必须扫描旧模块/服务注册/运行 opcode，并验证所有退役路由在任意旧请求体下均返回同一结构化 `410`；旧 `/api/frame-recording/analyze*` 页面拓扑分析同样只保留 `topology_replay_retired` 边界，录制会话、帧、缩略图和历史 Capture 存储接口继续可用。录制、OCR、UIA、扩展、资源、Player 和当前 Runtime 是独立能力，不能因删除旧页面/源码链而被顺带删除；尚未具有专用回放适配器的官方 OCR 契约继续标记未验证，不得由旧页面分析伪装完成。

## ADR-056：枚举参数由单一契约定义并按当前目标收束

- 决定：函数枚举参数的中文标签、稳定值和可用平台只在函数契约中定义，进入契约指纹；IDE、Player、Compiler 与 Runtime 不维护第二份选项表。每个 `select` 参数必须具有非空、值唯一的选项，并且默认值必须属于选项集合。平台专属选项携带明确 `platforms`，固定字面值在当前默认目标或 `target_scope` 下不兼容时由 Compiler 阻止；Runtime 驱动继续对动态值和损坏包做防御校验。
- 决定：Windows 文本输入支持 `auto / background / physical`，ADB 与 Android 本机支持 `auto / target`。`auto` 在 Windows 优先后台输入，仅当桌面目标或目标允许物理回退时才使用物理键盘并记录后台失败原因；`background` 失败不得偷偷回退；显式 `physical` 仍受目标物理输入权限约束。Windows 桌面固定允许物理输入。ADB/Android 的 `target` 表示目标宿主原生输入，不占用 PC 物理键盘。
- 原因：此前多个参数声明为下拉框却没有选项，前端只能降级为文本；Windows/ADB 选项混放又会让用户保存运行时必然失败的组合。单一契约同时解决表单可用性、平台提示、编译正确性和 Player 复用，避免相同枚举在各端漂移。
- 后果：切换目标后，只展示当前平台可选项；若已有值不兼容则原位显示禁用说明，不能静默改默认。右键、滚轮、物理键盘等平台专属选择必须通过对应真实宿主 Harness；自动化只证明契约、过滤、编译和驱动分支，不能替代真实 Windows/ADB/Android 输入证据。

## ADR-057：Approved 官方目录逐项约束实现稳定 ID

- 决定：[`docs/vnext/FUNCTIONS.md`](vnext/FUNCTIONS.md) 第 5 节的 60 个“规范显示名 → `function_id`”映射是官方 v1 唯一身份事实。注册表、ProgramDocument、ECIR、Runtime、Replay、Player 和测试必须逐项完全一致；Opcode 只是实现分派键，不能替代或反向定义公共函数身份。自动测试直接解析 Approved 表格并与完整注册表做集合与映射全等比较。
- 原因：实现过程中曾出现 14 个命名漂移，例如 `official.vision.find / official.image.find`、`official.log.write / official.log.output`。显示行为相同并不能抵消稳定引用、Player 绑定、项目锁、回放和扩展依赖的分裂；若继续在两套 ID 上开发，后续每个切片都会扩大迁移成本。
- 后果：格式 6 尚未交付旧项目兼容，因此本轮直接统一到 Approved ID，不保留别名、双读或迁移层。未来任何稳定 ID 变化都必须产生新契约主版本、显式迁移与独立 ADR，不能只改注册表或帮助文档。别名仍只用于函数库搜索，不进入持久化或发布产物。

## ADR-058：Player Schema 3 只开放已签名且可执行的稳定槽

- 决定：Player Schema 3 只允许 `project_variable / function_parameter / statement_parameter / function_action / setting` 五种判别式绑定。函数、语句、参数、变量和目标只使用稳定 ID；`statement_parameter` 可以绑定静态根参数，也可以携带 Compiler 已签名的稳定 `value_id` 覆盖动态表达式中的非重叠静态子值，`setting` 必须绑定具体 `target_id`。每个非按钮控件保存后端生成的 `source_type + type_fingerprint`，指纹覆盖权威来源类型和约束。旧 `variable`、`parameter_name` 补全、根级 `bindings` 和 schema 2 不兼容、不迁移、不双读。
- 决定：IDE Player 设计器只能通过后端生成的工作区绑定来源目录创建字段。目录包含稳定层级、绑定、推荐 Control、默认值、约束和指纹；前端不复制哈希算法，也不从标签或可见参数名推导身份。保存、发布、运行方案保存和每次运行都复验引用、类型指纹、来源约束、控件约束、重复绑定、目标作用域和失效状态。方案校验失败保留旧方案；目标设置以 `target_id -> setting_id` 隔离。
- 决定：嵌套 `value_id` 只接受 Compiler 生成并随 ECIR revision/发布签名锁定的 override slot；绑定身份使用 `function_id + statement_id + parameter_id + value_id`，ECIR 内部路径不成为作者契约。Runtime 只写本次任务的 ECIR 深拷贝，未知、过期、类型不兼容和结构注入继续由 `PLY-BIND-010/012` 阻止。专用 `resource` 和专用 `target` 绑定在各自完整闭环与真实 Harness 完成前仍使用 `PLY-BIND-011` 拒绝，前端不得展示假入口。IDE 预览必须走同一编译、绑定、目标覆盖和 Runtime 启动链，不回退格式 5 源码运行。
- 原因：显示名补全和前端自行计算类型会在重命名、约束变化与同名参数下写错值；一次性开放没有编译器槽的嵌套/资源/目标绑定只能形成“可保存但不执行”的半成品。先冻结最小真实闭环，可以保留完整未来上限，同时让每一个当前入口都具有后端、发布和 Player 承接。
- 后果：新项目直接创建 schema 3 空表单。Binding Contract 必须同时公布 schema、判别式字段、`statement_parameter.value_id` 可选字段、指纹契约、真实目标设置和明确未支持项；Binding Sources 是设计器唯一来源。静态根与动态表达式子槽按“最大非重叠静态子树”生成，避免父子覆盖顺序歧义。未来资源/目标槽仍必须逐项完成 `PLAYER.md` 的签名槽验收并新增决定，不能复用普通值槽偷偷放行。

## ADR-059：`.ecplayer` format 2 使用作者 Ed25519 身份与全文件完整性清单

- 决定：无签名 `bundle_format: 1` 不再加载。格式 6 Publisher 输出 `bundle_format: 2`，为清单、ECIR、目标配置、Player Schema、发布报告和每个资源生成大小与 SHA-256 记录，并以作者的 Ed25519 私钥签署规范化完整性清单。Loader 在解压和创建任务前拒绝无签名、重复路径、未列入清单、大小/哈希错误、签名错误、清单身份不一致和固定信任根不匹配的包。
- 决定：每个 `product_id` 的作者私钥保存在项目目录之外的当前 Windows 用户 DPAPI 边界，项目、Git、`.ecplayer`、Windows Bundle、日志和服务器都不得包含私钥。通用 Player 运行时由交付组装器同时固定该产品的公开信任根；命令行生产启动要求显式信任根。直接打开 `.ecplayer` 的开发验证可以读取包内公钥验证内容一致性，但只有与外部固定信任根匹配的已组装 Player 才具有发布者身份保证。
- 决定：`release_id` 由发布输入内容记录确定性派生。Publisher 在替换上一个产物前重新打开临时 ZIP 并使用同一 Loader 验证签名和所有文件，外部程序在发布过程中改动资源会使本次发布失败并保留旧产物。交付目录同时保存公开 `trust-root.json` 与签名/版本摘要；这不是商业授权或 DRM。
- 原因：仅验证 ZIP 结构或把公钥和签名一起放入包内只能发现普通损坏，无法阻止攻击者替换公钥后重签；只给 ECIR 算哈希又会漏掉被替换的表单、目标或资源。作者身份、全文件清单、外部信任固定和覆盖前自验构成最小完整交付链。
- 后果：旧无签名测试包必须重新发布，不提供格式 1 兼容加载器。Windows 独立 Player 启动参数携带由交付目录固定的公开信任根；未来内容更新、灰度策略、密钥轮换、吊销和 Android APK 仍须遵守 `UPDATES.md` 的 TUF 风格角色化元数据，不得把当前单产物签名冒充完整在线更新系统。

## ADR-060：Player 字段动作只写入已保存的 revision 方案

- 决定：Player Schema 3 的每个非按钮 Control 显式保存 `terminal_actions`，缺省规范化为空集合。每个动作及平台必须是字段和权威来源 `parameter_ui.actions` 的合法子集，Publisher 将该闭包写入已签名发布报告，Loader 重算并拒绝不一致产物。终端动作只允许写入已保存且具有稳定 `profile_id + profile_revision` 的方案，不为草稿伪造临时身份。
- 决定：`PlayerControlDestination` 精确绑定产品/项目、发布、方案、Control、动作、方案 revision 和目标。Player 在启动与确认两个边界重新验证全部身份，一个进程只有一个活动会话。Player Capture 使用 `workspace_kind=player` 与专属路由复用原生宿主，不借用 IDE 当前 Workspace 或 Execution 身份。方案保存与 Capture 确认原子地使 revision 加一；图片候选只在确认后进入当前方案的私有覆盖，取消或失败保留旧值。
- 原因：临时草稿身份、IDE 全局 Workspace 或只在前端隐藏按钮都不能防止过期/跨字段回填和权限绕过。签名最小权限闭包与持久方案 revision 让启动、宿主返回和原子写入共享同一个不可混淆的身份。
- 后果：旧或缺省 `terminal_actions` 的表单等价于全部关闭；旧方案文档可规范化为单调 revision Schema，损坏文档必须显式失败。Windows/ADB 的点、区域、图片和手势路径可复用当前驱动；控件捕获只在 Windows 原生宿主真实支持时开放。Android 本机原生步骤流、系统权限恢复与真机证据仍是独立完成门，不得由 Windows/ADB 切片冒充。

## ADR-061：Android 首版工具链、ABI 与 release 签名边界

- 决定：本条原定的固定 `minSdk 26` 已由 ADR-083 取代；`compileSdk 37`、`targetSdk 37`、ABI 与签名边界继续有效。正式通用 APK 只包含 `arm64-v8a` 与 `armeabi-v7a`；`x86_64` 仅作为独立的开发/模拟器测试产物，不并入正式通用包。
- 决定：release 构建只从项目目录之外的 keystore 或 CI secret 取得签名身份。仓库不保存正式私钥、默认口令或可发布凭据；缺失配置时 release 必须明确失败，不得退回 debug 签名。本地 debug 只用 Android 工具链的开发签名边界。
- 决定：没有真实原生依赖的纯 Kotlin/JVM 候选 APK 是架构中立产物；flavor 的 `abiFilters` 仅证明构建配置隔离，不证明 APK 已形成正式 ABI 闭包。不得为制造 ABI 标签加入假 JNI。正式 ABI 验收必须随实际 OCR、图像或扩展 native 依赖和 NDK 一起检查 APK 中的真实库条目，并精确覆盖 `arm64-v8a + armeabi-v7a`。
- 原因：API 下限影响 MediaProjection、SAF、Accessibility 与前台服务的兼容分支；ABI 集合直接影响 OCR/图像原生库、扩展闭包和 APK 体积；把 release 密钥或口令放入项目会违反发布私钥不进入项目/Git/产物的既有信任边界。
- 后果：Gradle/Manifest、原生依赖和 `ecx-runtime-1` Android 变体必须同时通过 API/ABI 预检。Harness 以 `AC-AND-BUILD-001` 验证 SDK 基线、正式/开发 ABI 隔离、真实 native 闭包、release 缺失外部签名时稳定失败、debug 可重复构建和产物不含密钥/口令。纯 JVM 候选保持 release readiness 阻塞；真机权限、输入、帧、离线和性能仍由原 `AC-AND-*` 闭环放行，自动 Gradle 构建不能替代真机证据。

## ADR-062：v6 在线更新采用独立产品域、签名静态 Feed 与显式平台安装边界

- 决定：IDE、Player 应用和项目内容是三个独立更新产品域，分别持久化信任根、已见元数据版本、强制策略、安装分组码、偏好和 A/B 状态。项目根 `updates.json` 只保存作者发布配置，不进入 `ProgramDocument`；只有作者启用对应产品域时，Publisher 才把经过 `.ecplayer` format 2 完整性清单覆盖的 `update/config.json` 放入 Bundle。全部关闭时不得把端点、身份、调度器或终端入口带入产物。
- 决定：官方托管与自建源共用同一开放静态 Feed 布局和签名对象：`<product_id>/<domain>/metadata/` 保存根、时间戳、快照、目标、灰度与强制策略元数据，`artifacts/<release_id>/` 保存不可变产物。仓库参考服务只负责 HTTP GET/HEAD、ETag、Range 与缓存语义，不持有发布私钥，不实现伪账号、VIP、授权、设备舰队或遥测。未连接真实官方提供方时，官方托管发布动作必须返回明确 `unavailable`，不能把本机目录冒充官方云。
- 决定：信任根轮换必须同时满足旧根与新根阈值，在线角色轮换后重新签署当前元数据；更新源或镜像迁移只能来自已验证根元数据。内容发布固定 Bundle `release_id` 并拒绝 Runtime、权限、ABI、宿主或原生代码指纹变化。Windows 应用包与 Android APK 只进入已验证暂存和平台安装等待状态；缺少真实安装助手或 PackageInstaller 承接时保持 `awaiting_platform_install` 并明确不可用，不以文件复制伪装安装成功。
- 原因：把更新配置并入可编辑程序事实会污染格式 6 单一事实源；动态定向 API、长期在线单密钥或可编辑 URL 会分裂官方/自建协议并削弱离线验证；通用 Python 进程无法安全替代 Windows 原子安装助手或 Android 系统安装确认。独立产品域、角色签名静态对象和显式平台边界可使关闭、离线、灰度、回滚与失败语义在所有宿主保持一致。
- 后果：客户端关闭时不创建产品身份且不调用任何传输；任务启动时固定三个产品域的 `release_id`，运行/暂停或未提交表单期间只允许暂存。强制策略使用独立低频检查，只在可信宽限期结束后阻止新任务。真实 Windows 安装助手、Android PackageInstaller、官方托管账号/配额和外部 HTTPS/CDN 仍必须在对应宿主 Harness 单独放行，自动化协议测试不能替代这些证据。

## ADR-063：独立 Windows Player 使用专用进程、路由与前端发布图

- 决定：Windows Player 不能从 IDE 的 `api.app` 或完整 vNext Router 派生。冻结入口先分派 capability/extension worker 与 Player Hub agent；普通分支必须解析、校验并提交 `.ecplayer + 外部信任根` 后才导入 Player 应用、Bundle Loader 或 Runtime。专用应用只监听 loopback，并由显式 OpenAPI allowlist 组合签名包运行、运行控制/诊断、最小 Capture、终端录制会话查看/导出/删除，以及终端更新、计划、Hub、LAN 管理路由。
- 决定：Player Runtime Router 不依赖 Workspace Manager、Compiler/Publisher、Program Service 或 legacy Execution/Capture/Replay。终端 Capture 的 HTTP 面只保留 SSE、字段动作/ACK 与关闭；会话注册、目标截图和宿主触发由已验签 Bundle Manager 内部调用。`core.vnext` 根包使用惰性导出；密封扩展调用拆为不含开发态发现/签名/Workspace 的发布运行模块；PyInstaller 清单显式列出运行闭包且禁止整包收集旧节点执行器、条件、参数、legacy Player、作者扩展服务或 `core.vnext`。
- 决定：Player Web 使用独立 Vite 图，仅产出 `player.html` 与轻量 `capture.html`。Assembler 只接受该目录和冻结 Runtime 模板，并在验签、组装前后拒绝 IDE `index.html`、项目 `src`、前端源码、EasyCode/作者 Python 源、source map、`.easy`、`programs/`、`program.json` 或 ProgramDocument；冻结 Runtime 的 `_internal` 可保留运行必需的第三方 Python 支持文件与依赖许可证。源码进程、普通浏览器或自动化文件清单不能替代无系统 Python、无 IDE/后端的真实 Windows Bundle 冒烟。
- 原因：HTTP 隐藏菜单、PyInstaller `excludes` 或打包后人工抽查都不能证明作者能力和可编辑事实没有进入产品。把启动顺序、路由闭集、导入图、Web 构建图和交付文件清单同时固化，才能让最小权限、外部信任固定和离线独立运行成为可执行边界。
- 后果：新增 Player HTTP、动态运行模块或静态入口必须先更新 `PUBLISHING.md`、精确 allowlist、导入/文件清单测试和 Harness；IDE/legacy 依赖回流直接视为发布失败。正式 PyInstaller 产物、WebView2/原生 Capture、OCR、扩展 worker、计划/LAN 与离线网络仍需在真实 Windows 主机串行验证，未执行时只能标记未验证。

## ADR-064：业务反馈留在 EasyCode 产品表面

- 决定：IDE、Windows Player、Android Player 和原生 Capture 宿主的业务成功、失败、确认、取消和可恢复警告必须使用 EasyCode 的 Dialog、Toast、就近错误或窗口内 Notice。禁止使用 Windows `MessageBox`、浏览器 `alert / confirm / prompt` 或其他宿主默认提示框承接产品反馈。
- 决定：文件/目录选择、Android 权限/设置与 APK 安装是操作系统拥有的授权边界，可使用系统界面。系统界面返回后不重复询问，结果、失败原因和恢复动作仍由 EasyCode 承接。
- 原因：宿主默认弹窗会分裂品牌与键盘交互，且无法承载稳定错误码、恢复动作和上下文；而文件授权、Android 权限和平台安装必须交给安全边界的所有者。
- 后果：Harness 静态扫描产品代码中的默认提示框调用，并在真实 Windows/Android 宿主上验证确认、取消、失败和焦点恢复。系统选择器和权限页作为明确例外单独验收，不作为统一对话框实现的绕过口。

## ADR-065：捕获层展示位置与目标坐标空间分离

- 决定：Windows 目标使用真实屏幕客户区作为捕获层展示区域；ADB/Android 虚拟帧没有 Windows 屏幕位置，使用当前显示器安全工作区内的等比居中展示。展示区域、原始帧尺寸和目标坐标空间分别传递，确认时由捕获宿主把显示坐标反算为原始帧坐标。
- 原因：把 ADB 帧的 `[0, 0, width, height]` 当作 Windows 屏幕矩形，会在多显示器和高分辨率设备上产生错误跨屏拒绝，并让采集值落入宿主坐标而非设备坐标。
- 后果：点、区域、路径和图片裁剪测试必须同时覆盖 Windows 对齐、ADB 真机/模拟器缩放、多显示器以及原始帧边界；仅验证捕获层出现不算闭环通过。

## ADR-066：Windows 与 Android Player 共用编译后的渲染层，平台能力留在原生宿主

- 决定：Windows Player 与 Android Player 使用同一份编译后的 Vue Player 页面、Control Registry、字段校验、设计令牌和交互状态模型。桌面与移动端不是两套页面，也不是按比例缩放：同一组件根据宿主能力、视口、安全区和输入方式投影为桌面“表单 + 运行区”或移动端单列、触控友好的布局。
- 决定：平台系统能力不进入 Web 渲染层。Windows 继续由专用本地 HTTP/原生 Capture 宿主承接；Android 由最小权限 Host Adapter 承接 MediaProjection、AccessibilityService、SAF、系统权限、前台服务、APK 更新和全屏捕获确认页。Android WebView 只加载 APK 内离线静态资源，禁止外部导航和任意网络；消息桥使用版本化请求、固定方法白名单、结构化结果和稳定错误，不向脚本开放文件系统、输入或未签名资源。
- 决定：Android 捕获层继续原生实现。点、区域、图片和路径在全屏原生确认页完成；文件/目录交给系统选择器。系统返回后由 Host Adapter 原子更新当前 `profile_id + profile_revision + control_id`，共享页面重新取得权威方案，取消或失败保留旧值。若系统 WebView 不可用，只显示原生启动/恢复错误页，不保留第二套完整表单作为降级实现。
- 原因：此前 APK 以原生 Kotlin 重写整套表单，只复用 Schema，没有复用 Control 和页面实现，导致视觉、交互、可访问性及新增字段能力持续漂移。共享渲染层可以让开发端预览、Windows Player、模拟器内 APK 和手机 APK 使用同一事实与组件，同时仍把权限和高风险能力留在操作系统边界。
- 后果：Android APK 构建必须嵌入独立 Player Vite 图的无源码、无 source map 产物，并验证资源哈希、离线启动、桥接白名单和外部导航阻断。Harness 需在桌面、模拟器和真机分别验证相同表单的内容/Control 一致性、移动响应式、字体放大、安全区、旋转草稿保持及真实捕获；像素完全一致不是目标，信息架构、动作名称、值语义和状态反馈一致才是验收标准。

## ADR-067：Android 字段采集采用悬浮准备与原地冻结编辑

- 决定：Android Player 的点、区域、图片和路径字段动作不再使用通知栏倒计时或采集前全屏步骤页。用户从 Player 发起并完成必要系统授权后，Player 退到后台，仅显示可拖动贴边的 EasyCode 悬浮按钮；开始采集时宿主移除全部 EasyCode 悬浮层，等待一张产生于移除之后的原始分辨率新帧，再由同一 WindowManager 捕获层原地显示冻结画面。确认、取消、微调、遮罩、选区、准星、放大镜和短暂冻结光效只属于显示层，不进入截图像素。
- 决定：冻结层按原始帧空间编辑。点、区域和路径直接返回原始坐标；图片从原始帧按确认选区裁剪。选区外暗化、选区内原亮度，控制按钮悬浮在截图内部并避让选区/系统安全区，不创建固定标题栏或底栏。悬浮准备阶段允许目标应用改变方向/尺寸，开始时按当下显示刷新帧缓冲；冻结后再改变坐标空间才取消候选。取消、系统返回、权限拒绝、冻结后方向/尺寸变化、会话过期和提交失败均保留旧字段值，并回到共享 Player 原 Control。
- 决定：`SYSTEM_ALERT_WINDOW` 只随真实 Android 终端捕获闭包进入 APK，并在字段动作第一次需要时由用户通过系统设置授权；缺失或拒绝时不降级为通知栏交互。MediaProjection 前台服务仍保留系统要求的低打扰通知，但通知没有产品动作。一个 Player 实例仍只允许一个 Capture Session，开始和确认两端继续验证完整 `PlayerControlDestination` 与方案 revision。
- 原因：现有通知横幅、三秒倒计时和独立全屏 Activity 会遮挡目标画面、进入截图或产生明显页面切换；手机端需要一边操作目标应用一边准备字段，并在点击后几乎无感地冻结当前原始画面。悬浮准备与原地冻结可以保留系统权限、稳定身份、旧值保护和精确编辑，同时缩短高频采集路径。
- 后果：`ScreenCaptureService` 负责 MediaProjection、悬浮控制和干净帧门；旧 `CaptureOverlayActivity` 不再是默认采集入口。Harness 必须在模拟器和真机分别验证悬浮授权、贴边/展开、按钮隐藏后的无污染原帧、原始尺寸、点/区域/图片/路径、微调、方向变化、取消、系统返回、通知不弹横幅、旧值保持及回到原 Control。只有自动化或模拟器证据仍不能替代真机放行。

## ADR-068：跨平台控件统一用户语义并保留平台适配边界

- 决定：前台只存在“控件”以及 `控件.查找 / 点击 / 读取文本 / 输入文本` 四个原子函数。内部以版本化 `control_selector` 和会话内 `control_ref` 分隔持久身份与运行句柄，并由 Windows UIA、ADB UIAutomator、Android Accessibility 三个 Host Adapter 实现；provider 是内部诊断字段，不形成用户可选的三套函数。
- 决定：控件捕获在 Windows、ADB 与 Android 本机使用同一个 Capture action、强类型 Control 和原子回填协议。Windows 直接读取 UIA；ADB 在干净目标帧取点并从同一设备的 UIAutomator 快照解析节点；Android 本机在悬浮层出现前缓存 Accessibility 快照，再在冻结画面取点。操作前必须重新定位，不能持久化原生节点对象或仅靠捕获区域执行。
- 决定：SurfaceView、Canvas、游戏引擎和其他自绘页面没有有意义语义节点时返回 `control.semantic_tree_unavailable`，明确建议图像、OCR 或坐标；平台不得把屏幕根容器冒充控件，也不得偷偷降级成坐标操作。合法选择器未命中仍是正常空结果；权限、驱动、选择器和操作错误是结构化异常。
- 原因：用户需要一种可理解、可发布的“控件”能力，而不是学习三种平台 API；同时 UIA、UIAutomator 与 Accessibility 的能力、权限和树结构不同，抹平失败边界会产生假能力，尤其会在自绘游戏界面误操作。
- 后果：本决定取代 ADR-060 中“控件捕获只在 Windows 原生宿主开放”的限制，并落实 ADR-038 中 Android 只有具备真实 Accessibility 才条件显示的要求。函数平台矩阵、目标能力、IDE/Player 动作、Android Runtime、发布闭包和 Harness 必须共同承接；像素回放仍不能重建历史控件树。

## ADR-069：控件捕获采用目标内最深命中与单向父级选择

- 决定：Windows UIA、ADB UIAutomator 与 Android Accessibility 的用户交互统一为“点击最深语义控件，按父级逐层上移”。一次点击产生从最深节点到当前目标根的有序候选链；界面只提供清空、父级、取消、确认，不提供子级列表或完整树浏览器。
- 决定：Windows 候选必须从显式目标窗口的 UIA 根向下解析，不能使用屏幕 z-order 决定控件归属。整窗截图使用实际 DWM 捕获纹理作为边界，忽略 GetWindowRect 的不可见阴影/缩放边框；选择器区域与点击映射使用同一真实帧坐标空间。
- 原因：用户通过点击和父级上移即可覆盖绝大多数可选控件，同时避免“一个父节点下大量子节点”造成的歧义。目标内解析还能保证捕获微信时不会因为 IDE 或浏览器遮挡而误取外部控件。
- 后果：控件参数在检查器中使用专用摘要 Control 和直接捕获按钮，底层 Record 字段不再作为主编辑界面。自绘窗口仍只能返回真实存在的 Pane/窗口语义；内部按钮缺失时明确改用图像、OCR 或坐标。

## ADR-070：循环控制与显式失败采用核心结构语句

- 决定：ProgramDocument 增加 `break`、`continue` 与 `fail` 三种核心结构语句，中文投影分别为“跳出循环”“跳过本轮”“结束为失败”。它们不注册为官方函数，因此 60 个官方函数身份集合不变。
- 决定：`break` 与 `continue` 只在当前项目函数词法循环体内合法，只作用于最近一层循环，不能跨项目函数调用边界；嵌套条件、目标作用域与异常区域不改变目标循环，离开异常区域前仍执行最终分支。
- 决定：`fail` 保存静态稳定错误 ID、字符串消息值节点和可选 JSON 详情值节点，运行时产生永久结构化异常。它可被现有异常区域捕获；未捕获时任务失败并保留稳定定位与脱敏详情，不接受瞬时错误自动重试。
- 原因：循环内提前结束/跳过和业务主动失败是通用结构控制，不应由布尔变量、额外项目函数或伪官方函数绕行。以核心结构承接可保持投影直观、作用域可静态验证，并让 IDE、Player 与 Android 共用同一 ECIR 语义。
- 后果：Schema、结构命令、验证、编译、Runtime、Android allowlist、编辑器、检查器与 Harness 必须作为一个垂直切片交付；结构命令拒绝把循环控制创建或移动到循环外，外部损坏文档仍由语义校验阻止保存、编译、运行与发布。

## ADR-071：基础转换与几何操作采用跨平台确定性纯值契约

- 决定：纯值注册表版本 6 增加基础标量转文本、文本严格解析整数/有限小数、文本拆分/连接以及坐标/区域缩放。解析失败是可选值的正常无结果；空分隔符、非文本列表与不受支持的转换输入是稳定结构化错误。文本拆分显式保留首、中、尾空项，不依赖 Python 或 Kotlin 的宿主默认行为。
- 决定：通用转文本只接受契约列出的基础标量与枚举，不接收资源、目标、文件或其他引用对象。坐标和区域缩放除更新数值字段外，必须保留来源目标、空间版本等附加元数据，后续跨目标检查不得因纯计算丢失依据。
- 原因：脚本需要把 OCR/配置文本安全转为数值、把基础值写入日志或文件、处理分隔列表并适配不同参考尺寸；若由标准函数或各 Runtime 自行拼接，会产生隐式 `0`、空项丢失、对象内部结构泄露和跨宿主结果漂移。几何操作丢失来源空间还会在 Windows/ADB 中途切换时造成隐蔽误点。
- 后果：注册表版本与哈希变化进入编译缓存、锁定和发布签名；目录只显示类型兼容的操作。Windows 与 Android 自动契约测试必须覆盖相同输入输出、正常无结果、稳定错误及空间元数据传播；真实坐标操作仍需在目标宿主 Harness 中验证，纯值单测不能替代点击结果。

## ADR-072：值编辑采用统一结构化表达式输入器而非来源模式切换

- 决定：参数、赋值和条件的主要编辑入口投影为一个强类型表达式输入器，不再常驻“填写 / 变量 / 计算”三个用户模式。键盘文字、候选选择和聚焦表单只编辑同一 ProgramDocument 值树；未完成文字保留在本地草稿，只有解析为唯一且类型兼容的稳定节点后才能提交。
- 决定：变量和结果在候选确认后成为保存稳定 ID 的可视词元；同名或歧义文字不静默解析。核心批准的纯操作可以在输入器内组合，普通函数与任何外部状态访问仍保持独立语句；未来可以提供“插入语句并引用结果”的复合编辑命令，但不能形成隐藏调用。
- 决定：统一输入器递归用于所有自由标量值槽，包括列表项、字典键和值、结构字段及纯操作输入。列表、字典和记录继续用多行容器组织；枚举是固定的契约行为选择，只显示契约下拉且不提供变量/计算来源；坐标、区域、资源、控件和其他捕获型值继续使用专用 Control，不能为了表面统一而退化为自由文本。
- 决定：统一输入器不设置“更多操作”或第二套聚焦表单。全部已验证核心纯操作使用 `命名空间.操作(参数…)` 的类型化编辑投影，并通过键入 `@`、命名空间、`.` 或 `(` 触发值、操作、成员和参数补全；帮助按钮只在参数标题旁按需展开当前类型的写法。普通函数和 I/O 仍不能嵌入。
- 决定：编辑前后复用同一输入外壳，不增加确认、取消或常驻操作行。单行使用 Enter/Escape/有效失焦，多行使用 Ctrl+Enter/Escape/有效失焦；无效草稿不得覆盖已提交值。顶层普通文本无需引号，纯操作参数中的文本使用成对引号消除语法歧义；中文标点只在字符串外规范化。
- 原因：来源三分法暴露了实现结构并迫使普通用户在知道目标值之前先理解内部模式；纯自由公式又会破坏重命名、类型诊断、稳定绑定和跨平台确定性。结构化输入器同时保留直接输入的效率与 ProgramDocument 的单一事实。
- 后果：IDE 需要提供词元投影、注册表驱动的函数/成员/参数补全、标题帮助、草稿错误、键盘路径和可访问性；Harness 必须验证文字不会成为第二事实、引用重命名不损坏、歧义不误绑、列表/字典叶子递归复用、枚举约束不丢失，以及全部注册纯操作都能通过输入语法往返。Player 仍只覆盖签名值槽，不获得修改表达式结构的能力。

## ADR-073：Program 快照按引用携带权威展示元数据

- 决定：ProgramDocument 继续只保存稳定操作、输入槽、记录类型和字段 ID。Program Service 的加载、结构命令、撤销和重做快照必须从核心权威注册表按当前文档实际引用内容附带展示元数据，包括中文操作短名、规范 `命名空间.动作` 名、中文参数名、记录类型名和字段名。
- 决定：结构化语句、检查器、统一输入器、Player 设计器和调试表面复用同一展示契约，不在前端硬编码第二份映射，也不通过拆分 `core.*` 等稳定 ID 猜测用户名称。展示契约缺失时显示“不可用计算 / 不可用字段”并产生可定位诊断；内部 ID 只允许出现在复制 ID、诊断详情和开发日志中。
- 原因：稳定 ID 适合持久化、绑定和迁移，但不是用户文案；仅在输入候选目录中提供中文名会导致页面刷新、撤销或重新打开后退回内部英文标识。把完整目录重复附在每次修改响应又会制造不必要传输和前端合并成本，按引用投影可以保持一致且体积有界。
- 后果：核心操作与记录注册表成为展示元数据的唯一来源；新增或改名必须同步更新该注册表和快照契约测试。ProgramDocument、ECIR 和 Player 签名槽不因本决定保存中文名，改显示名也不改变稳定身份。

## ADR-074：专用值动作与统一值输入共用一个字段表面

- 决定：检查器不再展示“填写 / 变量 / 计算”来源按钮或“编辑计算”入口。普通值、坐标、区域和路径由统一类型化输入器承接；资源、控件、文件和目标引用保留选择、捕获或系统授权动作，但这些动作与 `@` 引用、成员访问和纯值操作共同修改同一个稳定 `value_id`。
- 决定：坐标和区域直接值分别投影为 `坐标(x, y)` 与 `区域(x, y, 宽, 高)`，并允许引用兼容变量、结果字段和几何纯值操作。固定候选枚举仍为单纯下拉，不为了表面统一开放动态来源。
- 原因：来源按钮暴露内部 AST 分类，并让图片等字段出现没有上下文的“计算”入口；封闭的四格坐标表单又阻止“图像结果中心 + 偏移”等常见组合。统一值槽既降低理解成本，也不牺牲强类型、稳定绑定和专用采集效率。
- 后果：新增函数的每个参数必须先声明强类型和专用动作，再自动获得同一值输入投影；不得为新函数复制旧三模式表单。自动与真实交互验收同时覆盖直接值、`@` 引用、成员、纯值操作、捕获回填、无效草稿保持旧值和枚举固定选择。

## ADR-075：单点长按由“输入.点击”的保持时间表达

- 决定：正式版不增加重复的“输入.长按”原子函数；`输入.点击` 增加可选保持时间，`0` 表示普通点击，大于 `0` 表示在同一坐标持续按住后释放。
- 理由：单击、多击和长按共享坐标、按键、次数与间隔语义；扩展同一最小原子比维护两套近似函数更精简，也能在 Windows、ADB 与 Android 本机保持一致。
- 约束：保持时间为 `0..60000ms`，取消必须在保持期间生效；触控目标只接受主按键。拖拽继续负责多点连续路径，不用单点路径冒充用户可见的长按入口。

## ADR-076：拖拽使用整条路径的统一移动时长

- 决定：`输入.拖拽` 使用“路径、移动时长、缓动”三个核心参数，不向普通表单暴露每个采样点的独立时间轴。
- 理由：录制和框选首先产生几何路径；整条移动时长能覆盖滑块、多点手势和常见拖动，同时避免每个采样点生成难以理解的大量字段。
- 约束：移动时长为 `1..60000ms`。Windows 与 ADB 按相邻点距离分配总时长，Android 本机使用同一总时长提交连续 Accessibility 手势；相同输入必须产生确定性时序。

## ADR-077：项目函数提取采用语义分析与配套文档事务

- 决定：提取入口作用于同一语句块内的一条或多条连续语句。平台在写盘前分析局部符号流：外部只读局部值自动成为新函数参数，最多一个被后续流程继续引用的内部结果成为新函数返回值，并以调用结果绑定保持原调用者的稳定符号。
- 决定：不能保持语义的选择直接拒绝，包括跨语句块或不连续选择、依赖调用者返回、依赖未一并提取的外层循环、修改外部局部值以及存在多个逃逸结果。平台不通过隐藏元组、多返回值或确认框改变项目含义。
- 决定：源函数替换与新函数创建形成一个可撤销的配套文档事务。失败回滚新建文档；撤销同时恢复源语句并删除未被修改的配套函数；重做同时恢复二者。配套函数若已被单独修改，则阻止破坏性撤销并解释原因。
- 原因：仅复制几条语句并插入调用会破坏作用域、稳定 ID、控制流或留下孤立文件；把语义分析和双文档生命周期放入 Program Service，才能让“提取”成为可靠编辑能力而不是代码生成捷径。
- 后果：前端只收集选择和名称，不自行重写 ProgramDocument。测试必须覆盖参数提升、单结果回传、非法控制流、跨文件失败回滚、撤销/重做、项目目录刷新以及提取后调用的中文投影。

## ADR-078：调试展示由 ECIR 稳定映射投影，不由前端猜测内部槽位

- 决定：Compiler 在 ECIR `debug_map` 中为语句、值和局部符号附带稳定来源映射；Runtime Plan 将语句来源写入每条嵌套指令，Runtime 快照把当前函数局部槽位和项目变量投影为带中文名称、类型与值的只读条目。
- 决定：IDE 的“运行与调试”面板在日志与当前值之间直接切换。日志保留原始稳定语句 ID 作为定位键，点击可定位当前项目函数中的对应语句；普通界面不展示符号 ID。当前函数查找使用 `Ctrl+F`，覆盖语句摘要、备注和稳定 ID，逐项跳转时只展开命中路径。
- 原因：Runtime 原本已有值和指令 ID，但只显示原始事件会迫使用户阅读内部标识，也无法知道暂停时变量为何值。由编译映射统一投影可以覆盖项目函数调用、重命名和嵌套结构，同时避免前端维护第二套符号分析。
- 后果：新增局部绑定类型必须进入 `debug_map.symbols`；调试快照与前端类型需同步演进。值展示只读且有界，不成为持久变量或修改运行状态的入口；跨项目全文检索若后续加入，仍使用稳定 `function_id + statement_id`，不能解析显示文字反写项目。

## ADR-079：项目恢复使用修改前快照与显式选择，不恢复旧业务栈

- 决定：每次 ProgramDocument 替换或删除前，Program Repository 在 `.easycode/history/program/functions/` 写入带内容哈希的修改前快照；每个函数最多保留 100 项。恢复历史版本前再次归档当前有效版本；当前文件损坏时先把原始坏字节保存在 `.easycode/recovery/program/functions/`，再执行用户明确选择的恢复。
- 决定：项目检查发现任一 ProgramDocument 损坏时返回恢复状态，不激活可编辑工作区、不自动修复、不覆盖坏文件。欢迎页使用 EasyCode 内部恢复面板展示可用历史；无历史时保持原文件并要求外部备份。视图、折叠和面板状态单独写入 `.easycode/view-state.json`，读取损坏只回到默认布局，不影响业务文档。
- 决定：ProgramDocument 编辑采用服务端原子结构命令，成功即保存，不存在另一份等待覆盖磁盘的可编辑源码。外部冲突展示当前命令基线与磁盘 revision；用户可以重新加载后重交当前表单草稿，或保留界面稍后处理。平台不提供会静默抹掉外部修改的整文档强制覆盖入口。
- 原因：历史快照必须在主文件改变前落稳，才能覆盖磁盘满、进程中断和损坏场景；把坏文件保留为证据并要求显式恢复，比猜测修复更可审计。结构命令架构下提供“覆盖整个文档”会扩大一次普通字段修改的破坏范围。
- 后果：保存失败必须保留当前磁盘字节、前端草稿和可重试操作；历史项损坏只跳过该候选，不遮蔽其余恢复点。暂停仍只在当前进程续接；停止、取消和崩溃后的新运行从入口开始，诊断包保留最后稳定语句、调用栈、脱敏值和运行日志。

## ADR-080：Android OCR 使用随 APK 密封的中英文模型

- 决定：Android 本机 `文字.识别 / 匹配 / 等待出现` 复用 Windows/ADB 的 `OCRResult / OCRLine`、稳定字段 ID、区域、预处理、帧引用和正常空结果语义。宿主适配使用随 APK 静态打包的 ML Kit Text Recognition v2 中文识别器承接“自动（中英文）”，不使用 Google Play Services 动态模型、不在首次运行下载模型，也不增加第二套用户函数或模型选择表单。
- 决定：Android 发布预检与 APK 内预检同时白名单 `text.recognize / standard.text.match / standard.text.wait_visible`；缺少实现、模型闭包、ABI、帧权限或无效正则时失败关闭。OCR 缓存只绑定不可变 `frame_ref + 区域 + 预处理`，宿主关闭或帧空间失效即丢弃；结果继续携带来源目标、来源帧和空间版本。
- 原因：Android 完成门要求断网、断线和关闭开发后端后仍可 OCR。动态下载模型会让第一次运行和无 Google Play 设备产生假可用；自制字符识别器又无法满足中文游戏脚本的准确率和维护成本。官方 bundled 模型提供成熟的本机推理边界，同时允许前台契约保持不变。
- 后果：APK 真实包含 OCR 原生库，production 变体必须精确收束 `arm64-v8a + armeabi-v7a`，模拟器变体只含 `x86_64`；包体增大属于披露后的离线能力成本。自动构建、模拟器识别和 ABI 扫描不能替代断线真机、低端机性能、方向/权限变化与 release 外部签名验收；通过前这些状态必须继续标为未验证或阻塞。

## ADR-081：Windows 应用更新由安装目录外的独立助手整目录替换

- 决定：Windows `ide_package` 与 `windows_bundle` 使用严格 `easycode-windows-application-v1` ZIP。包内清单精确列出每个相对路径、长度和 SHA-256，并声明唯一启动入口；未登记成员、重复/越界路径、符号链接、入口缺失、大小或哈希不符均在修改安装目录前失败。
- 决定：运行中的 IDE/Player 只能生成包含已验证产物、本机固定安装根、本机重启命令、父进程和交接根的 schema 2 记录。冻结的更新助手复制到用户可写交接目录后等待旧进程退出，在安装目录同卷完成暂存、旧目录备份和原子目录交换；签名 Feed 不获得选择本地路径或命令的权限。
- 决定：新应用成功初始化本地 API 后写一次性随机健康探针。外部助手验证探针后生成绑定 `release_id + release_sequence + artifact_sha256` 的最终回执；启动失败或超时则隔离失败目录、恢复并启动上一版本。主更新状态机只认领最终回执，不能把早期启动探针或“后台进程已创建”当作安装成功。
- 决定：Player 的应用更新动作先使用 EasyCode 内部确认框说明退出、重启和回滚行为。系统文件选择、权限与 Android APK 安装仍属于允许出现的系统授权边界；Windows 应用更新不新增原生业务确认弹窗。
- 原因：Windows 进程不能安全覆盖自身文件，逐文件复制还会产生新旧 DLL 混装；让更新元数据控制本地路径会扩大供应链权限。外置单文件助手、严格清单、同卷整目录交换和独立健康回执能把下载成功、进程启动与真实可用区分开。
- 后果：独立 Player 交付目录必须同时携带 `EasycodePlayer.exe` 与 `EasycodeUpdateHelper.exe`，构建 Harness 必须验证成功更新和故意坏版本回滚。开发签名候选通过不等于 Authenticode 正式发布通过；IDE 正式安装根和重启命令必须由安装器显式配置，源码工作区默认不自更新。

## ADR-082：Android 行为只按公开能力分层，不按测试厂商分支

- 决定：Android 本机运行时只允许依据 SDK/API 级别、公开 Android 能力、当前权限与运行时探测结果选择行为。厂商、品牌和型号只可进入脱敏诊断与设备列表展示，不能决定权限入口、捕获、输入、文件、调度或恢复路径；不得加入小米、MIUI 或其他 OEM 私有包名、Intent、设置页结构和坐标脚本。
- 决定：公开系统 Intent 必须先验证存在可处理 Activity，并捕获启动失败；Accessibility 等授权返回后必须等待真实服务连接而不能假定设置页返回即已可用。设备缺少可选温度、热状态或其他诊断字段时记录为空，不把厂商差异冒充任务失败。
- 原因：当前小米 Android 13 真机只是一个物理测试样本，不是产品平台定义。依赖厂商页面和私有接口会在 AOSP、三星、OPPO、vivo 等设备上制造假支持，并让未来系统更新直接破坏运行路径。
- 后果：源码契约检查阻止已知厂商标识进入 Android 行为实现；发布报告必须分别记录 API、ABI、厂商和真机/模拟器证据。一个厂商或两个 API 的通过不能写成 Android 通用矩阵通过，正式放行仍需非小米实体设备验证。

## ADR-083：Android 最低版本由项目实际能力闭包自动推导

- 决定：Android 本机基础运行时最低支持 API 21（Android 5.0），项目与 APK 的实际 `minSdk` 等于其语句、监听、Player 终端动作和扩展闭包中所有 Android 本机能力要求的最大值，数量不参与计算。开发者不能手工把要求降到能力闭包以下；当前未使用高版本能力时也不被其他项目抬高。
- 决定：每个函数和语言机制在权威契约中声明 `minimum_android_api`。首批明确分层为：普通纯值、日志、基础文件、MediaProjection 捕获等可兼容能力以 API 21 为基线；当前安全消息身份与消息监听要求 API 23；基于 Accessibility `dispatchGesture` 的点击、滚动、拖拽及依赖它们的标准图像点击要求 API 24。新增能力必须先声明并验证 API 下限，不能沿用项目总开关或依据测试机厂商猜测。
- 决定：Compiler 输出数值下限及抬高下限的稳定函数/语句依据，发布报告原样锁定；Android Publisher 将该值传给 Gradle，构建后从 APK Manifest 反查并要求精确一致。Player/发布界面显示用户版本名（例如“Android 7.0 及以上”）并可展开“由哪些语句要求”；异常通用包即使被旁加载到更老设备，加载预检仍以稳定诊断阻止执行。
- 决定：PC 上的 ADB 目标属于 Windows Host 能力，不由 Android 本机 APK 的 `minSdk` 限制。因此 Android 5/6 设备既可运行只含 API 21 能力的本机 APK，也可由 PC ADB 模式执行更广的坐标/图像流程；二者的通过证据和权限边界必须分别记录。
- 决定：对用户的能力承诺分为两层：API 24（Android 7.0）是 Android 本机完整自动化基线；API 21–23 是按项目能力闭包裁剪后的兼容层。当且仅当脚本语句、监听、Player 字段动作、扩展及全部依赖都不高于 API 21 时，才生成 `minSdk=21` 的 APK。“可安装”不等于“所有 EasyCode 能力都可用”；IDE 必须在构建前显示实际最低版本和抬高它的稳定来源。
- 原因：固定 Android 8 会无谓排除只需基础能力的旧手机、云机和模拟器；宣称所有能力都兼容 Android 5 又会在触控、安全密钥等公开 API 尚不存在时制造假支持。按闭包取最大值可同时获得最广安装范围、真实能力边界和可解释发布结果。
- 后果：基础 Runtime 必须通过 API 21 lint 与兼容测试；API 21/23/24 的代表设备或等价系统镜像分别验收对应切片，较高 API 真机通过不能替代低版本验证。扩展若要求更高版本会自然抬高项目 APK；任何报告、ECIR、Gradle 参数与成品 Manifest 不一致都视为发布失败。

## ADR-084：Android Kotlin/JVM 扩展在 APK 构建期静态链接并由独立 Worker 进程调用

- 决定：`android-kotlin-v1` 的 `ecx-runtime-1` 产物必须包含一个已编译 JAR 作为 `module`；`entrypoints` 的值是实现 EasyCode 稳定 Android 扩展 ABI 的 JVM 二进制类名。Android Publisher 在验证扩展发布者签名、lock、密封描述、JAR 哈希和函数契约后，才把 JAR 作为该 APK 的构建输入静态链接。APK 不使用 `DexClassLoader`、不从内容更新槽加载新代码，也不在运行时下载扩展依赖。
- 决定：扩展函数通过版本化 JSON 请求/响应 ABI 执行，请求只包含稳定函数/指令/运行身份、类型化参数和批准的上下文；响应包含单一返回值、结构化事件或结构化失败。入口运行在 APK 内独立的 `:extension_worker` 进程；异常、进程退出、超时、取消、无效 JSON、返回过大和返回类型错误都由宿主收束为扩展错误，不能拖垮 Player 主进程或伪报成功。
- 决定：APK 内生成不可编辑的扩展注册表，锁定 `package_id + variant_id + function_id + class_name + artifact/module hash + minimum_android_api + permissions`。Bundle Loader 必须把该注册表与签名 `.ecplayer` 的扩展描述及 `easycode.lock` 精确比对后才允许执行。原生扩展、权限或入口变化属于应用更新，不能作为仅内容更新进入 A/B 项目槽。
- 原因：构建期静态链接兼顾离线运行、Android 新版本代码加载限制、可复现发布和第三方扩展能力；独立进程又能覆盖普通异常无法承接的崩溃与超时。直接在主进程反射或运行时解压加载 DEX 会扩大供应链、生命周期和更新边界。
- 后果：外部开发者通过单独的 Android Extension API JAR 编译扩展，不需要 EasyCode 内置源码编辑器。首个中立 Harness 必须证明合法返回、结构化日志、异常、超时、Worker 崩溃、篡改、缺少入口、API 下限和源码隔离；真实 Android 设备通过前仍不得把 Android 扩展标记为已验证。

## ADR-085：Android Manifest 权限由签名发布闭包裁剪

- 决定：Android Publisher 不再把模板中的网络、局域网、MediaProjection 与悬浮窗权限无条件带入每个 APK。基础离线 Runtime 固定保留前台执行、通知、唤醒和本地计划重启恢复所需声明；网络/消息、目标帧、Player 捕获动作、在线应用更新和扩展权限只在签名发布报告实际要求时加入。生成 Manifest 使用确定性构建输入，并以 `tools:node="remove"` 同时移除依赖 AAR 试图追加但闭包未批准的权限。
- 决定：构建完成后必须从成品 APK 反查全部 `uses-permission`。除 AndroidX 自动生成的包内动态接收器保护权限外，结果必须与计算闭包精确相等；缺失或额外权限均使构建失败。权限闭包、生成 Manifest、Gradle 输入和 APK 检查结果进入 evidence，不能只依赖源码模板或测试断言。
- 原因：离线 ML Kit 等依赖可能通过自己的 AAR Manifest 加入 `INTERNET` 与 `ACCESS_NETWORK_STATE`，仅从应用模板删掉权限并不能形成真实最小权限包。按项目最低 API 裁剪功能却继续携带所有权限，会让旧设备兼容、终端授权说明和“关闭在线能力即零外连”彼此矛盾。
- 后果：同一 EasyCode Runtime 可按项目生成权限不同的 APK；新增函数、Player 动作、扩展或维护服务时必须先进入稳定能力/权限注册表，不能直接修改 Manifest 绕过发布闭包。Manifest 权限声明不等于运行时授权，危险权限仍只在用户触发对应动作时由 EasyCode 内说明并交给 Android 系统授权。

## ADR-086：时间标量与文本提取使用跨运行时确定性纯值契约

- 决定：`date / datetime / time` 在 ECIR 求值后统一为 ISO 文本标量，类型仍由 ProgramDocument 与操作签名持有，不在运行值中重复包裹 `{kind, value}`。带偏移的 `datetime` 按真实时间点比较；无偏移值按本地日期时间比较；二者混合比较或计算差值返回 `time.timezone_mismatch`，不得猜测设备时区。
- 决定：日期时间格式只接受可移植标记 `yyyy / MM / dd / HH / mm / ss / SSS / XXX`。解析失败属于正常“无结果”，格式自身无效、运行值无效和时区不一致分别使用稳定错误；日期按天、时间按 24 小时循环、持续时间按毫秒计算。
- 决定：核心文本提取提供首个有符号 ASCII 整数、首次正则匹配的指定分组和首次匹配的全部捕获分组。无匹配返回无结果或空列表；整数超出 int64 返回无结果；非法正则与分组越界明确报错。Python 与 Android Runtime 使用同一操作 ID、输入槽、类型和可观察语义。
- 原因：此前时间字面量保留结构对象而 `时间.现在` 返回文本，使同一类型不能可靠比较或参与计算。确定性纯值能力既覆盖 OCR、房间码、时间计划等常见数据整理，又不把时钟读取或 I/O 偷渡进表达式。
- 后果：纯值注册表提升为版本 7，旧注册表哈希不能加载新 ECIR。新增时间格式标记或正则语义变化必须提升注册表版本并同时更新两端运行时、类型目录、语法参考和跨端契约测试。

## ADR-087：控件状态与通用操作只使用平台语义能力

- 决定：统一的 `控件.读取状态` 返回 `ControlStatus`，包含启用、可见、勾选、选中、可编辑、可聚焦、已聚焦、当前值和区域。某平台或某控件没有对应语义时，可选字段返回无结果，不能把“未知”伪造成 `false`。
- 决定：聚焦、设置值、选择项目、切换开关和滚动到控件共用稳定官方契约。Windows 使用 UIA Pattern，Android 本机使用 Accessibility Action；不支持相应 Pattern/Action 时返回稳定操作失败。此类操作不允许静默点击坐标冒充成功。
- 决定：ADB UIAutomator 能读取 XML 暴露的状态和设置可编辑文本；其控件引用已来自当前可见树时，“滚动到控件”只确认当前可见。UIAutomator 没有可移植的聚焦、选择和切换语义，因此现阶段这些动作只能按明确目标点击执行并保留真实路径，不宣称等同 Android Accessibility。最终真实宿主验收若证明语义不足，应在平台契约中禁用该固定能力，而不是伪报完整支持。
- 原因：同名“控件”必须让项目结构跨平台复用，但不同控件提供方的能力并不相同。用可选状态和稳定失败表达差异，可以保留完整上限，同时避免游戏 SurfaceView、自绘页面或缺失 Pattern 的控件产生假成功。
- 后果：Android 本机的滚动到控件要求 API 23；Compiler 会据此抬高项目最低 Android 版本。真实 Windows、模拟器和手机矩阵将在最终统一验收阶段补证，自动测试和编译通过只把总账推进到 `Partial`。

## ADR-088：整帧保存与裁剪合并为一个画面原子

- 决定：正式库只提供 `画面.保存`，参数为授权写文件、可选冻结画面、可选裁剪区域、PNG/JPEG 格式和 JPEG 质量。画面为空时在调用开始取得当前目标新帧；区域为空时保存整帧，因此不再增加重复的“截图保存”和“裁剪图片”函数。
- 决定：函数只接受当前运行目标拥有的不可变 `FrameReference`；跨目标、过期、元数据修改、越界区域、未知格式和非法质量均在写文件前失败。Windows/ADB 对授权路径采用同目录暂存和原子替换；Android 私有数据目录使用原子文件，外部 SAF Provider 使用其受权文档流并明确报告写入失败。
- 决定：PNG 保留无损像素；JPEG 质量只在 JPEG 时生效但仍保留稳定默认值。运行日志记录实际尺寸与格式，不记录图片内容。图片编码器属于 Player 发布闭包，不允许运行时下载。
- 原因：保存整帧和裁剪后保存只有区域参数不同，拆成两个入口会重复文件、格式、权限和错误语义。让同一函数接受固定帧还能保证“先识图再保存证据”复用完全相同的像素。
- 后果：最终统一验收必须分别覆盖 Windows、ADB 与 Android 本机整帧/裁剪、PNG/JPEG、外部授权、空间不足和写入中断。SAF Provider 无法提供原子替换时不得把普通流写入宣传为原子保存，相关证据未完成前总账保持 `Partial`。

## ADR-089：窗口位置、尺寸和显示状态使用三个正交原子

- 决定：Windows 窗口管理增加 `窗口.移动`、`窗口.调整大小` 和 `窗口.改变显示状态`。显示状态是固定枚举“还原/最小化/最大化”，不为三个状态分别增加近似函数；移动与尺寸保持分离，避免只改一项时要求用户先读取并回填另一项。`窗口.调整大小` 的尺寸明确指截图与输入使用的客户区尺寸，运行时根据当次窗口边框和 DPI 反算外框并验证结果，不把外框尺寸冒充客户区尺寸。
- 决定：位置允许负坐标以支持左侧或上方多显示器；尺寸接受 1..32767 的整数并把系统拒绝作为稳定操作失败。操作继续要求当前运行会话产生且通过进程、线程和窗口类复核的 `WindowReference`，不接受裸句柄。
- 决定：`WindowStatus` 增加“已最大化”，与既有“已最小化”并列。窗口操作不隐式激活、不改变 Z 序，只有显式 `窗口.激活` 才取得前台；系统策略拒绝时不伪报成功。
- 原因：位置、尺寸和显示状态是 Windows 自动化常见但相互独立的三种意图。正交原子能覆盖布局编排，同时避免一组移动并调整的万能表单和五个重复状态函数。
- 后果：这些函数只在 Windows 目标可插入。自动替身验证不等于真实窗口管理通过，最终候选仍需在普通 Win32、现代应用、多显示器和权限不匹配场景中验收。

## ADR-090：颜色能力由两个画面原子和一个纯值比较组成

- 决定：正式库只增加 `颜色.读取` 与 `颜色.查找` 两个目标原子。读取返回稳定 RGBA `Color`；查找接收颜色、0..255 容差、可选区域和可选冻结帧，按从上到下、从左到右返回首个坐标，未命中是正常无结果。大区域按有界行块执行并检查取消。
- 决定：两个已有颜色值的比较不再次截取屏幕，因此作为纯值操作 `颜色.接近` 提供，逐 RGBA 通道应用同一容差。颜色通道、容差不是 0..255 整数时稳定失败，不截断、不钳制，也不把无效值当黑色。
- 决定：Windows、ADB 和 Android 本机使用相同 RGBA 外部模型；宿主截图缺少透明通道时其 Alpha 明确为 255。显式画面只能来自当前目标和当前运行，避免切换目标后把旧坐标空间误用于新目标。
- 原因：读取、找色会访问目标画面，比较两个值则是确定性计算。分开这条边界既覆盖像素判断、区域找色和冻结证据帧，也避免增加“颜色是否存在”等重复流程函数。
- 后果：纯值注册表提升为版本 8，Python 与 Android Runtime、锁文件和语法参考必须精确匹配新哈希。真实三端和大画面性能证据留到功能面闭合后的统一验收，不由合成帧测试冒充。

## ADR-091：公开结构值必须可创建、可取字段且跨运行时同形

- 决定：每个官方函数公开的参数与返回类型，只能是已登记原子值、带权限的引用、类型化容器或具有稳定字段 ID 的命名记录。新增函数不能返回只有运行时知道键名的任意字典；自动契约测试遍历完整官方目录并阻止未登记类型进入可见函数库。
- 决定：`目录.列出` 使用命名的“目录筛选”和“文件系统条目”；筛选固定提供 `* / ?` 名称模式与最大条数，条目固定提供名称、条目类型、大小以及互斥的文件/目录引用。目录复制/移动统一返回“目录操作报告”，递归删除保留语义不同的“目录删除报告”。Windows 与 Android 必须写出相同稳定字段。
- 决定：消息批次、收件状态、收到的消息、已读等待和取消结果登记为可浏览记录，但保留已经发布到 Runtime/存储中的原字段 ID，不为追求命名外观制造迁移层。窗口查找的选择器登记为结构值，包含标题、匹配方式、类名、进程 ID 与匹配序号；IDE 使用通用结构编辑器，不把它退化为 JSON 或普通文本。
- 原因：函数“存在”不等于能在结构化编辑器中真正使用。缺少记录契约会造成参数无法配置、返回结果无法选择字段，或 Python/Android 同名函数返回不同形状；这些问题不会被仅调用 Runtime 的单元测试发现。
- 后果：类型目录成为公开函数组合能力的完成门。专用采集原子（坐标、区域、手势路径等）仍保持原子值，不为形式统一强行拆成记录；未来每种新增结构返回值必须同时提供字段展示、类型兼容、Compiler 校验和各 Runtime 同形测试。
- 后果：Android Publisher 与 APK 内预检的 opcode 白名单必须精确相等，并覆盖全部声明支持 Android 本机的官方函数；解释器已经绑定但预检遗漏的指令同样属于功能未完成。当前已据此补齐“等待应用退出”和剪贴板读写，未来新增 Android 函数必须由一致性测试同时推进两层预检。

## ADR-092：Windows Player 使用当前用户原子安装并与用户数据分离

- 决定：首个正式版的安装器采用无需管理员权限的当前用户安装，产品程序根固定在 `%LOCALAPPDATA%\Programs\EasyCode\Products\<product_id>`，运行方案、日志、录制和实例数据继续位于独立用户数据根。自动化宿主是否提权由后续 ADR-114 独立约束；安装权限不能推导运行权限。普通卸载默认保留数据；删除数据必须由用户另行明确选择。
- 决定：首次安装与离线修复复用 `easycode-windows-application-v1` 严格应用归档。安装器锁定产品/发布身份、归档长度和哈希，解包后再次逐文件验证，在同卷暂存完成后整目录交换；已安装在线更新仍由外置更新助手和健康探针承接。
- 决定：安装器创建当前用户开始菜单入口、可选桌面入口、HKCU 卸载项和 Player Hub 安装登记。启动入口直接引用冻结 Player、签名 `.ecplayer` 与固定信任根，不依赖批处理、系统 Python、IDE 或开发后端。
- 原因：只有可运行目录仍要求用户理解解压、路径和手工登记，不是普通用户可交付产品；机器级 MSI 又会无必要地引入管理员权限和更复杂的更新边界。当前用户原子安装足以覆盖目标场景，并可在未来签名而无需改变项目格式。
- 后果：开发候选可以验证安装逻辑，但生产放行仍要求 Authenticode 与干净客户机。安装器只能删除自身标记的精确产品目录；任何宽泛路径、符号链接、身份漂移或清单不一致必须失败关闭。
## ADR-093：Android 本机录制复用同一运行方案契约

- 决定：Windows/ADB 与 Android 本机 Player 的录制设置统一保存在 Player profile 的 `recording` 字段，并绑定精确 profile revision。Python Player 不再以旧实现状态拒绝 `android_local` 方案；实际录制执行仍由宿主自己的录制器承担，Windows/ADB 使用 `V6FrameRecorder`，Android 本机使用 `AndroidFrameRecorder`。
- 原因：共享表单和签名方案不能因打开它的宿主不同而出现互相矛盾的可保存性；平台差异应留在执行适配与能力预检层，不能残留为过期的方案数据限制。

## ADR-094：Android 应用生命周期按可证明能力发布

- 决定：`应用.启动` 支持 Android 本机，并通过 `MAIN + LAUNCHER` 的包可见性查询发现普通可启动应用，不申请可枚举全部安装包的 `QUERY_ALL_PACKAGES`。显式 Activity 仍可按结构化应用引用启动。
- 决定：`应用.等待退出` 只发布给 Windows 宿主，包括由 Windows 驱动的 ADB 目标；Android 本机在编译和 APK 预检前显示不支持，不允许发布一个运行时必然失败的入口。
- 原因：Android 没有面向普通应用、无需高风险权限且可可靠区分“退出”和“转入后台”的通用观察接口。平台必须提前说明能力边界，不能把确定失败伪装成条件支持。

## ADR-095：完整命令进入顶部菜单，工作区按任务选布局并持久化可调面板

- 决定：IDE 顶部提供 `项目 / 编辑 / 视图 / 运行 / 帮助` 完整菜单，使用稳定命令 ID 连接真实动作和可配置快捷键。页面内只保留高频或当前对象特有动作；菜单项必须反映真实启用状态和当前快捷键，不能放置无承接入口。
- 决定：程序、Player 等需要上下文导航、主操作面和检查器的工作区可以使用三域布局；资源、变量、目标、扩展和计划等采用列表/详情或主区/抽屉，不把三栏当作全局模板。设置、快捷键和发布审核等集中任务使用 EasyCode 自有大型模态工作区，不调用 Windows 通用确认框。
- 决定：长期侧栏、检查器和底部面板通过同一分隔条支持指针与键盘调整，安全边界内的尺寸写入项目 `.easycode/view-state.json`；窄窗口的临时抽屉状态不得覆写桌面尺寸。快捷键配置属于当前用户设置，不写入可发布项目。
- 原因：菜单解决完整能力的可发现性，页面保留高频操作才能降低日常认知负担；按任务选择布局可避免简单页面被空栏挤压。面板尺寸和快捷键是用户工作习惯，必须可调、可恢复并由真实持久化承接，而不是只做视觉拖动。
- 后果：UI 实施先接通命令、快捷键、尺寸持久化和禁用语义，再进行纯视觉精修。自动测试覆盖菜单到命令、冲突检测和视图状态往返；真实窗口验收覆盖宽屏、窄屏、键盘调整、重启恢复与焦点回归。

## ADR-096：扩展内容进入受控槽位，工作区左栏使用同一用户尺寸

- 决定：程序、资源、变量、目标、录制、扩展、计划和 Player 的首个长期左栏共享同一个用户宽度 `sidebar`。页面不得各自保存另一份宽度；右侧检查器使用反向分隔条语义，向右拖动缩小右栏、向左拖动放大右栏。窄窗口可临时改为抽屉或隐藏，但不得覆盖桌面宽度。
- 决定：扩展函数与官方函数使用同一函数卡、参数 Control、语句投影和结果绑定，只按来源进入函数库“扩展”分页，并按扩展命名空间分组。纯函数扩展不得添加新的活动栏入口；声明式功能工作区先进入“扩展”中心，只有用户明确固定后才可提升为活动栏入口。
- 决定：第三方扩展只可向平台登记的槽位贡献内容：函数库、受约束的声明式工作区、Player Control 区段、目标驱动和发布闭包。不得注入任意 Vue/HTML/JS、修改核心导航顺序、伪装官方来源或绕过共享 Control。禁用后所有可见入口和运行贡献必须一起消失。
- 原因：扩展如果另起一套卡片、页面和参数编辑器，会让产品像多个工具拼装而成；页面各自记宽度也会让切换工作区产生跳动。共享布局习惯与受控贡献槽位可以保留扩展上限，同时保持 EasyCode 的统一学习路径。
- 后果：后端函数目录必须保留 `source + package_id`，前端不得再把扩展函数混入官方页。中立项目级展示扩展用于验证签名、信任、启停、函数目录、Control、Worker、锁和卸载，不进入正式产品清单或发布包。

## ADR-097：稀缺外部环境矩阵延期，不伪装为通过也不阻塞 UI 阶段

- 决定：非小米 Android 实体设备、两台独立物理宿主的局域网矩阵和 EasyCode 官方托管生产服务暂缓验收。现有小米真机、Android 模拟器、同机双进程以及模拟器→真机证据继续保留；这些能力按当前契约实现，但未覆盖的环境只标记为 `Deferred`，不能写成已通过。
- 决定：物理双机特指同一或可路由局域网内、运行于两台独立电脑/设备上的 Player 实例，覆盖真实配对、防火墙、地址变化、睡眠/唤醒、网络分区、重连和幂等派发。单电脑多进程及模拟器→同机连接手机能验证协议与主要业务链，但不替代该矩阵。
- 决定：官方托管延期的是账号、域名/TLS、对象存储/CDN、配额、审计、监控与灾备等真实服务运营闭环；已经完成的签名 Feed、客户端更新协议、自建源和关闭更新模式仍保留。没有真实服务前只能称“协议与自建路径完成”，不能称官方托管理论通过。
- 原因：当前没有额外厂商真机、第二台电脑或生产云资源；继续用替身重复验证不能增加相应环境置信度。它们也不是结构化程序、官方函数、Compiler 或 Runtime 的已知功能空洞，不应阻塞接下来的 IDE/Player UI 精修。
- 后果：UI 阶段可以开始，但字段试用、第二物理宿主和官方托管上线时必须重新激活对应矩阵；客户现场若暴露厂商差异，应保留设备/系统/权限/日志证据后按平台垂直切片修复。生产签名、最终候选长稳和当前唯一设备可完成的断线独立验证不因本决定自动延期。

## ADR-098：参数契约区分主要、高级、条件与内部配置

- 决定：函数参数契约的 `ui` 元数据统一声明 `importance = primary / advanced / contextual / internal`、类型化 placeholder、帮助说明、有效默认值文案和可选显示条件。检查器默认只展示完成当前调用所需的主要字段；高级字段保留在同一检查器的一个折叠区中，条件字段只在前置选择成立时出现，内部字段不进入 IDE、Player 字段来源或普通帮助。
- 决定：`日志.输出` 的 `category` 由宿主依据官方、项目或扩展来源生成，作者界面不再配置；`等待.直到` 的 `past_policy` 对新调用固定使用 `next_day`，语义为等待下一次到达该时间。两个旧稳定槽仅作为加载既有 format 6 测试数据的内部兼容槽保留，不再构成公开作者能力，也不能发布为 Player 可配置字段。
- 决定：自由文本输入支持“普通文字 + 稳定变量/结果词元 + 纯值表达式”的混合投影，例如 `当前体力为 [项目 · 当前体力]`。输入器把它降低为既有 `core.text_concat.v1` 与必要的 `core.value_to_text.v1` 递归值树，不新增公式字符串、模板源码或另一种可编辑事实。持续时间允许用数值表达式和单位组成类型化值，例如 `[局部 · 等待秒数] 秒`；单位只参与草稿解析，ProgramDocument 保存经过注册表验证的持续时间纯值操作。普通 `[]` 是正式编辑和复制语法；只读界面的半框仅是 CSS 投影，不得持久化为装饰字符。
- 决定：普通函数结果可以新建局部变量，也可以写入当前词法作用域内类型兼容的既有局部变量；结果绑定继续保存稳定 `symbol_id` 和 `declare`，不接受任意表达式或项目变量。项目变量仍通过显式赋值语句修改，以保持写入在流程正文中可见。
- 原因：125 个可选参数被平铺、契约缺少 placeholder/帮助、文本与变量无法自然组合，会让普通作者先理解运行时细节再完成简单任务。把披露层写回共享契约，并把自由输入降低为现有强类型树，可以同时减少认知负担、保留高级能力并维持 IDE、Compiler、Runtime 与 Player 单一语义。
- 后果：函数契约指纹、前端 Control、Player 绑定来源和参数快照测试必须同步更新。隐藏不是删除执行能力；危险删除、覆盖、跨源网络和副作用重试仍按实际风险显式确认，不能进入无提示默认值。

## ADR-099：交互捕获使用有界常驻驱动、快照绑定语义与共享内存预览

- 决定：IDE 与 Player 的交互捕获分别维护目标级有界驱动池，键包含所有者、项目规范路径、目标类型、目标身份与完整目标签名；每个所有者最多 2 个、空闲 5 分钟。连接后的后台预热取得并丢弃一帧，预热与立即点击使用单航班初始化；配置变化、驱动失败、会话关闭和进程退出立即释放。Runtime 执行不复用该池。
- 决定：原生捕获热路径保留 RGB 冻结帧并以具名共享内存提供 BGRA 像素，避免 PNG 编码、磁盘往返和前端 base64；刷新、裁剪、保存等需要编码时才延迟生成 PNG。共享内存不可用时保留 PNG 文件回退，且映射/文件随快照关闭或宿主退出清理。
- 决定：ADB 控件捕获在视频帧取得期间并行预取同一设备 UIAutomator 快照；Windows 控件解析优先使用 UIA BuildCache 批量取得最小字段。桌面捕获不再通过固定 90ms 的隐藏/重显窗口探测，而是从冻结帧坐标排除原生捕获进程和输入穿透系统窗，绑定其下真实窗口；显式窗口目标继续绑定原 HWND。
- 原因：每次构造 scrcpy/WGC、同步 PNG/磁盘传输、串行 UIAutomator 与固定等待把一次简单取点放大为明显停顿；同时直接在顶层遮罩上做 UIA 会误捕获 EasyCode 自己。成熟链路应把可复用启动成本移到空闲期，把帧与语义并行，并让探测严格绑定冻结时的目标空间。
- 后果：普通界面的外观、按钮、键盘、选择和原子回填不变；新增耗时只进入本机结构化诊断。性能验收必须分别报告冷启动、预热后首击、连续热路径、控件解析和回退，不得用单元测试或单一总耗时冒充真实体验。

## ADR-100：值语法使用注册表驱动的全局发现目录

- 决定：值目录在现有类型兼容候选之外，统一返回版本化的语法发现信息：命名空间、全部核心纯操作的展示与搜索元数据、当前字段兼容状态、直接值示例、运算符和参数枚举。IDE 的统一输入器、字段帮助、自动生成语法文档与 Harness 只消费这一事实源，不再各自维护一份手写能力清单。
- 决定：零记忆入口固定为 `Ctrl+Space`。键入 `@` 只发现当前作用域值本体，选择值后键入 `.` 逐级发现字段；键入命名空间或 `命名空间.` 发现对应纯操作；进入参数后发现参数名称、类型、枚举与可用直接值；已有操作数后发现当前类型允许的运算符。不兼容操作可以在明确搜索或命名空间目录中显示，但必须禁用并说明所需结果类型，不能允许提交后才报错。
- 决定：核心命名空间固定由纯值注册表投影为“文本、数值、类型、时间、结果、条件、坐标、颜色、列表、字典、JSON、文件”。自然语言、旧名称和英文只作为搜索别名；规范名称、稳定操作 ID 和输入槽不因别名改变。普通官方、项目和扩展函数仍只作为独立语句，不进入表达式目录；扩展不得借发现元数据注册私有表达式语法。
- 决定：每个可执行核心纯操作必须具备命名空间、动作名、用途、参数标签、搜索关键词、示例和适用结果类型的可生成元数据。注册表操作集合、后端发现目录、前端可解析语法和生成文档任一漂移都使测试失败。目录响应带注册表版本和哈希，客户端按该身份缓存；没有真实目录时只保留直接值编辑，不显示不可提交的假操作。
- 原因：只有“支持语法”而没有输入时发现路径，等价于普通用户无法使用。把候选散落在组件、placeholder 和文档中还会在新增操作后必然漂移；将发现信息并入权威值目录，才能让用户只记住 `@`、`.`、命名空间和 `Ctrl+Space`，同时保持 ProgramDocument、Compiler 与 Runtime 的强类型边界。
- 后果：值目录线格式提升但保持旧字段兼容读取；统一输入器需要覆盖命名空间、操作、字面量、运算符和参数五类候选及完整键盘路径。语法参考由同一元数据生成。未来新增核心操作若没有发现元数据、解析往返与帮助覆盖，不得进入可执行注册表。

## ADR-101：结构化值的作者方式由 Record 注册表决定

- 决定：命名 Record 除稳定字段 ID、展示名和类型外，必须声明作者方式与字段 UI 契约。作者方式区分可内联构造、聚焦编辑、仅引用和仅捕获；字段契约承接默认值、Control、约束、帮助、重要性和条件显示。函数参数目录、IDE 检查器与 Player 表单都从同一注册表投影，不再根据当前值的外观或字段数量各自猜测。
- 决定：小型可构造 Record 在右侧检查器中直接渐进编辑；列表、字典、JSON 和深层 Record 才使用摘要加外置字段动作进入轻量事务浮层。运行时结果、画面/控件等宿主句柄不得开放手工结构构造；专用选择与捕获继续写入强类型 ProgramDocument。OCR 预处理采用内联开关，阈值仅在二值化开启时出现且范围固定为 0..255。
- 决定：输入框外观内只表达值、有效默认值、单位或不可交互状态，任何“编辑、选择、捕获”动作都位于边界外并使用与 Control 等高的共享动作原语。结构浮层按内容使用紧凑、普通和宽三档，不再给所有记录强制同一大尺寸，也不得同时展示整值编辑器与字段树。
- 决定：每次 Program 快照收集 RecordValue 时同时投影该 Record 的全部稳定字段展示名。目录请求失败不能把已经保存的记录降级为“字段 N”或裸 ID；未知扩展 Record 采用安全聚焦或只读失败状态，不能静默退化成任意 JSON。
- 决定：字段动作还必须声明并满足当前表面的真实适配能力。聚焦编辑器中的嵌套字段先写本地草稿、保存时再原子替换根值；在作者本机强类型文件引用与草稿动作执行器完成前，嵌套文件字段仅提供 `@` 兼容引用，不投影 Player 动作，也绝不把系统选择器返回的裸路径写入 ProgramDocument。
- 原因：同一边框里混放尾注和按钮、四字段配置打开大弹窗、以及字段名依赖异步目录，会同时破坏理解、密度与离线稳定性。将作者方式写入唯一类型事实，才能让新增官方函数、Player 字段和受控扩展自动获得一致外观，而不是继续按截图修补。
- 后果：Record 目录和函数契约指纹会更新；前后端目录 DTO、快照投影、结构编辑器与测试必须同步。新增 Record 若未声明安全作者方式、字段展示与失败语义，不得作为公开可配置参数进入正式函数库。

## ADR-102：检查器表单采用单行优先与最短编辑路径

- 决定：桌面检查器的标量、枚举、引用、简单表达式与紧凑 Record 叶字段默认投影为一行 `标签 | 32px Control | 同高外置动作`。帮助和校验错误按需出现在下一行；只有多行正文、复杂集合或当前宽度无法同时保留可辨认标签与可用输入区时才回落为纵向布局。
- 决定：能在原 Control 内完成的输入不得先显示只读摘要或打开第二张表单；能由同排动作补充的选择、捕获不得增加模式选择或确认中间页。条件 Control 直接承接布尔值、比较、且/或/非、变量、字段与候选补全，不再提供打开同一字段的外置构建器。只有一行会损害可读性且确实需要保存/取消事务的有界集合、字典、JSON 或深层 Record 才进入轻量聚焦编辑层。
- 决定：该规则由共享 Program Control、结构字段与 Player Control 投影承接，官方函数、项目函数和受控扩展不得自行复制一套纵向表单或弹层策略。触控宿主可放大点击目标，但不能改变字段层级、动作含义或额外引入编辑步骤。
- 原因：把每个标签、输入和动作机械拆行，或把所有结构值都放进弹层，会让少量参数看起来像长文档，并让一次赋值被放大成多步任务。单行优先保留高密度可扫读性，最短路径减少学习和操作成本，同时仍为复杂事务保留明确边界。
- 后果：新增 Control 与 Record 契约必须同时通过单行几何、窄宽回落、键盘焦点、错误说明和聚焦事务测试；截图中“看起来整齐”不能替代真实计算尺寸与操作闭环。

## ADR-103：开发端导航与反馈只保留一套宿主外壳

- 决定：活动栏由宿主的一份稳定工作区清单投影为 `compact` 图标模式和 `labeled` 图标加名称模式。首次使用默认文字模式，顶部品牌/项目图标以及“视图”命令切换模式；偏好属于当前设备用户，不写入项目或发布包。窄宽可以临时只投影图标，但不能覆盖偏好。工作区按钮继续只负责切换工作区和展开/收起侧栏。
- 决定：所有第一方与受控扩展左栏组合 `NavigationPane / PaneHeader / ListToolbar / ObjectListItem` 公共原语，统一背景、标题、有效备注、动作、搜索、列表密度、层级和选中状态。`NavigationPane` 唯一负责把标题动作投影为 28px 纯图标按钮，页面只提供 Lucide 图标、tooltip、可访问名称和命令；`PaneHeader` 必须穿透动作组容器统一按钮，`ObjectListItem` 唯一持有弱橙背景与无圆角 2px 直线标识。领域页面不得复制或叠加一套侧栏 CSS。
- 决定：运行输出、当前值和问题保留各自的数据语义，但只进入一个 `BottomFeedbackPanel`，以标签切换。外壳唯一持有高度、拖拽、背景、通用动作和关闭；活动栏与状态栏只是打开相应标签的快捷入口，内容页不能再持有固定面板高度。
- 原因：图标栏对熟练用户高效，但对新用户缺乏发现性；逐页实现标题、搜索、列表和选中态会让相同操作在切换页面时持续改变。问题、日志和当前值相关但用途不同，把它们拆成多个外壳会浪费空间，把数据混成一个列表又会破坏诊断语义。
- 后果：新增页面和扩展必须通过共享外壳契约测试才能接入。自动验收检查计算样式、持久化、窄屏、键盘和单一底部尺寸所有权；浏览器旅程分别覆盖初次用户文字模式和熟练用户紧凑模式。

## ADR-104：右侧检查器只保留一套任务语法

- 决定：程序、资源、项目变量、运行目标、Player、回放、扩展和计划的右侧区域统一组合 `InspectorHeader / InspectorBody / InspectorSection / InspectorField / InspectorDisclosure / InspectorFeedback`。页面可以拥有领域内容，但不能复制区块层级、字段节奏、折叠行或状态反馈 CSS；后续第一方页面与受控扩展也必须使用同一出口。
- 决定：检查器主标题使用当前对象或函数契约的业务名称，可选元信息只显示一条短状态。完整语句投影、资源哈希与稳定 ID 不再作为标题或正常字段值的视觉回退；稳定引用通过目录补全人类名称，ID 只保留在持久化、命令、复制和诊断边界。
- 决定：测试、选择、捕获、派生条件等辅助动作归属参数区块或具体字段。动作状态和结果原位出现，不单独创建一级区块；正文只保留一级任务区块、字段、按需反馈和低频折叠四种层级。`primary / advanced / contextual / internal` 继续是参数披露唯一事实。
- 原因：单个字段即使满足 32px 和单行规则，若标题泄漏内部 ID、辅助动作另占区块、页面分别维护间距和反馈，整体仍会产生五六种竞争层级并在切换页面时跳动。统一任务语法可以在不删除能力、不改变强类型值或宿主契约的前提下减少认知与视觉噪声。
- 后果：共享检查器组件、Program Control 和八个工作区必须迁移到公共类与出口；Harness 同时检查源码消费、计算样式、窄宽、状态、键盘和真实浏览器任务。领域数据、ProgramDocument、Player Schema、Runtime 与持久化格式不因此改变。
- 修订（2026-09-07）：字段几何不再把所有短文本、枚举和引用机械压成横向一行。共享 Control 契约只把开关、短状态等稳定紧凑控件投影为标签与 Control 同排；其余字段统一为标签在上、Control 与所属动作在下。该修订只改变公共呈现规则，不改变字段值、命令、持久化或运行语义。

## ADR-105：中央语句使用版本化语义摘要契约

- 决定：官方、项目和受控扩展函数通过同一个 `statement_summary` 线格式声明中央流程摘要。服务端把摘要模板确定性投影为固定文字与稳定参数槽；参数槽携带 `parameter_id`、语义角色和自动表现提示，真实值仍只来自 ProgramDocument。扩展不得注入 HTML、CSS 或私有中央组件，省略摘要时只显示规范函数名。
- 决定：中央摘要只负责无需悬停即可理解的基础流程语义，并保持单行、只读；完整参数始终在右侧检查器。当前不冻结摘要参数数量上限，后续只有真实扫读证据证明过载时才增加限制。图片缩略图位于图片参数槽原位，自动时间戳名称显示为“未命名图片”；当前渲染行按资源复用预览请求，失败或失效使用固定尺寸可读回退，稳定 ID 不进入普通界面。
- 决定：IDE 作者可以在右侧查看和配置自己使用的账号、密码等真实值；本 ADR 不增加作者侧强制脱敏。Player 只接收开发者明确发布的签名值槽，发布暴露边界继续由 Player 契约负责。中央是否省略长值依据流程可读性，而不是替开发者作安全决定。
- 原因：现有函数模板、表达式文字和语句列表资源追加形成三条摘要路径，使同一个值在函数、结构语句和图像行中表现不同，并迫使新增函数继续增加页面特例。结构化摘要契约让函数只声明业务语义，统一投影器和渲染器长期负责表现与失败状态。
- 后果：官方函数目录契约 Schema 提升；摘要文字变化会更新契约指纹但不改变 ProgramDocument、参数、返回或运行语义。扩展函数契约增加可选摘要模板字段并保持旧包可读。自动测试必须覆盖契约参数引用、扩展校验、语义投影、资源预览复用、失效回退和旧摘要兼容。

## ADR-106：操作录制只生成可审阅的 ProgramDocument 骨架

- 决定：操作录制会话只暂存基础输入、窗口、控件和目标事件；停止后确定性投影为现有官方函数调用，作者确认时以一个结构命令写入 ProgramDocument。录制器不新增宏格式，不推断条件、循环或扩展私有函数。
- 原因：基础动作可以从宿主事件可靠观察，业务意图不能。直接保存另一种宏会产生第二编辑事实，自动猜测复杂意图会制造看似成功的错误脚本。
- 后果：控件树存在时优先生成控件路径；游戏/画布生成目标空间坐标和路径，并只提出由用户确认的图像/OCR替换建议。插入前可审阅，插入后可一次撤销。

## ADR-107：一次控件捕获保存同一控件的确定性策略集合

- 决定：用户只捕获一次目标控件；系统从同一快照生成主策略与有序后备策略并立即回测。Runtime 仅在当前策略产生唯一完整候选时继续，歧义停止且不产生输入副作用。
- 原因：要求用户捕获两个控件不能提高同一目标的稳定性；保存多种稳定属性组合可以抵抗名称、层级或自动化 ID 的单点变化，同时仍保持可解释和可审计。
- 后果：选择器契约升级为 `ControlSelectorV2`；运行日志记录实际策略；重新捕获经影响分析和项目事务更新引用。概率性静默自愈不进入本期。

## ADR-108：统一触发器属于项目控制面

- 决定：`TriggerDefinitionV1` 首期绑定已有 IDE 项目函数，只决定启动时机。防抖、冷却、并发、目标和权限在创建普通运行请求前判定；触发器不进入 ProgramDocument，也不随项目静默进入 Player 包。Player 继续使用自己的签名运行方案和计划控制面；未来允许作者显式发布触发器时必须另立终端权限、配置冲突和宿主生命周期切片。
- 原因：快捷键、应用和文件事件属于宿主生命周期，不是脚本内部执行步骤。把它们建成函数或第二脚本会混淆“何时启动”和“启动后做什么”。
- 后果：运行中心提供唯一“启动方式”入口；禁用状态零订阅；首期发布闭包确定性排除 IDE 触发定义。首期只实现 Windows 快捷键、应用生命周期/焦点、文件目录变化和登录启动。

## ADR-109：浏览器 DOM 以第一方扩展实现、以普通函数体验使用

- 决定：浏览器 DOM 使用第一方签名功能扩展贡献宿主、`DomSelectorV1`、函数和捕获能力；作者仍通过统一函数库、ProgramDocument、中央摘要和右侧 Control 使用，不建立第二编辑器。
- 原因：DOM 会话、驱动和元素生命周期与 HTTP、桌面 UIA 均不同，适合独立扩展闭包；但用户没有理由学习另一套编排模型。
- 后果：首期 Windows 支持本机 Edge/Chrome；未启用时零后台和零运行期下载。DOM 不进入 HTTP 原子函数，不与 UIA 选择器隐式转换，验证码绕过、任意脚本注入和网络拦截保持范围外。

## ADR-110：官方扩展是同一签名包的受治理分发范围

- 决定：官方、用户和项目扩展使用同一 Manifest、签名、密封产物及运行契约。新领域扩展先通过用户/项目范围手动导入完成全生命周期，再把完全相同的产物提升到官方只读范围。
- 原因：单独维护内置版会绕过真实导入、权限、锁定和卸载路径，使扩展平台无法被自身产品验证。
- 后果：自动测试从分发包安装开始；项目向导只能显式推荐而不能静默导入；当前签名目录仍是包载体，单文件安装格式另立规格。

## ADR-111：结构剪贴板与批量编辑使用原子 Program 命令

- 决定（2026-09-09 修订）：`Ctrl+C` 保存当前选择的不可变类型化结构快照而不修改项目，并允许在同一工作区 generation 的其他项目函数中粘贴；`Ctrl+X` 仍只建立当前 ProgramDocument 内不立即删除的待移动集合。`Ctrl+V` 在当前主选中语句或分支锚点执行复制或移动。复制统一再生整个集合的自有稳定 ID 并重映射集合内部符号引用，项目级引用保持稳定；跨函数粘贴由目标函数契约和作用域重新校验，不可见的外部局部引用、非法层级或返回类型不兼容时整体拒绝并保留复制剪贴板。跨函数切换只取消剪切态；切换项目、工作区重连、按 `Escape` 或重置会清空结构剪贴板。
- 决定：批量移动、缩进、删除、粘贴和同类参数修改都经受类型约束的命令包进入 Program Service，在单一 revision 检查内完成一次校验、一次保存和一个撤销条目。客户端不得以连续单命令请求冒充原子操作。
- 决定：同一函数调用的多选检查器复用函数契约与 Program Control，只编辑公共参数。混合值先显示不确定态，只有作者明确提交的字段才覆盖全部选择；备注、结果绑定、危险审核和其他单语句动作不进入批量模式。
- 原因：即时复制违反平台通用快捷键预期；逐条网络写入会产生部分成功、多次撤销和中间非法引用；另做一套批量表单又会让同一参数出现不同编辑语义。
- 后果：Program API 使用既有命令包和结构快照粘贴契约，IDE 的复制剪贴板提升为项目工作区级临时状态，剪切态继续属于文档。系统剪贴板、跨项目粘贴、跨函数剪切移动和异构参数批改保持范围外；跨函数复制不创建第二套格式、不绕过目标函数验证，也不产生源文档写入。

## ADR-112：Windows 同名窗口使用可验证捕获绑定而非永久句柄或枚举序号

- 决定：Windows 窗口目标可以携带版本化捕获绑定。捕获复用现有原生冻结帧宿主，从点击位置解析可见顶层窗口并记录稳定 `binding_id`、标题、窗口类名、可执行文件名及当前实例 HWND/PID/进程创建时间。Runtime 先验证当前实例，失效后只在稳定特征唯一命中时恢复；仍有多个候选即明确要求重新捕获。
- 原因：标题、类名和程序可能重复，单独 HWND/PID 又只在当前生命周期有效且可能复用。窗口序号、左右位置或任意首项会在双开账号交换、重启或窗口层级变化后产生 P0 级误操作。
- 后果：目标表单增加共享图标式捕获与即时测试；手工修改标题规则清除旧绑定；IDE 探测、Capture、视觉/输入 Runtime 与 Windows Player 共用同一解析器。捕获候选和测试失败只影响草稿，未经保存不改项目；跨机器仍无法唯一解析时必须在目标机器重新捕获，不伪造永久 Windows 窗口身份。

## ADR-113：窗口初始化复用当前目标身份并显式保证完整可见

- 决定：Windows 目标作用域提供 `窗口.获取当前目标窗口`，把已由目标绑定解析并复核的窗口转换为仅在本次运行有效的 `window_ref`；不得把作者机 HWND、PID 或同名窗口序号写进流程。`窗口.确保完整可见`只在必要时把外框夹入当前最近显示器的工作区，不改变尺寸和 Z 序；工作区不足时明确失败。
- 原因：同名多开项目已经由目标绑定解决身份问题，初始化流程再次按标题或进程号查找会绕过该安全边界。截图和坐标又以客户区为准，因此窗口定尺与可见性必须使用同一个已绑定实例。
- 后果：项目函数可以在目标作用域内取得当前窗口后执行还原、客户区定尺、可见性和激活；离开该作用域后当前目标恢复为调用前状态，运行期 `window_ref` 也不得持久化或跨运行复用。

## ADR-114：Windows 自动化宿主在启动边界一次性申请管理员权限

- 决定：Windows Player 的可执行清单声明 `requireAdministrator`，在宿主启动时通过一次 UAC 建立运行期权限；流程语句和单次运行不得在执行途中静默提权。网页开发端仍是普通浏览器页面，但承载本机 API、窗口管理、捕获与输入的 EasyCode 后端必须由自提升启动脚本启动。Android 与无桌面目标不继承 Windows 提权语义。
- 原因：Windows UIPI 禁止普通权限进程调整、激活或向高权限目标注入输入。运行到一半才发现权限不足会留下部分执行状态；给系统 Python 全局设置管理员兼容标志又会污染无关项目。
- 后果：Windows Player 每次启动都会显示系统 UAC；开发端第一次启动或重启后端也需要用户在交互桌面确认。自动化测试验证 Player 打包清单和启动脚本的提权声明，真实宿主验收必须核对后端/Player 与目标进程权限级别一致。

## ADR-115：Player 窗口重绑与多实例使用同一签名设置契约并隔离宿主资源

- 决定：Windows 目标新增可由作者显式发布的 `target.window_binding` 设置槽和 `capture-window` 终端动作。终端用户在空闲、已保存方案中从全桌面冻结帧点击一个窗口，确认后只把版本化捕获绑定原子写入当前 Player 实例的当前方案；运行与后续字段捕获都消费该方案合并后的有效目标。它不是可替换任意目标的第二套模型，稳定 `target_id`、目标类型、工作区域和已签名权限仍由发布包决定。
- 决定：Hub 打开的每个 Player 实例使用操作系统原子分配的 loopback 端口，并以 `EASYCODE_PLAYER_DATA_DIR` 隔离方案、日志、图片覆盖和 WebView2 用户数据；实例窗口标题显示实例名。Windows Player 可执行清单继续声明 `requireAdministrator`，每个实例在启动边界独立完成 UAC，不在运行中提权。
- 原因：仅覆盖同名窗口标题无法区分两个游戏账号；固定 8000 端口和共享 WebView2 数据目录又会让第二个 Player 实例启动冲突或共享可变状态。把重绑放进已签名目标设置槽可以复用既有权限、revision、取消保值和目标校验闭环，同时不开放任意目标替换。
- 后果：作者若希望客户选择窗口，必须在 Player 设计器中加入“目标窗口实例”并允许 Windows“捕获目标窗口”。同一台机器上每个实例分别保存绑定；句柄失效且稳定特征仍有歧义时运行/检查必须停止并要求重新捕获。自动验收覆盖端口竞争、实例数据根、窗口绑定回填、方案 revision 和管理员清单；真实 Windows 放行仍需用两个同名窗口冒烟。

## ADR-116：缺失调用参数由显式 Program 命令按锁定契约恢复

- 决定：当调用语句缺少当前契约声明的参数节点时，ProgramDocument 仍是唯一可编辑事实；客户端不得合成默认节点，Program Service 也不得在普通读取时静默写盘。右侧检查器提供一个就近恢复动作，提交 `repair_missing_arguments` 后由服务端一次补齐该调用全部缺失参数，并纳入 revision、原子保存和撤销历史。
- 决定：恢复值只来自当前工作区锁定的函数契约；有默认值生成强类型默认节点，无默认值生成显式 `unset`。已有值与稳定 ID 原样保留，未知参数不自动删除，危险调用审核指纹失效。无缺失、契约不存在或并发 revision 冲突时不产生写入。
- 原因：逐字段显示“需由 Program Service 修复”却没有恢复入口会阻断脚本作者；由前端或每个 Control 各自补默认值又会制造第二事实源和类型漂移。显式单命令既能恢复当前草稿，也避免读取项目时发生用户不可见的修改。
- 后果：所有官方、项目和扩展调用共享同一恢复路径；函数契约兼容增加参数后仍需作者明确确认补齐。项目格式和运行语义不变，不引入旧项目迁移层。

## ADR-117：Windows 同名多开使用有界定向后台输入与显式效果验证

- 决定：`输入.点击`、`图像.点击一次` 和 `图像.点击直到消失` 保持现有参数契约，不给每条语句增加“后台/物理”选择。Windows 目标驱动先把目标点解析到所属的最深可用子窗口，再以有界同步窗口消息直接交给该窗口过程；普通单击使用 50ms 平台最小按压时间，避免按下与抬起被 Chromium/DirectX 目标折叠进同一渲染帧。投递设置短超时并在窗口挂起时中止，不移动或占用物理鼠标。ADB 与 Android 本机继续使用各自的目标原生输入。
- 决定：窗口消息被处理仍只代表 `delivered_unverified`。需要确认点击生效的流程使用图片、文字或页面状态作为后置条件，并在未变化时重试、走失败分支或停止；不得把“消息已送达”冒充业务成功。物理输入只保留为桌面目标或明确兼容场景的末级能力，不作为同名多开与无人值守流程的默认回退。
- 原因：同名多开需要把动作精确发给指定 HWND，物理鼠标会抢占用户操作且无法隔离多个实例。与此同时，DirectX/Chromium 游戏可能处理 Windows 消息却不产生业务效果，所以输入可靠性必须由“定向投递 + 画面后置条件”共同建立，而不是把复杂度扩散到每个函数表单。
- 后果：已有 ProgramDocument、IDE、Player 和标准函数契约不发生兼容变化；Windows 多开验收必须证明两个同名窗口分别接收定向后台动作、物理光标不移动，并通过真实画面后置条件验证每次业务效果。无法接受窗口消息的目标必须明确报告不支持后台操作，不能静默改用物理鼠标。

## ADR-118：多实例 Player 采用单一控制台与独立运行进程

- 决定：后续 Windows Player 的默认多开入口采用一个原生 Player 控制台窗口。左侧固定展示当前用户已登记实例及各自的运行状态和高频运行控制；选择实例后，中部显示该实例的已发布表单与运行方案，右侧显示环境检查、运行状态和日志。控制台只消费签名发布包与 Player Hub 数据，不引入 IDE、ProgramDocument 或作者接口；独立 Player 窗口继续作为故障恢复和单实例诊断入口。
- 决定：单窗口只统一用户界面，不能把多个自动化实例合并为一个运行进程。每个实例继续使用独立子进程、系统分配的 loopback 端口、数据目录、WebView2 用户数据、窗口绑定、运行现场和日志；控制台通过受限本机控制通道管理它们。一个实例崩溃、卡死、停止或更新不得终止其他实例。管理员权限在控制台/子进程启动边界显式建立，流程中途不提权。
- 决定：关闭控制台只关闭空闲工作进程，不把关闭管理界面解释为停止业务任务。运行中或暂停的实例在控制台退出后继续到终态并随后自动退出，新控制台可在此期间通过实例目录中的受限描述文件重新接管；显式停止只能来自对应实例的运行控制。
- 原因：每开一个账号就增加一个完整窗口会降低切换和监控效率，但把实例改成同进程标签页会扩大故障半径，并让端口、捕获会话、窗口绑定、更新与运行现场重新共享。控制面统一、运行面隔离可以同时获得一个窗口的操作效率和多进程的可靠性。
- 后果：该控制台必须作为单独垂直切片实施，至少闭环实例枚举、方案 revision、参数保存、窗口捕获、启动/暂停/继续/停止、日志游标、进程重启恢复、同名窗口隔离和无 IDE 客户机打包。上述验收完成前，现有“一实例一窗口”仍是正式可用模式，不得以只有实例列表或只能再开窗口的半成品冒充统一控制台。

## ADR-119：IDE 刷新后接回原运行会话

- 决定：IDE 页面刷新、渲染器重建和短暂前端断线只销毁界面连接，不自动取消本机 Runtime 中仍处于 `queued / running / paused` 的任务。工作区重新载入时通过服务端按权威项目路径查询活动会话；标签页以临时保存的 `execution_id` 精确接回自己的会话，记录不存在时才采用该项目最新活动会话。接回沿用原事件游标、运行身份和目标所有权，不编译或启动第二份流程。
- 决定：终态会话不作为活动运行恢复。后端进程重启、会话过期或查询返回不存在时，IDE 清除旧控制态，说明原会话已经结束并允许用户重新运行；不得猜测恢复调用栈。多个标签页或多个运行并存时，服务端返回项目内完整活动集合，标签页优先自己的会话，不能仅靠一个全局“最后运行”覆盖所有标签页。
- 原因：浏览器刷新并不代表用户要求停止业务任务。只在前端内存保存运行编号会让后台任务继续占用目标，而新页面既无法停止也无法继续，最终表现为“流程不能重启”；自动取消又可能中断已产生副作用的长流程。
- 后果：IDE 增加工作区范围的活动运行只读接口和刷新恢复测试。页面离开不发送隐式停止；明确停止继续使用现有取消 API。进程崩溃后的持久执行恢复仍不在本决定范围内。

## ADR-120：Player 布尔选项固定状态是可执行契约

- 决定：`key-value + map<string,bool>` 的单个选项可以声明 `fixed_value: true | false` 与可选 `fixed_reason`，分别表达开发者强制必选和强制不可选。该字段不扩展到普通枚举、任意字典或其他 Control；选项必须引用默认字典中真实存在的字符串键。
- 决定：固定状态由同一 schema 3 表单事实贯穿 IDE 设计器、共享 Player Control、方案持久化和运行绑定。Player 使用锁图标、状态文字、禁用复选框及可访问说明投影；后端在保存方案和应用绑定时再次写入固定值，拒绝依靠前端禁用来保证语义。
- 原因：仅把复选框置灰既不能区分“暂时不可用”和“作者强制”，也能被旧方案、直接请求或临时覆盖绕过。脚本作者需要保留完整任务清单，同时明确哪些能力当前不交付或必须启用，而不必把本属一个列表的键拆成许多项目变量。
- 后果：Player option 线格式新增受约束的可选字段，但 schema 版本不变；未使用该字段的表单保持原义。表单校验、配置方案、预览、独立 Player 与 Android Player 必须共享归一和失败语义，新增实现以 `REQ/AC-PLY-OPTION-*` 验收。

## ADR-121：Player 品牌属于表单事实，原生窗口只投影签名发布结果

- 决定：schema 3 Player 表单根级保存应用名称与可选图片资源 ID。名称继续使用 `title`，图标使用 `icon_asset_id` 且只允许项目中真实存在的 PNG、JPG、JPEG 或 BMP 图片资源；未设置时统一回退 EasyCode 默认名称与图标。
- 决定：发布组装器从已验证 `.ecplayer` 的表单和资源闭包生成只用于显示的 `product.json` 与图标副本。Windows 原生宿主以它设置窗口标题和任务栏图标，Vue Player 以签名表单设置标题栏；它不改变产品身份、签名、权限或运行入口。生产 Player 默认使用系统分配的 loopback 端口，直接双击可执行文件时自动发现同目录 `release` 中的包、信任根和品牌元数据。
- 决定：Windows Player 保持无浏览器页头的无框原生窗口，并由共享标题栏提供最小化、最大化/还原和关闭。DWM 可见边框与圆角关闭，边缘仍保留不可见缩放热区。桌面端页面导航、参数区与运行区分别承担纵向滚动；窄屏改为一个连续纵向滚动面，横向内容自适应而不把必要操作裁掉。
- 原因：每个项目重新打包通用 Runtime 会增加时间和分叉风险，而固定名称、固定图标、固定 8000 端口和依赖浏览器样式又会让正式交付不可用或缺乏产品身份。将品牌保存在表单、在发布边界派生原生元数据，可以保持一个运行时并让每个发布项目获得稳定外观。
- 后果：资源删除检查必须把 Player 图标视为真实引用；名称、图标、端口发现、原生窗口控制和长表单滚动进入 Windows Bundle 冒烟。可执行文件内部版本资源仍属于通用 EasyCode Runtime，不由项目品牌修改。

## ADR-122：Player 暴露字段复用共享强类型 Control 并预选安全终端动作

- 决定：IDE 与 Player 复用同一强类型 Control 原子、值形状和 `parameter_ui` 动作元数据，不为 Player 维护一套把窗口、图片、区域、控件、文件或颜色退化为字符摘要的表单。新加入 Player 的字段预选类型与平台交集内、已经有真实宿主承接的安全推荐动作；作者可逐项关闭，最终显式集合才进入签名发布闭包，既有字段不自动改写。
- 原因：开发者明确暴露字段的目的就是让终端用户配置它。仍要求作者在另一个折叠区逐个发现并打开显而易见的取点、框选、图片、控件、窗口或文件动作，会让真实能力在 Player 中看似不可编辑；另写 Player 控件还会造成两端类型和交互持续漂移。
- 后果：暂时不可用的已签名动作必须留在字段旁并显示恢复原因，未保存方案不能令入口消失；权限仍只在终端用户主动触发时申请，脚本不能静默调用。新增值类型或采集动作必须先进入共享 Control、强类型返回、宿主能力和发布闭包，不能只补一个前端按钮。

## ADR-123：便携 Player 默认进入已验证多实例控制台

- 决定：正式便携分发中的 EXE 或随包启动脚本无显式参数启动时，先验证并把所在分发登记到当前用户 Player Hub，再在同一进程打开控制台并聚焦该产品。控制台保持一个可见窗口，实例仍使用独立进程、端口和数据目录；显式单实例、控制台工作进程和维护命令不经过默认分派。登记失败时回退为该签名包的单实例 Player并保留诊断。
- 原因：多实例控制台已经是权威模型，但旧打包入口显式传入单包参数，实际绕开了控制台，用户看不到实例列表和“新建实例”。让安装入口与架构默认值一致，才能同时获得单窗口管理体验和实例故障隔离。
- 后果：打包清单、启动脚本、直接双击 EXE、Hub 登记、控制台聚焦和失败回退必须同一切片测试；不得把多个自动化运行时塞入同一个 WebView 或共享同一方案/日志目录。

## ADR-124：冻结 Player 的运行能力不得经由旧执行器聚合包延迟加载

- 决定：vNext OCR 引擎、预处理和结构化结果移动到不依赖节点执行器、条件、旧 Player 或 IDE 服务的 runtime-neutral 模块；vNext Runtime、预览和回放直接依赖该模块，旧 OCR 执行器只做兼容外壳并反向复用。冻结清单显式携带新模块，不通过 `core.node_executors.base.__init__` 触发旧注册器。
- 原因：Python 导入某个执行器子模块前会先执行包初始化；旧初始化会一次性加载分支和条件实现，而独立 Player 正确排除了这些作者/旧运行依赖，导致 OCR 第一次调用才出现 `core.conditions` 缺失。只把整个旧包塞回成品会破坏最小发布边界并掩盖同类问题。
- 后果：Player 运行闭包增加对被排除旧根包的静态引用检查，并在阻断这些包的进程中实际触发延迟 OCR 路径。冻结候选还必须执行真实 OCR 冒烟；以后任何运行能力重新引入 `core.node_executors / core.conditions / core.params / core.player` 都在打包前失败。

## ADR-125：Player 的低频重能力由作者显式发布

- 决定：运行录制进入 Player 表单的版本化 `features.recording` 契约，缺省关闭。关闭时界面、方案 API 和运行时都不可启用录制；开启时复用既有录制闭环。共享 Windows Runtime 可以保留通用实现，但项目发布权限和运行活动严格按签名表单收缩。
- 原因：录制对长稳诊断很有价值，但不是每个小脚本的日常任务。把它永久放在运行准备区会增加理解、权限和磁盘负担；删除能力又会损害复杂项目的诊断路径。
- 后果：作者端增加一个项目级开关；Player、方案保存、启动计划、历史轮询和验收都读取同一事实，不能只靠前端隐藏。以后新增同类重能力沿用显式发布模式，不能默认塞入每个项目。

## ADR-126：Player 页面与实例生命周期收束到紧凑共享导航

- 决定：Player 少量页面使用内容区顶部页签，溢出页面进入“更多页面”；控制台新建实例由 Hub 直接生成唯一名称并原子选中。实例删除只允许空闲且无引用的 revision，并把默认数据目录隔离到本机恢复区。
- 原因：固定页面侧栏和实例创建小表单同时占用横向与认知空间；实例删除又不能为了简洁牺牲运行隔离和数据恢复。
- 后果：页签与溢出菜单成为共享组件；实例命名和删除规则属于 Hub 后端事实，前端不自行猜测名称或直接删除目录。

## ADR-127：Player 显式关闭是受确认的完整进程退出

- 决定：独立 Player 与多实例控制台的标题栏关闭、系统关闭手势和 `Alt+F4` 使用同一宿主握手。没有活动任务时直接完成释放；存在运行、暂停或排队任务时由共享应用内确认说明影响。用户取消时窗口与现场完全不变；用户确认时，独立 Player 停止当前运行，多实例控制台停止全部活动实例，并在 Capture、录制、Runtime、Worker 与本地 HTTP 服务完成有界回收后才授权原生窗口关闭。停止准备失败时原生窗口不得先消失。
- 决定：正常关闭完成 ASGI 与本机服务的有序清理后，冻结 Player 进程执行最终强制退出兜底，防止 OCR、采集或第三方原生库遗留的非守护线程让无窗口进程继续占用端口和发布目录。该兜底不跳过业务停止与 lifespan 清理。进程崩溃、系统强杀和断电仍不解释为用户同意取消任务；控制台工作进程保留既有孤儿检测与终态回收能力。
- 原因：可见窗口消失但 `EasycodePlayer.exe` 仍运行，会让用户误以为脚本已停止，并阻塞下一次启动、更新和替换 `Player_Bundle`。只在 Vue 中关闭 WebView 或只向当前实例发送停止都不能闭合多实例运行边界；原生宿主必须等待应用确认，应用必须以运行时真实状态决定是否需要确认。
- 后果：本决定取代 ADR-118 中“正常关闭控制台时活动任务继续运行”的条款，但不改变异常崩溃后的恢复语义。标题栏、原生 WebView2 宿主、Player-only API、控制台 Worker 管理、冻结入口、打包占用错误和真实 Windows 验收必须作为一个垂直切片更新。
## ADR-128：固定位置点击与视觉后置条件以两个官方标准函数交付（2026-09-11）

- 决定：增加 `图像.点击位置直到出现 / 点击位置直到消失`，以规范 `ProgramDocument` 组合新帧图像查找、指定位置单击、单调超时、可取消间隔和连续稳定帧；融合 Runtime 只能作为等价投影。两个函数都先观察，目标状态已成立时零点击返回；到期返回 `ImageClickConditionResult`，不把业务未达成伪报为异常。
- 原因：真实桌面/游戏流程大量出现“点击入口 A，直到页面标志 B 出现/旧标志 C 消失”。用现有 `点击直到消失` 会错误点击被观察图片自身；逐句手写循环则容易遗漏新帧、超时、取消或稳定帧，且设备响应差异会把流程推进到错误页面。
- 后果：IDE、Windows/ADB Runtime、Android 本机、Player 预检、发布闭包和无副作用预览共享同一强类型参数/返回契约。多图片竞速、最高分分支、拖拽直到条件等仍按现有 ProgramDocument 组合表达，不因单项目需求扩张通用目录。

## ADR-129：表达式草稿延迟校验，可选结果支持失败即停的严格成员访问（2026-09-11）

- 决定：统一表达式输入器把输入、粘贴和中文输入法组合内容保留为未提交草稿；草稿可以暂时不完整或暂时不是字段最终类型。父级已保存值的诊断在编辑期间不继续标红；只在 Enter、Ctrl+Enter 或有效失焦时校验完整结果，失败保留草稿与焦点，成功才提交强类型值树。
- 决定：未收窄的 `optional<Record>` 根和 Record 内可选成员继续显示真实逐级字段，并允许提交为既有 `member_access`。该节点语义是严格消费：来源为空时 Windows 与 Android Runtime 统一抛出 `runtime.optional_empty`，当前运行失败并停在消费语句，后续副作用不执行；来源有值时结果仍是字段声明类型。它不做隐式真假转换，也不伪造空文本、零、坐标或记录。
- 决定：“有结果”条件仍保留为无结果属于正常业务分支时的推荐写法，但不再是读取图片、OCR、窗口、控件等结果成员的强制仪式。候选只提示两种失败语义的差异，不因尚未收窄而禁用字段。
- 原因：流程作者经常把“必须找到图片并点击”当作当前步骤的前提；强迫每次都增加一层判断会制造大量无业务含义的分支，而在输入未完成时显示最终类型错误又会直接阻断正确表达式。Runtime 已能在成员求值点精确失败，因此可以在不牺牲可解释性和类型安全的前提下提供短路径。
- 后果：值目录、Program 校验、统一输入器、Windows Runtime 与 Android Runtime 必须通过同一严格访问验收；错误日志保留稳定错误 ID、当前语句和调用栈。需要把无结果当作 `false`、继续或默认值的流程仍必须显式判断或配置默认值，不能依赖严格访问吞错。

## ADR-130：视觉分析区域按当前帧交集执行（2026-09-11）

- 决定：`图像.*`、`文字.*` 与 `颜色.查找` 的区域是分析范围提示。当前目标因窗口边框、DPI、方向或客户区出现少量尺寸变化时，Windows、ADB、Android 本机、无副作用预览和离线回放统一使用作者区域与当前帧的交集；部分越界继续分析并保留帧坐标，完全无交集返回该函数类型的正常空结果。区域格式错误或宽高不为正数仍抛出永久 `vision.region_invalid`。
- 决定：`画面.保存` 不采用上述宽容语义。文件输出继续要求作者裁剪区域完整位于画面内，以免静默生成尺寸、内容或下游契约不同的文件。
- 原因：靠近窗口边缘捕获的分析区域常因客户区只变化几个像素而越出右侧或底部。把仍然存在的大部分有效像素全部拒绝，会让长期运行的视觉流程因无业务意义的尺寸抖动中断；而完全无交集本质上等同本帧未命中，不应伪装成驱动异常。
- 后果：视觉日志和预览必须在发生裁剪时展示实际结果，离线回放与正式 Runtime 不再漂移；图片模板大于裁剪后区域时正常未命中，OCR 无交集不得启动引擎。真实跨平台冒烟仍需分别覆盖右/下边缘缩小、左/上裁剪和完全无交集。

## ADR-131：颜色使用共享 RGBA Control 与冻结帧取色（2026-09-11）

- 决定：`color` 的可编辑事实仍是 `record_type=color` 的四个稳定字段。IDE 与 Player 复用同一个 RGBA Control，固定输入接受 `#RGB / #RRGGBB / #RRGGBBAA` 并规范化显示；不把颜色保存为自由字符串，也不要求先调用运行时函数取得固定颜色。
- 决定：增加逐字段动作 `pick-color`。Windows、ADB 与 Android 本机都从当前目标的一张冻结原帧点选并采样一个像素；展示缩放只影响投影，不改变原帧坐标。Player 仍需作者显式开放并进入签名能力闭包，脚本不能静默发起取色。
- 决定：取消、目标或 revision 变化、宿主失败、帧尺寸变化和越界结果都保留旧值；确认后一次性提交完整 RGBA，绝不以黑色或部分字段兜底。运行时 `颜色.读取` 继续是普通函数，与 Control 取色动作分工而不重叠。
- 原因：颜色已经是官方基础类型和运行能力，但缺少直接物化入口与捕获动作，使新建颜色参数卡在通用表达式中，也让 Player 暴露颜色后只能看到不可理解的结构。沿用稳定值槽和 Capture Session 可以补全体验而不增加第二套模型。
- 后果：函数/扩展默认 UI、统一输入器、共享 Control、原生捕获宿主、Player 发布闭包、Windows/ADB 与 Android 本机确认链按 [颜色值输入与取色规范](vnext/COLOR_AUTHORING.md) 同一切片验收。

## ADR-132：Player 常态诊断由控制台保底，完整录制继续按需开启（2026-09-11）

- 决定：Windows Player 在未开启运行录制时仍保留低成本、容量有界的进程日志、运行事件日志和失败终态诊断。多实例控制台为选中实例始终显示“复制摘要”和“诊断包”两个带文字的紧凑动作，不以无文字图标或悬停提示作为唯一入口；导出由控制台进程直接读取该实例隔离目录，因此实例工作进程已退出、端口已失联或嵌入页无法请求自身 API 时仍然可用。独立 Player 的正常运行失败继续提供现有单次运行诊断包。
- 决定：最近诊断包按需在本机生成，不订阅画面、不编码视频、不启动后台上传。默认只包含版本与实例状态、工作进程描述、容量受限的控制台/实例日志尾部和最近一次已经生成的失败诊断；不包含方案值、完整录制、项目源码或任意目录内容。已有失败诊断中的变量继续走既有脱敏规则，可能包含的一张失败截图在清单中明确披露。进程日志使用滚动文件并停止记录成功的高频轮询，只保留生命周期、写操作、失败请求和异常。
- 决定：控制台工作进程所有权同时使用 PID 探针和短时文件租约判断。Windows 因权限或安全软件无法查询仍然存在的控制台 PID 时不得把“不确定”当成“已退出”；租约原子刷新遇到短暂文件占用必须重试且不能令状态轮询返回 500。工作进程退出前写入可读退出原因，供最近诊断包收集。
- 原因：运行录制适合低频深度复现，但终端客户通常不会为日常运行承担持续截图、编码和写盘成本。另一方面，把诊断下载只放在实例自身服务上，会在最需要取证的“后端已经退出、前端仍显示旧页面”场景同时失去入口。
- 后果：该能力不改变脚本、ProgramDocument、Player 表单或录制发布契约，也不自动向开发者发送数据。客户无需等待失败或识别无文字图标，随时可在选中实例下取得摘要或 ZIP；开发者仍可在确有必要时另行发布并让客户显式开启完整录制。

## ADR-133：Player 控制台以实例行为运行控制面，以详情栏为诊断与配置面（2026-09-11）

- 决定：左侧实例行直接承接运行/继续、暂停、停止、刷新和删除，操作使用紧凑图标和完整可访问名称，使多实例操作者不必逐个切换详情。售后摘要与诊断包属于当前实例的详情，不占用多实例高频控制行；正常态位于右侧运行管理区，实例 iframe 失联时由控制台同位置的恢复面板承接。没有完整返回语义的“独立窗口打开”暂不展示。
- 决定：控制台实例栏、Player 配置内容与运行栏采用共享可访问分隔条和折叠契约，本机持久化宽度及折叠状态。整个详情区可以折叠为仅实例控制列表；视图状态不改变 Player 表单、运行方案、实例数据或任务生命周期。原生无框宿主必须通过非客户区命中保证四边和四角缩放，不依赖 WebView 内容自行处理。
- 决定：Player Web 与冻结 Runtime 建立显式能力清单。IDE 发布器只允许组装声明满足当前 Web 必需能力的 Runtime；缺少或过期清单属于“运行时未就绪”。诊断下载使用经校验的响应生成本地文件，HTTP 错误、错误媒体类型与零字节响应不得伪报成功。
- 原因：多开时最昂贵的操作是反复切换实例后再到右侧启动或停止；售后诊断却只针对当前对象，不应挤占每个实例的高频控制。无框窗口、固定栏宽和不可折叠详情会阻止多实例控制台适应不同屏幕，而只检查 EXE 文件存在会把新前端和旧后端拼成表面可启动、实际缺路由的交付物。
- 后果：实例控制命令继续作用于隔离工作进程；左侧“运行”通过已加载实例表单启动当前配置，其他生命周期命令走控制台 API。新增跨 Player Web/Runtime 的能力必须更新能力清单和完成门；正式候选仍需真实冻结 EXE 的边缘缩放、五实例控制和失联诊断冒烟。

## ADR-134：作者短语是结构命令，不是第二门源码语言（2026-09-12）

- 决定：EasyCode 1.0 保持 ProgramDocument 为项目函数唯一可编辑事实。中文继续承担目录、摘要、Control、帮助和自然语言搜索；行内编辑器增加临时键盘意图输入，把“调用并判断”“执行直到”等高频意图一次提交为普通结构命令。意图文本不保存，不反向解析既有文档，也不增加 Monaco 或英文/中文源码文件。
- 决定：条件简写只对 `bool`、`optional<T>`、数值、文本、列表和字典采用冻结的类型化适配，并在提交时物化为显式布尔值树。普通函数不能隐藏在条件中；在条件任务里选择查询函数时，由一个原子事务创建一次独立调用、结果绑定和相邻条件。目标、权限、驱动、资源和内部失败继续作为结构化异常传播，不进入“否则”。任意记录、引用对象和未知 JSON 不具有隐式真假含义。
- 决定：通用“执行直到”由 Program Service 原子展开为有界循环、逐轮查询、命中跳出、动作和可选间隔，默认先观察、状态已满足时零动作。它不增加 Runtime opcode 或平权宏格式。经过多项目验证且参数稳定的组合仍可作为官方标准函数，但必须与规范 ProgramDocument 组合等价。
- 决定：项目函数的现有参数/返回模型成为正式作者能力。签名编辑由 Program Service 项目事务维护稳定 ID、函数体引用、调用参数和契约指纹；函数参数可以直接作为 Player 字段来源，不要求复制为项目变量。
- 原因：当前结构安全已经成熟，但作者经常为了一次查询判断或有界重试手工创建变量、条件和循环，中文长条件也会降低可写性。引入可保存文本源码会重新制造解析、格式化、双向同步和第二事实源；把常用意图编译成现有结构，可以同时得到简洁输入、可视理解、类型安全和跨平台一致执行。
- 后果：Program Service、值目录、行内插入器、函数头、撤销重做、调用影响检查和 Harness 按 [`AUTHORING_LANGUAGE_V1.md`](vnext/AUTHORING_LANGUAGE_V1.md) 分阶段闭环。ADR-020/024/066 等禁止普通调用进入表达式的决定继续有效；本决定只缩短作者操作，不放宽运行边界。
